# mpy6a

Или просто **труба**. Это распределённый _WAL_, т.е. **W**rite **A**head **L**og, т.е. сущность предоставляющая
функциональность распределённого лога с группировкой записей по **сессиям**, с возможностью получить записанные
данные для т.н. **незавершённых сессий** (и, опираясь на данные, завершить сессии).

## Как работает.

Есть консенсус-узел в кластере. Это 2N + 1 [машинки](docs/shard-arch-concept.md)
связанные [консенсусом](docs/consensus.md).

Каждый хост является лидером некоего пула рафтов.

1. Клиент случайным образом выбирает один из этих хостов и говорит: хочу завести сессию.
2. Сервер выбирает один из индексов, заводит новую сессию, возвращает её id. Ну и проводит операцию "создай новую
   сессию" через консенсус. Активные сессии хранятся просто в мапе.
3. Клиент шлет команды "добавь в сессию данные" или "перезапиши все данные сессии этими данным"
4. В конце клиент говорит: "закрой сессию" (удаляется нафиг) или "отправь на повтор через T секунд". Если выбрано
   последнее, то сессия летит в дерево упорядоченное по времени повтора. Которое дерево может сброситься в LSM-лист если
   прижмет.

Когда настает время повтора

1. Один из хостов вытаскивает сессию в активные одного из индексов и проводит эту операцию через консенсус.
2. По реквизитам создания сессии определяется к какому классу сервисов она относилась. Поэтому извлеченные данные сессии
   отправляются к нужному типу сервиса.
3. После чего начинается взаимодействие зеркально повторяющее то, что было при создании сессии: []
   добавление/перезапись -> закрыватие/повтор.

Два правила:

- Если во время взаимодействия отвалился клиент, то индекс …
- Если во время взаимодействия отвалился хост консенсус-узла, то один из смежных индексов берет лидерство над сессией
  и …

В обоих этих вариантах и кладет сессию/сессии в очередь повторов с задержкой T.

## Как с этим работать.

Предполагаемый профиль работы - запись намерений в сессии и простая линейная логика в некотором сервисе.

Т.е. мы пишем "сейчас сделаем X", и сразу после этого делаем тот самый X.

И для метода M работающего с WAL-ом должен быть сопряженный метод M' выполняющий **компенсацию** по сигналу от трубы.

С идемпотентной логикой.
Т.е. если например, ситуация: M' при первом прогоне выдал ошибку. Но успешно отработал при втором прогоне M'.
В итоге, результат не должен отличаться от случая, когда мы все успешно выполнили при первом прогоне M'.
