## 1. Scope and the document's place in the sequence

The document is the **prelude**: it fixes the plumbing the consensus driver will later sit on, so that the consensus
document can describe decisions without re-describing sockets, framing and catch-up requests. It has three chapters:
topology, link establishment, transport framing, plus one implementation chapter naming what lives in
`lifetime.Controller` (data plane) and what lives in the new `src/consensus.zig` (control plane).

Which op codes are _named_ here and which are named in the consensus document is open (**U1**). The proposal is: this
document fixes the op-code numbering scheme and reserves ranges; the consensus document defines the individual consensus
ops and their payload codecs, and the snapshot/catch-up transfers stay in this document only as a named family ("give me
the data for host h from state s"), with the payload defined later.

Terminology is taken from the code, not invented:

| document term        | code fact                                                                                                            |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `index_count`        | `cfg.indexes`, the number of index threads **per host**; each index owns one inbox and one ring                      |
| `replication_factor` | `cfg.wal.hosts()`, `1..=256`, bounded by the `host_idx: u8` of the WAL API (`src/config.zig:174-179`)                |
| `host_idx`           | `cfg.host_index`, validated `< hosts`; the only host identity the process has                                        |
| index of the thread  | `role.index.inbox_idx`, identical to `frame.index_idx` (`src/index.zig:50-51`, `src/index.zig:139`), `0..indexes-1`  |
| `state` (u128)       | `state.IndexState.state` (`src/state.zig:155-163`), layout `(host_id: u8, index_id: u16, epoch_id: u40, index: u64)` |

The last row matters for the wire format: the `u128` in a vector-clock frame is not an opaque counter, it is the packed
state value the WAL/state design already defines, and `start_state_idx` in the commit envelope is the same type. The
consensus driver is the only writer of that field (`src/state.zig:162`), so the transport treats it as data.

The source states the topology rule as fact and this letter keeps it: `host_idx_0` dials `host_idx_1` iff
`host_idx_0 < host_idx_1`, and the higher host answers on the same socket. One socket therefore serves both directions
of one index-to-index pair, there is no separate reply socket, and an index has exactly `replication_factor - 1` links,
which sums to `index_count * (replication_factor - 1)` sockets per process.

## 2. What the code gives us today

Everything below exists and is reused; nothing here is proposed.

- **One client listener per process.** `lifetime.createServerSocket` binds `cfg.bind:cfg.port`, calls `listen`, and the
  descriptor travels to every front inside `START_WORK` (`src/lifetime.zig:1188-1219`, `src/front.zig:101-115`). Fronts
  arm one `accept` multishot per ring and re-arm when the multishot ends.
- **One producer per index inbox.** `routeAccepted` round-robins accepted client sockets into the child indexes' SPSC
  inboxes; the inbox protocol is explicitly single-producer, and the producer is the owning front
  (`src/front.zig:251-266`, `src/index_inbox.zig:1-30`).
- **Index identity is global and stable.** `role.index.inbox_idx` is the index number on every host; the WAL battery is
  indexed by `(host_idx, index_idx)` (`src/lifetime.zig:138-149`), and an index thread already holds one
  `state.IndexState` per host in the replication group, indexed by `host_idx`, with its own slot at `cfg.host_index`
  (`src/index.zig:92-146`).
- **Per-ring tracked operations.** `TaskCtx` (`src/slots.zig:42-91`) already has `accept`, `recv`, `close`, `timeout`,
  `file_read` and `wal_flush`; a link's connect, handshake, send and receive completions fit the same three-step shape.
- **Cross-thread payload slots.** `CrossTaskSlots` carries plain values up to 16 bytes to another thread's ring
  (`src/cross_task.zig:1-20`, `src/cross_task_slots.zig:142`).
- **The ring API has the primitives.** `pushConnectIp4`, `pushSend`, `pushRecv`, `pushClose`, `createTCPClientSocket`
  all exist in the vendored zigring.

What is missing, and is the subject of this thread:

- no peer listener, and no config surface for peer addresses (**U2**, **U3**);
- no handshake, so no way to tell a peer connection from a client connection or to bind it to `(host_idx, index_idx)`
  (**U3**, **U8**);
- no way to deliver an accepted peer socket to an index that is not a front's own child (**U4**);
- no frame layout, no length delimitation, no reorder window, no op codes (**U5**, **U6**, **U7**, **U13**);
- no per-link state on the index side: no fd table, no staging buffers, no link FSM (**U14**, **U15**);
- `src/consensus.zig` does not exist.

## 3. Topology, in terms of thread ownership

For index thread `i` on host `h`:

- it **dials** every host `j` with `j > h`, as the source says, and owns the resulting outbound socket. Dialing is done
  by the index thread itself on its own ring, never by a front;
- it **accepts** nothing directly: connections from every host `j < h` arrive at the process listener, are read by a
  front, and are handed to index thread `i` — so the accepting front must end up pushing into the inbox of the index it
  does not necessarily own (**U4**);
- it talks to `host_idx == cfg.host_index` never: there is no self-link, and with `hosts == 1` the whole transport is
  dark (no listener socket is even created, or the listener exists but no link is ever installed — **U2** decides
  whether the disabled state also removes the socket).

The socket count formula is correct as written and needs no change. What it does **not** say is that a link is
per-`(index thread, peer host)` and never multiplexed across indexes: an "index 3 on host 0 to index 3 on host 1" socket
carries only that pair's traffic, so the frame format needs no index field and the receiver needs no demux on the link.
This is stated as fact in the promoted document.

Duplicated links are possible in exactly one situation: the higher host has an existing link and the lower host dials
again (after a restart or a reconnect). The source's rule — replace and close the old one — is kept, but the ordering
and the fate of the old link's buffered frames are open (**U9**).

## 4. Link establishment and handing a socket to an index

The source sequence is: the connecting side presents itself with its host index, its thread index and its version; a
duplicate registration is replaced, and the pre-existing socket is closed with `pushClose` on the index's ring; fronts
process inbound connections and forward the established socket to the index thread, while outbound connections are made
by the indexes themselves.

This maps onto the code as follows (all proposals, hence the U tags):

1. A peer dials the process listener. A front accepts it and must read the handshake before it can know where the socket
   belongs (**U3**, **U5** for the handshake's own framing, **U8** for its contents and validation).
2. The front resolves `index_idx` to the owning index thread and hands the descriptor over. When that index is not one
   of the front's children, the descriptor travels to the owning front through a `CrossTask.PeerLink` slot, and that
   front performs the inbox push (**U4**). The inbox gains one `FrontMessage` variant, so the index still has exactly
   one producer.
3. The index thread registers the link in its per-host link table. If a link for the same peer host already exists, the
   new one wins and the old one is retired with `pushClose` on the index's ring — `TaskCtx` gains a dedicated peer
   variant rather than reusing the fire-and-forget `close`, so the completion can update the link table (**U15**).
4. Both sides perform the same handshake; the dialer additionally checks that the presented identity is the one it
   dialed, and both check the version (**U8**).
5. The index arms the first `pushRecv` on the link — the front stops touching the socket after the handover; the
   handshake payload it read is passed along so no byte is lost (**U3**, **U5**).

The dialing side's failure policy is open (**U10**): a refused or timed-out dial must not block the index service loop,
so the retry has to be a timer plus a slot-borne continuation rather than a blocking connect.

## 5. Transport framing, and the three defects in the source layout

The source packet is:

| `seq_id: u16` | `vector_clock_frame: (u8, u128)` | `op_code: u8` | `op_payload: bytes` | `commit_envelope` |
| ------------- | -------------------------------- | ------------- | ------------------- | ----------------- |

The intent is clear and stays. Three defects have to be fixed before this can be implemented:

1. **There is no length.** A TCP link is a byte stream; `op_payload: bytes` followed by `commit_envelope` cannot be
   parsed without knowing where the payload ends. The envelope's own length is self-describing only after its first
   `uvarint`, which sits after the payload. A length prefix is mandatory (**U5**).
2. **The envelope is written two different ways.** The table says `(u128, uvarint, bytes)`; the prose says
   `(no_of_decisions: uvarint, start_state_idx: u128, decisions: bitmap)`. The prose order is the one the rationale
   describes ("the number of outcomes is deliberately first so an empty envelope is a single zero"), so the table is
   stale. The bit numbering inside `decisions`, and whether `0` really means "the envelope ends here", must be stated
   exactly (**U6**).
3. **`seq_id` has no stated space or window.** Is the counter per direction of one link or per link? Is it reset when a
   duplicate link replaces the old one? What closes a hole that will never be filled? The proposal is: per direction,
   per connection, consumed only when the SQE is submitted successfully, window smaller than 65536 so modular comparison
   is unambiguous, and a hole or an out-of-window frame is a link failure that forces a redial (**U7**).

Two semantics questions are independent of the layout and are open because the transport cannot be tested without them:
what exactly a vector-clock entry claims (**U11**) and what exactly the commit envelope acknowledges (**U12**). The
encoding beneath all of it — endianness, packed or padded, varint flavour, checksums, where the version lives — is
**U13**.

## 6. Implementation surface

Data plane stays in `lifetime.Controller`, as the source says: the per-index link tables (descriptors, peer host,
phase), the staging buffers for outbound frames and the receive buffers for inbound frames, their lifetime tied to
`Controller.init`/`deinit` and sized from `cfg.wal.hosts()` and the new config knobs.

Control plane lives in the new `src/consensus.zig`: the handshake codec, the frame codec, the reorder window, the link
FSM, the vector-clock rotation and the commit-envelope bookkeeping. Whether the codec may live in a separate
`src/transport.zig` while `consensus.zig` owns only the link FSM is open (**U15**), because the source names only
`consensus.zig`.

The concrete touch list, pending the answers:

- `src/config.zig`: peer addresses and the peer port, validation, docs and fixtures (**U2**).
- `src/lifetime.zig`: link tables and buffers in `Controller`; `createServerSocket` possibly split into a client and a
  peer listener.
- `src/front.zig`: peer accept arm, handshake read, routing to the owning index or the owning front.
- `src/index.zig`: `FrontMessage.peer_link`, link registration in the frame, first receive, teardown on drain.
- `src/slots.zig`: `TaskCtx` variants for connect, handshake, send, receive, close.
- `src/cross_task.zig`: the `PeerLink` slot payload; `CrossTask` stays within its 16-byte proof.
- `src/consensus.zig`: new file, control plane.
- tests: two index threads in one process on `127.0.0.1` with distinct ports must be able to establish a link, exchange
  a frame with a forced out-of-order `seq_id`, and replace a duplicate link.

## 7. Out of scope

- The consensus algorithm: quorum, terms/epochs, leader election, decision rules.
- Payload codecs for consensus ops, snapshot chunking and the contents of a catch-up transfer.
- The WAL and state-machine semantics that the ops mutate.
- The client-facing protocol and the front's client path, which is untouched.
- Fencing and epoch advancement, except where the transport must carry the state value.

## Open questions

- **U1.** This document is the prelude to the consensus documentation. Proposed: it fixes framing, the link lifecycle
  and the op-code numbering scheme with reserved ranges, while individual consensus ops and their payloads are defined
  in the consensus document; snapshot/catch-up transfers appear here only as a named family. Proposed also: the promoted
  document is rewritten in English in place, replacing the Russian text of `docs/CONSENSUS-TOPOLOGY-AND-TRANSPORT.md`.
  Confirm or override both.
- **U2.** `cfg` today has one endpoint, `bind` + `port`, used for clients, and `wal.hosts` + `host_index` but no peer
  addresses at all. Proposed: a new block `cluster = { peer_port = 7001 peers = { "10.0.0.1" "" "10.0.0.3" } }`,
  `peers[host_idx]` being the address of that host and the own slot empty, `len(peers) == wal.hosts()`; the peer
  listener binds `bind:peer_port`. Validation: `peer_port != port`, block absent when `hosts == 1`. Is this the shape,
  or do you prefer full `host:port` entries per host, or a DNS convention?
- **U3.** A front accepts a connection and cannot route it until it reads the handshake, but the client path currently
  reads nothing and hands the socket straight to an index. Proposed: a separate peer listener (separate port) so the
  client path is untouched, and the front reads the handshake on the peer path only. Alternative rejected: one port with
  a first-byte discriminator, because it forces the front into the client protocol. Confirm the separate listener.
- **U4.** An index inbox is SPSC and its only producer is the owning front, but a peer may dial the process listener on
  any front's ring. Proposed: the accepting front reads the handshake, computes the owning front as
  `index_idx / (cfg.indexes / cfg.fronts)`, and either pushes `FrontMessage.peer_link` into its own child's inbox or
  forwards a `CrossTask.PeerLink { fd, host_idx, index_idx, version }` slot to the owning front's ring, which then
  pushes the same inbox message. Confirm; the alternatives are per-front peer ports or abandoning the single-producer
  rule.
- **U5.** The frame has no length field, so `op_payload` cannot be delimited on a stream. Proposed layout, little endian
  and packed: `seq_id: u16`, `vc_host: u8`, `vc_state: u128`, `op_code: u8`, `payload_len: u32`, then the payload, then
  the envelope. Proposed cap on `payload_len` (4 MiB) with larger transfers chunked; a frame above the cap is a protocol
  error. Confirm the field order and the cap.
- **U6.** The envelope is written as `(u128, uvarint, bytes)` in the table and
  `(no_of_decisions: uvarint, start_state_idx: u128, decisions: bitmap)` in the prose. Proposed: the prose wins;
  `no_of_decisions == 0` makes the envelope exactly one zero byte with nothing after it; otherwise `start_state_idx`
  follows as `u128` LE and the bitmap is `ceil(n/8)` bytes, bit `i` (LSB-first inside a byte) being the decision for
  `start_state_idx + i`, `1` confirmed. Confirm, including the direction of the bits.
- **U7.** `seq_id` is a `u16` reorder cursor, but the source does not say whether it is per direction or per link, what
  happens at wrap, or when a hole is abandoned. Proposed: one counter per direction of one connection, reset to zero
  when a connection replaces another; a sequence number is consumed only when its SQE is successfully submitted, so a
  normal sender never leaves a hole; the receive window is 1024 frames, modular comparison on `u16`; a hole that cannot
  be filled and an out-of-window frame both declare the link failed. Confirm the window size and the failure rule.
- **U8.** The handshake is "host index, thread index, version". Proposed frame:
  `(version: u16, host_idx: u8, index_idx: u16)` sent by **both** sides; the accepting side sends first immediately
  after accept, the dialer sends immediately after `connect`; each side validates version equality and the dialer
  validates that the peer's identity is the one it dialed, and that both indices are in range. A mismatch closes the
  link: fatal at startup for the acceptor? What is logged, and does the dialer keep retrying forever or give up after N
  attempts? Confirm.
- **U9.** Duplicate links are replaced and the old socket is closed with `pushClose` on the index's ring. Proposed: the
  new link is installed before the old is retired (no window with no link), the old link's receive window and any
  partially received frame are discarded, pending catch-up requests are re-issued on the new link, and the replacement
  is logged at warn. Confirm, especially the discard (nothing is replayed frame by frame, recovery is the consensus
  catch-up's job).
- **U10.** Dialing must not block the index loop. Proposed: the dial is a `pushConnectIp4` with a tracked slot; failure
  (refused, timeout, negative completion) schedules a retry with exponential backoff from 100 ms to 5 s, reset on
  success; the first dial is issued once the index has finished recovery and before the service loop; failures are
  logged at warn, never fatal. Confirm, and say whether the backoff bounds are config knobs or constants.
- **U11.** A vector-clock frame is `(host_idx: u8, state: u128)`, one entry per packet, rotating over all hosts. What
  exactly does the entry claim: the sender's **applied** state for that host in this index's replication group, or the
  durable/committed one? Proposed: applied, because it is what the sender can serve a catch-up request from; the
  sender's own host index is included in the rotation; rotation order is `0..replication_factor-1` and restarts at zero
  after a link replacement. Confirm.
- **U12.** The commit envelope reports "status of confirmations". Proposed: it is the **receiver's** acknowledgement of
  the peer's proposals in this index group, cumulative from `start_state_idx`, bit `1` meaning confirmed; it is not a
  gossip of third-party decisions, which is what the vector clock is for. Because decisions are ordered, a contiguous
  run plus holes is both necessary and sufficient. Confirm the direction and that the positions are
  `state.IndexState.state` values, not frame sequence numbers.
- **U13.** Proposed encoding: all fixed-width fields little endian and packed (no alignment padding), `uvarint` is
  LEB128 without a length limit beyond the field it encodes, no checksum (TCP covers integrity), the protocol version
  lives only in the handshake and never in a frame, `op_code` numbering reserves `0x00..0x1F` for transport/catch-up and
  `0x20..0x7F` for consensus ops, `0x80..0xFF` stays unused, and an unknown or out-of-range `op_code` closes the link
  rather than being skipped, because a frame we cannot interpret means the peer speaks another version. Confirm.
- **U14.** The source says sends are fired asynchronously with no coupling to the operations. That needs owned memory
  per frame until the send completes, and a bound. Proposed: a per-link outbound queue of fixed-size staging buffers
  from a process-wide pool sized in config; when the pool or the ring's slots are exhausted the link is declared failed
  and torn down rather than dropping frames or stalling the index loop; inbound frames are decoded into a per-link
  reorder window and dispatched to the consensus control plane one at a time. Confirm the pool size knob and the
  overflow policy.
- **U15.** The source puts the control plane in `src/consensus.zig` and the data plane in `lifetime.Controller`. Is a
  separate `src/transport.zig` allowed for the codec and the reorder window, with `consensus.zig` owning only the link
  FSM and the semantics? Confirmed additions: `TaskCtx` variants for connect/handshake/send/recv/peer close,
  `FrontMessage.peer_link`, `CrossTask.PeerLink`, per-index link tables in `Controller`, and the note that
  `CrossTaskSlots` needs no type change beyond the new variant (it stays inside the 16-byte proof). Confirm or narrow.
- **U16.** Teardown is unspecified. Proposed: `shutdown_soft` keeps the links alive until the index drains, then closes
  every one of them with `pushClose` before `reportDrained`; `shutdown_hard` closes them immediately; an inbound peer
  connection arriving at an index that is already draining is closed at once, the same shape as the client refusal in
  `src/index.zig:176-186`; no goodbye op exists in v1, so the peer sees EOF and the lower host redials if it is still
  running. Confirm, and say whether a goodbye/fence op is wanted in the prelude after all.
