This thread surveys where `zunit.Volume` earns its keep in the mpy6a configuration and command line. It is a proposal,
not an implementation plan: no code is changed here. `zunit` is already wired into the build (`build.zig`,
`build.zig.zon`), and the first conversions are in the tree, so the useful work left is choosing which remaining values
are genuinely volumes, which base each one needs, and which byte-shaped knobs should exist at all.

## 1. What is already volume-typed

`src/config.zig:32` defines one shared config wrapper:

```zig
pub const Bytes = zunit.Volume(.b).Siggy;
```

and `src/config.zig:38` provides the comptime-friendly constructor used by defaults and tests:

```zig
pub inline fn bytes(n: u128) Bytes {
    return Bytes.fromBase(n) catch unreachable;
}
```

The following fields already use it:

| field                    | type    | default                    | validation                                                         | notes                                                         |
| ------------------------ | ------- | -------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------- |
| `wal.plain.lba`          | `Bytes` | `bytes(4096)`              | `[512, 1 MiB]`, power of two, divides 1 MiB (`src/config.zig:608`) | buffer size and flush granularity (`src/config.zig:131`)      |
| `wal.pmem.lba`           | `Bytes` | `bytes(4096)`              | same                                                               | same (`src/config.zig:139`)                                   |
| `snapshots.size_barrier` | `Bytes` | `bytes(256 * 1024 * 1024)` | `>= 1` byte (`src/config.zig:633`)                                 | pair-size bar for starting a procedure (`src/config.zig:107`) |

`Wal.lba()` is the narrowing pattern the rest should copy: `value64()` first, then `std.math.cast(u32, ...)`, returning
zero on overflow so validation rejects it (`src/config.zig:168-176`). It is already the model for any new volume field
whose consumer wants a `u32`.

The duration side is also already converted: `init_timeout`, `shutdown_timeout` and `snapshots.interval` are
`Seconds = zunit.Duration(.secs).Siggy` (`src/config.zig:35`, `:78-79`, `:106`). This thread does not reopen durations.

The only configuration leaf that is plainly a byte count and is still an untyped integer is `logging.pool_frame_size`.

## 2. Candidate: `logging.pool_frame_size`

**Current shape.** `pool_frame_size: u32` is declared at `src/config.zig:195`, defaulted to `2048` at
`src/config.zig:75`, and passed unchecked into `blog.BufferPool.init` at `src/lifetime.zig:459`:

```zig
try logger.pool.init(self.allocator, self.cfg.logging.pool_capacity, self.cfg.logging.pool_frame_size);
```

The blog contract is visible in `zig-pkg/blog-0.0.18-.../src/buffer_pool.zig:36-40`: the frame size must be a power of
two and at least 512 bytes, and the frame count must be a non-zero power of two. Those checks currently run at logger
construction, not at config parse time, so a bad document loads and then fails during startup.

**Proposed shape.** Make the field a volume, default it with the helper, and narrow at the consumer:

```zig
pub const Logging = struct {
    method: union(enum) {
        pretty: enum { light, dark, flat },
        json: void,
        file: []const u8,
    },
    pool_capacity: u32,
    pool_frame_size: Bytes = bytes(2048),

    pub fn frameSize(self: Logging) u32 {
        const widened = self.pool_frame_size.value64() catch return 0;
        return std.math.cast(u32, widened) orelse 0;
    }
};
```

`2KiB`, `2048` and `2.0KiB` would all decode; the canonical rendering under the shared `.b` base is `2048`, the same
shape `wal.lba` already has. The blast radius is the fixtures in `src/main.zig:402` and `src/lifetime.zig:2008`,
`:2097`, `:2141`, `:2181`, `:2703`, `:2925`, which write a bare `1024` and would become `config.bytes(1024)`.

**U1 (blocking).** Adopt `Bytes` for `logging.pool_frame_size`, with `frameSize()` narrowing for the blog call? The
alternative is to leave it a `u32`; that keeps the type and all fixtures untouched but leaves the one remaining
user-facing byte quantity without unit literals.

**U2.** If U1 is accepted, should config validate the blog contract at parse time? Proposed: add a `validateLogging`
step and two new `ParseError` variants, `InvalidPoolCapacity` and `InvalidPoolFrameSize`, so `fromText` rejects a frame
size that is not a power of two in `[512, 1 MiB?]` and a capacity that is not a non-zero power of two. The alternative
is to keep the current behavior, where `BufferPool.init` reports `error.InvalidConfig` after the process has already
begun startup. The upper frame bound is not in blog today; confirm whether config should invent one.

## 3. Base audit for the fields already converted

`zunit`'s base is both the working unit and the precision constraint, so the choice is not cosmetic. For the fields that
already carry `Bytes`, the question is whether `.b` remains correct or whether a coarser base would make the canonical
document nicer at the cost of rejecting values that are legal today.

### 3.1 `wal.lba`

`.b` is the only base that accepts `512`, and 512 is a legitimate hardware LBA and is exercised by the WAL tests
(`src/wal.zig:2132`, `:2194`, `:2308-2309`). `4KiB` is accepted as input and decodes to the same 4096; only the
canonical spelling in the rendered default is `4096` rather than `4KiB`. Moving to `.kib` would reject `lba = 512`,
require raising the validation floor to 1 KiB (`src/config.zig:608`), and invalidate every 512-byte fixture. The display
benefit does not justify that.

**U3 (blocking).** Keep `Volume(.b)` for `wal.lba`, and therefore keep `Bytes` as the shared alias for it. Proposed:
yes. Override only if a 512-byte LBA is deliberately no longer supported; then the base, the floor, the 1 MiB-divisor
rule (`wal_block`, `src/config.zig:601`) and the tests all move together.

### 3.2 `snapshots.size_barrier`

The field is a pair-size bar, so `.mib` would render the default as `256MiB` and read naturally; `.kib` would render it
as `262144KiB`. Both raise the effective floor above the current one byte. `.b` preserves `4KiB` in the tuned test
(`src/config.zig:921`) and the one-byte barriers used to force a procedure in the index tests (`src/index.zig:1429`,
`:1491`, `:1549`, `:1883`, `:2005`, `:2437`, `:3089`, `:3778`), at the cost of the raw `268435456` canonical default
that the current rendering test asserts (`src/config.zig:974`).

**U4.** Choose the base for `snapshots.size_barrier`. Proposed: keep `.b` for now, because it preserves every accepted
value and keeps the test fixtures cheap; accept `.kib` (and a 1 KiB validation floor) or `.mib` (and a 1 MiB floor, with
the one-byte index fixtures rewritten) only if the prettier canonical default is worth the fixture churn. If the base
changes, the shared `Bytes` alias no longer fits this field and a `Kib`/`Mib` alias plus constructor is needed (`U4a` in
the same decision).

## 4. Derived byte budgets: counts that hide a volume

Two config keys are frame/buffer counts whose product with a frame/LBA size is the real resource budget. A volume type
on the count itself would be wrong, but replacing the count with a byte budget is a legitimate volume-unit candidate.

### 4.1 Logging pool

`logging.pool_capacity` is a count of frames (default 1024) and `logging.pool_frame_size` is bytes per frame (default
2048), so the default log pool is 2 MiB per logger. The user thinks in memory, not in frames.

**Proposed shape.** Replace `pool_capacity` with a volume budget:

```zig
pub const Logging = struct {
    // ...
    pool_bytes: Bytes = bytes(2 * 1024 * 1024),
    pool_frame_size: Bytes = bytes(2048),

    pub fn poolCapacity(self: Logging) u32 {
        const bytes = self.pool_bytes.value();
        const frame = self.frameSize();
        if (frame == 0 or bytes % frame != 0) return 0;
        const count = bytes / frame;
        if (count == 0 or count > std.math.maxInt(u32)) return 0;
        return @intCast(count);
    }
};
```

Validation would require exact divisibility and a non-zero power-of-two frame count, the blog contract. The default
document would say `pool_bytes = 2097152` under `.b` or `pool_bytes = 2MiB` under `.mib`; the latter is the natural
spelling but rejects sub-MiB pools. Deprecating `pool_capacity` is a config-format break; keeping both creates two
sources of truth.

**U5 (blocking).** Replace `logging.pool_capacity` with `logging.pool_bytes`, derive the frame count, and make the
budget the only memory knob? Or keep the count and accept that the logging pool is the one resource sized in frames? If
replacing, confirm the new key's base and what happens to old documents that still say `pool_capacity`.

### 4.2 WAL battery

`wal.buffers` is a ring depth (default 32) and `wal.plain.lba`/`wal.pmem.lba` is the buffer size, so the per-pair data
area is `buffers * lba` bytes (128 KiB by default). Unlike the logging pool, `buffers` is not merely a resource budget:
the four-buffer floor is a correctness rule for the snapshot bring-tail (`designs/SNAPSHOTS.md` §6), and the WAL writer
indexes its ring by ordinal modulo `buffers` (`src/wal.zig:323-324`, `:704-710`). Hiding the ring depth behind a byte
budget would make that contract harder to see.

**Proposal.** Do not add a `wal.battery_bytes` config key. If an operator needs the total, expose a read-only
`batteryBytes()` accessor or log the computed value; keep `buffers` as the source of truth.

**U6.** Confirm that the WAL battery stays a ring depth and gets no volume budget in this thread. If a total-size knob
is wanted, it needs a separate decision: divisibility by `lba`, the `>= 4` floor, precedence against `buffers`, and
whether the old key is deprecated or rejected.

## 5. CLI candidates

The running CLI is deliberately small: `run` has only `-c/--config` (`src/main.zig:22-32`), and the other commands are
`show-dev-config` and `version` (`src/main.zig:34-45`). There is no numeric flag in the tree today, so there is no
existing CLI value to retype as a volume.

The deferred toolchain design does name one:

```text
mpy6a pmem-migrate lba --old-lba 4Kib
```

(`docs/todo.md:3-15`, restated in English: the `pmem-migrate lba` subcommand works on the updated config and requires
the old LBA value to rebuild the NVDIMM buffers when the device LBA changes.) `4Kib` is accepted by `zunit`; the suffix
table in `.contexts/ZUNIT-SDK.md` allows `KiB`, `Kib`, `Ki`, `kib` and `ki`.

**Proposed shape.** When the command lands, type the flag as `zunit.Volume(.b).Dap` and make it required:

```zig
const Lba = zunit.Volume(.b).Dap;

.old_lba = dap.Flag(Lba){
    .help = "Previous device LBA, e.g. 512 or 4KiB.",
},
```

`.b` is required for the same reason as `wal.lba`: an old LBA can be 512, and `--old-lba 512` must decode. The new LBA
is the one already in the updated config, so `--new-lba` is not proposed unless the tool needs a preview override. This
is a type decision for a command that is not in `cliDecl` yet; it does not implement `pmem-migrate`.

**U7 (blocking).** Confirm that `--old-lba` is `Volume(.b).Dap`, required, and that there is no `--new-lba` (the value
comes from the updated config). If the command should accept a dry-run new value, say so and state its default and its
relation to `wal.lba`.

**U8.** Confirm that no config-override flags are added to `run` in this thread. Proposed: none, so the CLI does not
grow `--wal-lba`, `--log-frame-size` or `--size-barrier` merely to exercise unit literals. If such overrides are wanted
later, each flag should use the same base as its config field and the same validation.

## 6. Explicit non-candidates

These were checked and deliberately left alone:

- **Counts, not volumes.** `fronts`, `indexes`, `elephants`, `host_index`, `queue_depth`, `cross_task_slots`,
  `accept_backlog`, `sqpoll_threads`, `index_inbox_capacity`, `ring_slots_capacity`, `wal.buffers`, `wal.hosts`,
  `snapshots.slots`, `registry_keep`. A unit suffix would add no meaning; their constraints are powers of two, slot
  bounds or thread counts, not byte arithmetic. `logging.pool_capacity` is the one count whose product with a byte value
  is a real budget, and §4.1 makes it a U rather than a silent conversion.
- **Internal constants.** `wal_block = 1 << 20` (`src/config.zig:601`) and `wal.BLOCK = 1 << 20` (`src/wal.zig:27`) are
  the fixed 1 MiB WAL block; `CRC_LEN`, `HEADER` and `BLOCK_CONTENT` are structural. `max_config_bytes = 32768`
  (`src/config.zig:540`) is the manager's read cap, not a config leaf. None is user-facing, so none gets a volume type
  now. If one is ever exposed, `wal_block` is naturally `Volume(.mib)` and `max_config_bytes` is `Volume(.b)`.
- **Durations.** Already converted; no volume work follows from them.
- **CLI arguments that are paths, names or counts.** The `run` config path, the command names, and the deferred
  `pmem-migrate cpu --old-index-count` / `replication --old-factor` values (`docs/todo.md:23-29`) are not volumes.
