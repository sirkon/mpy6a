### 2.1 The derived logging pool

`Logging` keeps two volume leaves, but only one of them is a budget. The count is computed:

```zig
pub const Logging = struct {
    method: union(enum) {
        pretty: enum { light, dark, flat },
        json: void,
        file: []const u8,
    },
    pool_bytes: Bytes = bytes(2097152),
    pool_frame_size: Bytes = bytes(2048),

    pub fn frameSize(self: Logging) u32 {
        const widened = self.pool_frame_size.value64() catch return 0;
        return std.math.cast(u32, widened) orelse 0;
    }

    pub fn poolCapacity(self: Logging) u32 {
        const budget = self.pool_bytes.value64() catch return 0;
        const frame = self.frameSize();
        if (frame == 0 or budget % frame != 0) return 0;
        const count = budget / frame;
        if (count == 0 or count > std.math.maxInt(u32)) return 0;
        return @intCast(count);
    }
};
```

The consumer at `src/lifetime.zig:459` becomes:

```zig
try logger.pool.init(
    self.allocator,
    self.cfg.logging.poolCapacity(),
    self.cfg.logging.frameSize(),
);
```

A non-divisible budget, a zero frame size or an overflow collapses to zero. `BufferPool.init` then rejects the zero, so
the failure stays where U2 left it. The derivation is deliberately not a validator: it never answers whether a count is
a power of two.

### 2.2 Default document after the accepted changes

## 4. Derived budgets and CLI

- **Logging pool, accepted as a budget.** `pool_bytes` is the only memory knob; `poolCapacity()` is a derivation, not a
  second source of truth. `BufferPool.init` keeps the blog contract.
- **WAL battery, rejected as a budget.** `wal.buffers` stays the source of truth because the four-buffer floor is a
  correctness rule for the snapshot bring-tail and the writer indexes its ring by ordinal modulo `buffers`
  (`src/wal.zig:323-324`, `:704-710`). No `wal.battery_bytes` key and no accessor.
- **`pmem-migrate lba`, accepted in type only.** The command is absent from `cliDecl`; when it lands, `--old-lba` is
  required and `.b`-based so a legacy 512 is readable. No `--new-lba`; the new value is the updated config's `wal.lba`.
- **`run`, no new flags.** No `--wal-lba`, `--log-frame-size` or `--size-barrier`.

## 5. Explicitly out of scope

- Implementing `pmem-migrate` or any other deferred toolchain command (`docs/todo.md`).
- Reopening durations, `wal.buffers`, the thread/slot counts, or the internal constants `wal_block`, `wal.BLOCK`,
  `CRC_LEN`, `HEADER`, `BLOCK_CONTENT` and `max_config_bytes`.
- Adding config-override flags to `run`.
- Changing the registry, admission or flush rules behind `wal.buffers` and `wal.lba`.

## Open questions

- **U9.** With `wal.lba` on `.kib` and `size_barrier` on `.mib`, should `src/config.zig` expose three aliases and three
  constructors, `Bytes`/`bytes` for `.b`, `Kib`/`kib` for `.kib` and `Mib`/`mib` for `.mib`? Proposed: yes, keeping
  `Bytes` as the `.b` name so the logging fields and their `config.bytes(...)` fixtures keep their spelling.
  Alternatives: use `B`, `KiB`, `MiB`; or declare the new fields with `zunit.Volume(...).Siggy` directly and add no
  aliases. Which names should the design use?
- **U10.** Iteration 1 tied `.mib` to a 1 MiB validation floor and to rewriting the one-byte index barriers. Confirm the
  floor rises to 1 MiB, and choose the fixture strategy: (a) raise the eight index fixtures to `mib(1)` and make only
  the tests that need a dispatch write more than 1 MiB, for example about 1100 records of 1 KiB, which keeps every
  record within two ring buffers; or (b) keep `>= 1` as an internal validator rule and give the tests a `.{ .raw = 1 }`
  value, which bypasses the parser floor but depends on zunit's public `raw` field. Proposal: (a) for the dispatch
  tests; the skip-guard tests never cross the bar, so `mib(1)` is enough there.
- **U11.** Removing `pool_capacity` makes every document that still says `pool_capacity = ...` fail, because siggy
  rejects unknown fields with `error.UnknownField`. Should this be a clean break, with `mpy6a.cfg:9` updated and the
  parse failure accepted, or should `Logging` keep an optional deprecated `pool_capacity` next to `pool_bytes` for one
  release? If kept, state the precedence when both are present and whether a conflict is an error. Proposal: clean
  break, because the tree is pre-1.0 and already renamed `interval_s` to `interval`; no second source of truth.
- **U12.** What is the default `logging.pool_bytes`, and how does it relate to `pool_frame_size`? The old defaults were
  1024 frames of 2048 bytes, a 2 MiB budget. The pad's note that 512 bytes is a reasonable logging volume supports three
  readings: (a) keep the 2 MiB budget and the 2048-byte frame, capacity 1024, behavior-preserving; (b) keep the 2 MiB
  budget but lower the frame to 512 bytes, capacity 4096; (c) make the whole pool 512 bytes with a 512-byte frame,
  capacity 1. A 512-byte budget with a 2048-byte frame is not derivable and would fail at `BufferPool.init`, so it is
  not a fourth option. Which default should the design and the default document carry?
