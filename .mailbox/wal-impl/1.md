## 1. The source design, restated in English

### 1.1 One file per index

One index — including a mirror index — has its own WAL file. An index is the triple
`(host_idx, index_idx, self_index_state)`. The file holds the data of exactly that data set: there is no place in it for
the state of other hosts' data sets; juggling several data sets is the index's business as an execution flow, and each
data set gets its own file and its own battery. **U9** anchors what "the data of the data set" means precisely.

```zig
// This is the lifetime.Controller from ./src/lifetime.zig
pub fn walOpenWrite(self: *Self, host_idx: u8, index_idx: u16, state: u128) !*WalWriteFile;
pub fn walOpenRead(self: *Self, host_idx: u8, index_idx: u16, state: u128) !*WalReadFile;
pub fn delete(self: *Self, host_idx: u8, index_idx: u16, state: u128) !void;
```

`walOpenWrite` hands out a writer positioned for writing starting from the given state: a wrapper over the existing
file, or, if the file does not exist, the same wrapper over a freshly created one. The write side is where consistency
is kept; the read side is necessarily asynchronous (a synchronous interface is tolerable only for startup replay and is
useless for a request from another host: "give me the records starting from state X").

### 1.2 The buffered writer, with optional NVDIMM

Per-record `O_DIRECT` flushes are rejected outright (feeding SSD makers is a bad idea), so both operating modes buffer.
The difference is only where the buffers live and what a "publish" means:

- **Plain mode.** The battery is ordinary allocated memory; a crash loses the un-flushed tail; durability of a record
  begins when its buffer's flush completes.
- **PMEM mode.** The battery is a computed region of an mmap'd NVDIMM; every publish is a `CLWB` → `SFENCE` pair, so the
  un-flushed tail survives a power cut; the file flush exists to recycle ring slots, not to establish durability.

The memory decomposition is analogous in both modes: an array of buffers laid out sequentially, and an array of 64-byte
buffer headers.

```zig
buffers: []u8,          // length index_count * buffers_count * buffer_size
headers: []BufferHeader, // length index_count * buffers_count
```

In PMEM mode no allocator is used: a region of the mmap'd NVDIMM stick is given to the index threads and divided by the
number of indexes `(host_idx, index_idx)`; inside one index area the buffers and the headers are placed. The buffer
count, the host count (equal to the replication factor), and the LBA size are config values; changing any of them
requires a migration (the toolchain commands of `docs/todo.md`).

The buffer size is the device LBA: each buffer of a pair has length `|LBA|`, and a flushed file has length `|LBA| × N`
for N flushed buffers. One flush is one whole buffer at an LBA-multiple offset, so `O_DIRECT` alignment holds by
construction.

### 1.3 The write sequence (the order is critically important)

1. Check that the space — the volume of free buffers plus the remainder of the current one — suffices for the new
   portion of data. If not, refuse immediately. A write that would exactly fill the last buffer and leave no room after
   it is **also refused**; the doc calls this point fundamental.
2. Write all the data into the buffer.
3. If the current buffer lacks room, grab a new one and write into it. In PMEM mode every write is accompanied by `CLWB`
   → `SFENCE`.
4. If buffers became exactly filled as a result, grab the next one, set its length to 0, and clear its filled flag. Also
   with `CLWB` → `SFENCE`.
5. Update the metadata of the buffer that was current at the start of the operation. If it stopped being current (new
   ones were grabbed), set its filled flag. Accompanied, of course, by `CLWB` → `SFENCE`. Here, attention: the metadata
   of the **following** buffers changes first (in order: the next buffer's meta, then the one after it, and so on), and
   only at the very end the "commit" — the metadata of the old buffer.
6. Put the filled buffers into the flush queue starting from a certain position. **Never submit several buffers at
   once**: submit one write task from position `Offset` into the SQ, wait for the reply in the CQ, then submit the next
   task (if the next buffer is marked filled). After the write, mark the flushed buffer empty.

The flush itself is mandatory `O_DIRECT`, bypassing the OS page cache.

### 1.4 The data format

A record is

| `state_idx` | `uvarint(len(op))` | `op...` |
| ----------- | ------------------ | ------- |

Data is written in 1 MiB blocks whose last 4 bytes hold a CRC32C (Castagnoli) hash of the block's content. If a new
record does not fit into the block's remainder, the current content is padded with zeros (the zeros counted in the hash)
and the new record is written into the next mebibyte. This must be accounted for in length estimation. The hash function
is the ready-made hardware CRC32C of the `blog` package, plus "the standard combinator for hashes of concatenated
blocks" (**U6** anchors what the combinator is for).

### 1.5 The read

High level, both modes: ignore the file's tail if the remainder is smaller than the buffer length. In PMEM mode blocks
are additionally recovered from memory: the file belongs to a known `(host_idx, index_idx)` pair, so the battery
location is computed, not searched. The buffers form a ring: with `buffers_count = 32` and file length `|LBA| × N`, the
buffers `buffer_idx(N + k) = (N mod 32 + k) mod 32` may hold data that was not yet flushed before, say, a power cut.
First the file is read, then — guided by the state of the headers — the rest is finished from memory.

The search for a start position is binary: blocks are 1 MiB regions with CRC32C at the end, so reading from a mebibyte
boundary is guaranteed to land at the start of some record; by the content we know where we are and can immediately
discard the case where the first record's index there is greater than the requested one.

The process state is something like:

```zig
pub const FileReadProcess = struct {
    state: enum { Seek, Read },
    buf: []u8,
    fd: std.posix.fd_t,
    // ...
};
```

and a seek task is set up as `state = .Seek`, a slot is taken, and something like

```zig
pub const TaskCtx = union(enum) {
    // ...
    FileRead: struct {
        file_process: *FileReadProcess, // the fd comes from here
        offset: u64,
        buf: []u64, // a buffer of the needed byte count
    },
};
```

is put there; arriving in the CQ it is dispatched by `state` (continue seeking, start the readout, and so on).
`FileReadProcess` must also hold a description of the task it performs: a readout from the very beginning is one thing,
a readout starting from a given state is another.

Ownership discipline (matching `src/state.zig`'s G1 rule): the battery, the wrappers, and every ring task of a pair
`(host_idx, index_idx)` are touched only by index thread `index_idx`. No atomics, no locks; `flush_in_flight` and
friends are plain fields.

`walOpen*`/`delete` open and unlink **synchronously** (`std.os.linux.open`, the `createLogFile` idiom in
`src/lifetime.zig:267`): they are cold, rare operations (per data set per epoch), and the doc's signatures are
synchronous. The ring carries only data traffic: flushes and reads.

## 3. File identity, the `Controller` seam, and the writer API

The triple names the file. **U2 (blocking).** The doc gives no on-disk name format, and the snapshot convention is the
nearest neighbor (`snapshot.<host_idx>.<index_idx>.<state>` with `<state>` the full `u128` as 32 lowercase hex digits,
`sdks/state-snapshot.md` §3.4). Proposed: `wal.<host_idx>.<index_idx>.<state>`, `<state>` = 32 lowercase hex digits,
files in a configured directory; the tag is opaque, never parsed back — confirm or override.

The `state` argument of `walOpenWrite` is (a) the file name tag and (b) the writer's monotonicity floor — "calibrated to
writing starting from the given index". **U1 (blocking).** The doc pins `write(self, buf: []u8) !isize` and the record
as `state_idx | uvarint(len(op)) | op`, but not what `buf` holds. Proposed: `buf` is the **fully framed record**
(`state_idx: u128 LE(16) || uvarint(len) || op`), minted by the caller (the consensus driver owns state minting; an
epoch bump jumps the state inside one file, so the writer cannot derive it); the writer validates
`state_idx > last_written` and `>= open state`, and returns `buf.len` on success; refusal at admission is an error (a
`error.WALFull`-style member of a small WAL error set), not a negative `isize` — confirm or override. If the caller
should instead pass the raw op and the writer frames the record, the writer must then also own state minting, which the
consensus layer owns today (`applyIndexOp`'s contract, `src/lifetime.zig:464`).

`close()` gains its missing `self: *Self`, and `delete`'s edge semantics are pinned by **U4**: proposed — `close` drains
the flush queue (waits for the in-flight flush completion on the caller's ring), releases the battery slice and the fd;
`delete` unlinks and is idempotent (a missing file is success) — confirm or override.

## 4. The battery

Per pair, two columnar arrays inside the pair's area: the data array first (`buffers_count × LBA`, LBA-aligned by
construction), then the header array (`buffers_count × 64`). Area stride: `buffers_count × (LBA + 64)` rounded up to a
multiple of `max(LBA, page)` so every pair's data array stays LBA-aligned.

**U5 (blocking).** The doc pins the header **size** (64 bytes, one cache line per slot so one `CLWB` covers a publish)
and implies two fields — a length and a filled flag — but the walk needs more. Proposed `BufferHeader`: `data_len: u32`
(valid bytes; LBA when filled), `flags: u32` (bit 0 = filled), `buffer_seq: u64` (the buffer's absolute file position ÷
LBA: the flush offset, and the stale-lap check for the walk — a slot holds stale bytes from the previous ring lap until
reused), `crc_running: u32` (the running CRC32C of the open 1 MiB block as of this buffer's end — makes reopen trivial:
no re-reading of the file or the tail), `last_state: u128` (the state_idx of the last record ending in this buffer — the
writer's monotonicity floor after restart), `reserved: u32`; 40 bytes used, padded to 64 — confirm or override.

**U8.** "index_count" in the doc's array-length formulas: proposed = the number of `(host_idx, index_idx)` pairs the
process serves = `indexes × hosts` (each index thread manages one data set per host of its replication group), pair →
area index `index_idx × hosts + host_idx` (thread-major, stable across restarts, movable only by the migration
toolchain). If the intended meaning was per-thread instead, the structure is isomorphic; the plan proceeds with the pair
reading.

**U7 (blocking).** Config shape (siggy): a new `wal` block —
`wal = plain { dir = "..." buffers = 32 hosts = 3 lba = 4Kib }` or
`wal = pmem { dir = "..." device = "/dev/pmem0" buffers = 32 hosts = 3 lba = 4Kib }`. Validated at startup: `lba` a
power of two in `[512, 1 MiB]` dividing 1 MiB exactly; `buffers >= 2`; `hosts` equal to the replication factor (today's
hardcoded `src/index.zig:18` — proposed: the config value replaces the constant); `host_index < hosts`; in PMEM mode,
the mapping must cover `pairs × area_stride` bytes. The block is optional; an absent block leaves the module unopened
(nothing in the skeleton opens WAL files today) — confirm the knob set and the names.

PMEM barriers: Zig std has no wrapper; `src/wal.zig` carries a small arch-gated inline-asm module (`clwb` + `sfence` on
x86_64, with a `clflushopt`/`clflush` fallback selected by CPUID; PMEM mode compiles only where supported), following
the arch-gating idiom of the vendored `blog` CRC32C. On restart in PMEM mode the headers are **never zeroed** — their
whole point is to survive; plain mode zeroes its DRAM headers at allocation.

## 5. The write path

State kept by `WalWriteFile`: `flushed_upto` (absolute ordinal; file length is `flushed_upto × LBA` when idle),
`flush_in_flight: ?ordinal`, the current buffer ordinal and offset, `crc_running`, `last_state`, and the ring/queue
bookkeeping. All plain fields.

`write(record)` on the owning index thread, in the doc's order:

1. **Admission.** Compute the cost: the record, plus — if it does not fit the current block's content remainder — the
   zero padding of the whole remainder plus the 4 CRC bytes (padding can span several buffers; every padded buffer
   becomes filled and joins the flush queue). A record must fit into a fresh block's content capacity (`1 MiB - 4` minus
   framing) — anything larger is `error.RecordTooLarge`; the consensus ops are session-sized, so this is a guard, not a
   limit that bites. Then the doc's fundamental rule: after the write there must remain at least one buffer whose header
   is the zero-terminator (`data_len = 0`, filled cleared) — the exact-fill of the last free buffer is refused with
   `error.WALFull`. ("Free" = holding no un-flushed committed data.)
2. **Copy.** Bytes go into the current buffer; the record never crosses a block boundary: if it does not fit the block
   remainder, the remainder is padded (zeros counted in the hash), the block's CRC is written into its last 4 bytes, and
   the record starts in the next block. PMEM: `CLWB` → `SFENCE` of the touched data.
3. **Spill.** When the current buffer is exhausted, grab the successor and continue there.
4. **Terminator.** An exactly filled buffer's successor gets `data_len = 0`, filled cleared, persisted (`CLWB` →
   `SFENCE`). This is the battery's core invariant, stated in the doc's own steps 4–6: **a data area only ever receives
   bytes after its control line has been persisted as a zero-terminator.** Every path that makes a buffer current (fresh
   allocation, exact-fill transition, post-flush reclamation in step 6) satisfies it.
5. **Commit-last.** The headers of the grabbed successors are persisted first, in chain order; the metadata of the
   buffer that was current at op start — the filled flag, the length, `crc_running`, `last_state` — is persisted
   **last**. This is the commit point of the write: a torn crash between the successor publishes and the old buffer's
   publish leaves a chain the walk refuses to trust past the last fully committed buffer.
6. **Flush queue.** Exactly one flush in flight, ever:
   `pushWriteOffset(fd, taskIdx, buffer_ptr, LBA, ordinal × LBA, flags)` (the positional variant exists in the vendored
   `zigring`, `src/iouring.zig:522`), the CQ handler marks the flushed buffer's header the zero-terminator (persisted in
   PMEM mode), advances `flushed_upto`, and submits the next buffer if it is marked filled. One at a time, per the doc:
   two in flight could persist N+1 while N is lost to scheduling, and the file would be non-contiguous.

**U3.** `docs/todo.md` wants the flush SQE to carry `RWF.DSYNC` in PMEM mode only, so the SSD's volatile cache is
flushed too; the vendored `zigring` zeroes `rw_flags` on writes today, so adopting it needs a small upstream variant.
Proposed: adopt it here (PMEM mode only) with the zigring tweak; the alternative is leaving it in `docs/todo.md` as
deferred — confirm or override.

**Reopen** (the writer half of recovery). Effective file length is `len & ~(LBA-1)` (the torn-tail rule);
`N = len / LBA` flushed buffers. In PMEM mode the committed chain is walked from ordinal N (the walk of §7, run in
"where do I continue" mode): the resume point is the chain's end — the current buffer, its `data_len`, its
`crc_running`, its `last_state`. In plain mode the tail is gone: the current buffer is fresh (header zeroed), and
`crc_running` is reseeded by one cold read of the open block's flushed extent from the file (skipped when the previous
block closed exactly: the file end is then on a block boundary and the next block starts empty).

## 6. Format and checksums

- Record: `state_idx` (proposed LE u128, `U1`), `uvarint(len(op))`, `op` bytes. The WAL is op-agnostic: it never encodes
  or decodes ops; the record codec (`encodeRecord` / framing validation) is a small helper in `src/wal.zig` for the
  driver's use. The doc's `TaskCtx.FileRead.buf: []u64` reads as a typo for `[]u8` — noted here as fact.
- Block: 1 MiB, last 4 bytes the CRC32C of the content, zero padding counted. Blocks align to buffer boundaries by the
  validated config (`1 MiB % lba == 0`), so the CRC slot always lands inside the block's last buffer and every block
  close is also a buffer fill.
- CRC32C via the vendored `@import("blog").crc32c.hardwareCrc32C` (the doc's `@import("blog").hardwareCrc32C` is off by
  one namespace — `root.zig` re-exports the `crc32c` module).
- **U6.** "The standard combinator for hashes of concatenated blocks": proposed — the standard CRC combination operation
  (the `crc32_combine` algorithm, Castagnoli-flavored: a GF(2) matrix shift of `crc2` by `len2` bytes), implemented in
  `src/wal.zig` as `crc32cCombine(crc1, crc2, len2)` and proven against naive recomputation in tests. Its role: the
  write path maintains the open block's running CRC incrementally — each appended piece is checksummed with
  `hardwareCrc32C` and combined in — without ever re-reading the block; the reader instead verifies a closed block with
  one `hardwareCrc32C` over its whole 1 MiB. Confirm this reading or state the intended one.

## 7. The read path

`WalReadFile` owns the fd (opened read-only by `walOpenRead`) and mints one `FileReadProcess` per read operation. A
`FileReadProcess` carries: the `Seek | Read` state, a block-sized buffer (1 MiB plus one LBA of slack for the merged
tail), the task description the doc asks for (`read_all` — no-alternative readout from the start; or
`seek_then_read(target_state)`), the sink, and the walk cursor.

**The merged stream.** The logical stream is the file bytes `[0, N × LBA)` followed by the PMEM chain (PMEM mode only):
from ordinal `N`, slot `o mod buffers_count`, take the buffer while its header's `buffer_seq` matches `o` (stale-lap
check) and the chain is committed — `filled` full LBA, or the partial current buffer (`data_len > 0`, not filled: the
live tail; take `data_len` bytes and stop). Stop at the first `data_len == 0` (the zero-terminator) or the first
inconsistency. This is the recovery walk of the doc's read section, run at open time for the writer, and per read task
for the reader; the doc's `buffer_idx(N + k) = (N mod 32 + k) mod 32` is exactly this slot arithmetic. PMEM tail bytes
are plain `memcpy` — no ring traffic; only file slabs go through the ring.

**The tail block rule.** The last block of the merged stream is open — it has no CRC yet (a CRC exists only when the
writer padded and closed it). The reader verifies a block's CRC when the bytes are there; a match means the block is
closed and its records parse up to the padding (a padding run reads as `state_idx == 0` with `len == 0` — no real record
has state 0, so the block scan stops there). A mismatch, or the open tail block, is read by framing alone: records parse
while they fit the merged extent; a record whose bytes run past the extent is torn and is dropped — replay stops there,
never repairs. **U10** anchors this rule plus the delivery contract.

**The seek.** `seek_then_read(T)` binary-searches the block index: read a block (file slab + PMEM tail), take its first
record's `state_idx` — a mebibyte boundary is always a record start, per the format — and if it is greater than `T` the
target lies before the block, else at or after it. Converge on the last block whose first record is `<= T`, then scan
forward through the blocks, delivering each record with `state_idx >= T` to the sink. The states are u128s and totally
ordered (the epoch slice sits above the op-counter slice), so the comparison is a plain integer compare and epoch jumps
inside one file search correctly.

**Driving.** A read task is armed as the doc shows: `state = .Seek` (or `.Read` for `read_all`), a slot is taken from
the ring's `RingSlots`, the `TaskCtx` variant is stored, `pushReadOffset(fd, taskIdx, buf, len, offset, flags)` is
submitted at LBA-aligned boundaries, and each CQE is dispatched by the `FileReadProcess.state` — continue seeking, start
the readout, assemble the merged block, verify, deliver. **U10** also proposes the delivery contract: a caller sink
`fn (ctx, state_idx: u128, op: []const u8) !void` — startup replay applies records through the existing `applyIndexOp`
(the sequencing of snapshot-then-WAL is the snapshot design's, `sdks/state-snapshot.md` §5; this plan only provides the
pieces plus a thin synchronous driver that pumps the same state machine with `popCQE`/`park` during Phase A recovery,
where the index thread already owns its ring); the remote-serve path streams the same records over the network — that
wiring belongs to the consensus design. One state machine, two drivers, as the doc's "synchronous is tolerable for a
start" suggests.

- File opens/unlinks are synchronous in `src/lifetime.zig`; data ops are ring-only. This keeps SQPOLL syscall-free on
  the hot path, per `docs/shard-arch-hld.md` §1.

## 9. Implementation stages and test gates

Each stage lands compiling and tested; `zig build test` stays green after every one.

- **A. Config + seam.** The `wal` block in `src/config.zig` with validation; the `Controller` grows the battery fields
  and the partition math (plain allocation first, the PMEM mapping behind the mode flag); the three methods exist as
  thin, correct skeletons (open/create/unlink, wrapper alloc/free). Tests: config round-trips and rejections; path
  construction; open/create/delete idempotence.
- **B. Format core.** `src/wal.zig`: `encodeRecord`, block framing (fit, pad, close), `crc32cCombine` proven against
  `hardwareCrc32C` of the concatenation over random splits and lengths (property test); padding and boundary cases
  (exact fit at every edge: buffer, block). Pure, no I/O.
- **C. Battery + write path, plain mode.** Ring algebra (slot from ordinal, laps), admission with the pad accounting and
  the never-full rule (the exact-fill-of-last-buffer refusal is a named test), the copy/spill/terminator/commit-last
  sequence against a memory battery with a **synchronous flush sink**. Tests: header chains after arbitrary write
  sequences; the terminator invariant holds on every path.
- **D. Ring-driven flush + close.** The one-at-a-time choreography with a fake CQ pump; buffer reclamation re-zeroes
  headers; `close` drains. Tests: interleavings, refusal when the SQ is momentarily full, exactly one flush in flight at
  all times.
- **E. PMEM mode.** The partition (`pair → area`), the barrier module (x86_64 asm, CPUID-gated fallback; a no-op barrier
  build flag so all logic tests run against an ordinary-memory "PMEM" battery — persistence itself is untestable without
  hardware and is covered by the walk logic instead), reopen via the walk. Tests: resume position, `crc_running` and
  `last_state` recovery, stale-lap and torn-commit chains (successor published, predecessor not — the walk must stop
  before), terminator stops.
- **F. Read path.** `WalReadFile`, `FileReadProcess`, the merged stream, the seek, the tail-block rule, the sink, the
  synchronous startup driver. Tests: round-trips of synthetic files (O_DIRECT where the filesystem supports it — `tmpfs`
  does not, so the fixture detects `EINVAL` at open and falls back to buffered for logic tests; a manual integration
  checklist covers a real filesystem); binary search over many blocks and epoch jumps; **fuzz**: random truncations and
  byte flips of a valid file must never panic and must stop the stream at the first inconsistency.
- **G. Wiring.** `src/index.zig` owns one wrapper per data set, dispatches the two CQE kinds, and the recovery
  invocation point is documented for the snapshot design to call. `docs/WAL.md` gains a pointer to the promoted plan;
  `docs/todo.md` loses the items this plan absorbs (only **U3**'s outcome decides that).

## 10. What the later designs own

The snapshot design: the registry, the pairing, the sequencing (load snapshot → set `st.state` from the tag → open the
WAL → replay). The consensus driver: what is written, when, the monotonicity discipline above the writer's floor, and
the remote-serve request handling. Rotation/retention: when `delete` is called. The toolchain: `pmem-migrate`
(`docs/todo.md`).
