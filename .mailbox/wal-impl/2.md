## 1. The source design, restated with the answers folded

One index — including a mirror index — has its own WAL file. An index is the triple
`(host_idx, index_idx, self_index_state)`; the file holds the data of exactly that data set (every accepted op of it,
whichever replica's index thread writes it, and nothing else; consensus artifacts never touch the WAL — U9), and
juggling several data sets is the index thread's business as an execution flow, each data set with its own file and its
own battery.

```zig
// lifetime.Controller, src/lifetime.zig
pub fn walOpenWrite(self: *Self, host_idx: u8, index_idx: u16, state: u128) !*WalWriteFile;
pub fn walOpenRead(self: *Self, host_idx: u8, index_idx: u16, state: u128) !*WalReadFile;
pub fn delete(self: *Self, host_idx: u8, index_idx: u16, state: u128) !void;
```

**U2 (folded).** On-disk name: `wal.<host_idx>.<index_idx>.<state>` in the configured directory, `<state>` rendered as
32 lowercase hex digits — symmetric with the snapshot convention (`sdks/state-snapshot.md` §3.4). The tag is opaque:
nothing derives an epoch or a slice back from it, and nothing parses it except to hand it to `st.state` at load
(`sdks/state-snapshot.md` §5: the caller sets the state from the name tag **before any op is applied**).

The `state` argument of `walOpenWrite` is (a) the file name tag and (b) the writer's positioning floor — "calibrated for
writing starting from the given index" (`docs/WAL.md`:15). What "starting from" means for the _first_ record is **U11**
below; everything else about the discipline is settled.

`walOpenWrite` hands out a writer over the existing file or, if none exists, over a freshly created one. `walOpenRead`
and `delete` open/unlink synchronously with the `std.os.linux.open` idiom of `createLogFile` (`src/lifetime.zig:267`) —
cold, rare operations, per data set per epoch; the ring carries only data traffic (flushes and reads), keeping the
SQPOLL hot path syscall-free (`docs/shard-arch-hld.md` §1).

**U4 (folded).** `close(self: *Self) !void` drains the flush queue — retries a pending submission if one is parked
(§3.6), then waits for the in-flight completion on the caller's ring, releases the battery slice and the fd. `delete`
unlinks and is idempotent: a missing file is success.

## 2. The battery

Two operating modes, both buffered. Per-record `O_DIRECT` is rejected outright.

- **Plain mode.** The battery is ordinary allocated memory; a crash loses the un-flushed tail; durability of a record
  begins when its buffer's flush completes.
- **PMEM mode.** The battery is a computed region of an mmap'd NVDIMM; every publish is `CLWB` → `SFENCE`, so the
  un-flushed tail survives a power cut; the file flush exists to recycle ring slots, not to establish durability. The
  headers are **never zeroed** in this mode — their whole point is to survive. Plain mode zeroes its DRAM headers at
  allocation.

Memory decomposition, both modes, per pair `(host_idx, index_idx)` — two columnar arrays inside the pair's area: the
data array first (`buffers_count × |LBA|`, LBA-aligned by construction), then the header array (`buffers_count × 64`).
Area stride: `buffers_count × (|LBA| + 64)` rounded up to a multiple of `max(|LBA|, page)` so every pair's data array
stays LBA-aligned. Pair → area index `index_idx × hosts + host_idx` (U8: "index_count" in the doc's formulas is the
**pair count** `indexes × hosts`; thread-major, stable across restarts, movable only by the migration toolchain).

A pair's area is owned by its index thread and **lives as long as that thread** (U1's pad): WAL files open and close
over the same area epoch after epoch; the battery is not per-file. In plain mode the thread's slices are allocated at
thread start with zeroed headers; in PMEM mode the stick is mapped once (`lifetime.Controller`, the resource owner) and
the areas are used as found. Inside one area, the headers and buffers form a ring:
`buffer_idx(o) = o mod buffers_count`, the doc's `buffer_idx(N + k) = (N mod 32 + k) mod 32`.

**U5 (folded).** `BufferHeader`, one per slot, exactly 64 bytes — one cache line, so **one publish is one `CLWB` and is
atomic in practice**; that line size is the reason the header exists:

| field              | meaning                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `data_len: u32`    | valid bytes in this buffer; `                                                                                      | LBA | `when filled,`0` for the zero-terminator     |
| `flags: u32`       | bit 0 = filled                                                                                                     |
| `buffer_seq: u64`  | the buffer's **absolute ordinal** (`file_position ÷                                                                | LBA | `): the flush offset and the stale-lap check |
| `crc_running: u32` | the running CRC32C of the open block as of this buffer's committed extent; makes reopen trivial — no re-reading    |
| `last_state: u128` | the `state_idx` of the last record ending within this buffer's committed extent — the writer's floor after restart |
| `reserved: u32`    | padding to 64                                                                                                      |

**The uniform publish rule** (a consequence of U5's fields, pinned here): _every_ header publish — commit, terminator,
post-flush reclamation — writes `buffer_seq` as the absolute ordinal being published. A zero-terminator publish for
ordinal `o` writes `data_len = 0`, `filled = 0`, `buffer_seq = o`, and carries `crc_running`/`last_state` **as of the
preceding committed buffer's end** — the values a resume from an empty buffer `o` continues from. A commit publish for
ordinal `o` covers the bytes committed _in_ `o`. Result: whatever state a walk finds, `crc_running`/`last_state` are
always the correct fold-back point for that buffer's committed extent.

**U7 (folded).** The `wal` config block is **not optional** — there is no configuration that leaves the WAL module
unopened. "Not optional" reads as _always on_: the block carries full defaults and the default document is a runnable
dev environment — `hosts = 1` (single host, no replication), plain mode. The comptime default check (`config.zig`
`Manager()` validating `Config{}`) forces this shape: every field defaultable, the default valid. Remaining knob
defaults are **U13**.

**U3 (folded).** Flushes carry `RWF.DSYNC` in PMEM mode only, per `docs/todo.md`: the SSD controller must drop its
volatile cache too, else the file — which in PMEM mode exists only to recycle slots — can silently lose a flushed buffer
the battery has already forgotten. The flag rides the SQE (`sqe.rw_flags = std.os.linux.RWF.DSYNC`,
`std/os/linux.zig:4974`), not a separate `fdatasync`; the snapshot doc's "the WAL path never fdatasyncs"
(`sdks/state-snapshot.md` §3.4) stays true. What zigring lacks for this is §8; the todo item is absorbed by this plan at
stage G.

## 3. The write path

**U1 (folded).** The writer API is:

```zig
pub fn write(self: *Self, state_idx: u128, data: []u8) !void
```

The caller (the consensus driver, whose minting discipline this feeds — `st.state` is "moved only by the consensus
driver", `src/state.zig:157`) passes the raw op bytes; **the writer frames the record** (`state_idx` as 16 LE bytes,
then `uvarint(len(data))`, then `data` — the same uvarint scheme as `lifetime.putUvarint`/`readUvarint`,
`src/lifetime.zig:774`/`:790`) and copies it into a battery buffer synchronously; the caller may reuse `data` the moment
`write` returns. The record's bytes then live in the battery for as long as the index thread does.

The state discipline: `prev_state_idx: ?u128` on the writer — **null after open** (first start or restart, as the pad
says), the last accepted state thereafter; every write after the first must satisfy `state_idx == prev_state_idx + 1`.
The first accepted write's constraint is **U11**. The layout fact behind it: `state` is
`host_id: u8, index_id: u16, epoch_id: u40, index: u64` (`src/state.zig:157`), whose low `u64` is the op ordinal within
the epoch — so strict `+1` inside one file means **an epoch bump never happens mid-file**; a new epoch is a new triple,
a new snapshot and a new WAL (`sdks/state-snapshot.md` §3.6: the index thread finishes the WAL swap before the registry
append).

The error set of `write` (pad's three kinds plus the doc's space refusals):

| error                   | when                                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- |
| `error.WALFull`         | the fundamental rule: after this write, no buffer would remain free                                        |
| `error.RecordTooLarge`  | the framed record cannot fit a fresh block's content (`1 MiB - 4`)                                         |
| `error.InvalidStateIdx` | `state_idx` violates the `+1` discipline / **U11**'s first-write rule                                      |
| `error.NoFreeSlots`     | a flush submission would be needed and the slot table is depleted (`zigring.Slots.add`, `slotter.zig:111`) |
| `error.RingFull`        | a flush submission would be needed and the SQ window is full (`getOpSlot`, `iouring.zig:409`)              |

What a refusal of the last two kinds _means_ — nothing written, `prev_state_idx` untouched — and the completion-side
counterpart policy are **U12**.

### 3.1 Admission

On the owning index thread, before any byte moves:

1. Compute the cost: the framed record, plus — if it does not fit the current block's content remainder — the zero
   padding of the whole remainder plus the 4 CRC bytes. Padding can span several buffers; every padded buffer becomes
   filled and joins the flush queue. A record that cannot fit a fresh block is `error.RecordTooLarge` (the consensus ops
   are session-sized; a guard, not a biting limit).
2. The fundamental rule: after the write there must remain at least one free buffer (`data_len = 0`, `filled` clear) —
   an exact fill of the last free buffer is `error.WALFull`.
3. **U12's proposal**: if this write will require a flush submission at its end (it fills ≥ 1 buffer ∧ no flush is in
   flight ∧ none is pending) check now that a slot is available (`RingSlots.add`) and the SQ window has room; a refusal
   here leaves the writer untouched.

### 3.2 Copy, spill, terminator, commit-last

4. Bytes go into the current buffer; the record never crosses a block boundary: if it does not fit the block's content
   remainder, the remainder is zero-padded (zeros counted in the hash), the block's CRC is written into its last 4 bytes
   (inside the block's last buffer, since `1 MiB % lba == 0`), and the record starts in the next block. PMEM: `CLWB` →
   `SFENCE` of the touched data.
5. When the current buffer is exhausted, grab the successor and continue there.
6. An exactly filled buffer's successor gets the zero-terminator publish (§2's uniform rule: `data_len = 0`, `filled`
   cleared, `buffer_seq` = the successor's ordinal, resume values carried), persisted `CLWB` → `SFENCE`. This is the
   battery's core invariant: **a data area only ever receives bytes after its control line has been persisted as a
   zero-terminator for its ordinal**. Every path that makes a buffer current satisfies it: fresh allocation, exact-fill
   transition, post-flush reuse.
7. **Commit-last.** The headers of grabbed successors are persisted first, in chain order; the metadata of the buffer
   that was current at op start — `data_len`, `filled`, `crc_running`, `last_state` — is persisted **last**. That
   publish is the write's commit point: a torn crash between the successor publishes and the old buffer's publish leaves
   a chain the walk refuses to trust past the last fully committed buffer.

### 3.3 The flush choreography

Exactly one flush in flight, ever, per doc step 6 — two could persist N+1 while N is lost to kernel scheduling and leave
the file non-contiguous:

- Submit one flush per SQE: `StreamSQ.pushWriteOffset(fd, task_idx, buffer_ptr, |LBA|, ordinal × |LBA|, flags)` from
  ordinal `flushed_upto`'s slot, then `StreamSQ.commit()` to publish (§6 explains why the stream path, not the direct
  `Ring.pushWriteOffset`). `rw_flags` = `RWF.DSYNC` in PMEM mode (**U3**), `0` otherwise.
- On the completion (the index thread's CQ drain, `src/index.zig:89`): mark the flushed buffer's header the
  zero-terminator for its ordinal (persisted in PMEM mode), advance `flushed_upto`, retire the slot, and submit the next
  buffer if it is marked filled. A submission failure _here_ has no caller to error into — **U12's proposal**: park
  `flush_pending`, retried by the drain pass each loop iteration; nothing is lost, the flush is merely delayed, and the
  SQ window drains as other ops complete.
- After the write's commit, if a flush submission is due and was pre-checked at admission, it cannot fail.

### 3.4 Open, fresh and reopen

**Fresh open** (no file exists). Persist the ordinal-0 zero-terminator of the pair's area **first**, then create the
file. This ordering is what makes a stale slot-0 header from a previous file of the same pair untrustworthy _by
construction_: a 0-length file implies its slot-0 terminator was persisted (the walk starts at ordinal 0 and stops
there), and no file at all means no walk. If the terminator were written after the create, a crash in between would
leave a 0-length file whose slot 0 still holds the _old_ file's committed header (`buffer_seq == 0`, filled) — a false
positive the walk would deliver as this file's content.

**Reopen.** Effective file length is `len & ~(|LBA| - 1)` (the torn-tail rule); `N = len / |LBA|` flushed buffers. In
PMEM mode the committed chain is walked from ordinal `N` (§5's walk, in "where do I continue" mode): the resume point is
the chain's end — the current buffer, its `data_len`, `crc_running`, `last_state`. In plain mode the tail is gone: the
current buffer is fresh (header zeroed), and `crc_running` is reseeded by one cold read of the open block's flushed
extent from the file — skipped when the file end is on a block boundary, because the previous block closed exactly and
the next block starts empty.

## 4. Format and checksums

- Record: `state_idx` (16 LE bytes), `uvarint(len(op))`, `op`. The WAL is op-agnostic: it never encodes or decodes ops;
  `encodeRecord` and the framing validation are small helpers in `wal.zig`. The doc's `TaskCtx.FileRead.buf: []u64` is a
  typo for `[]u8` — noted as fact in iteration 1 and unchanged.
- Block: 1 MiB, last 4 bytes the CRC32C of the block's content (zero padding counted). Blocks align to buffer boundaries
  by the validated config, so the CRC slot always lands inside the block's last buffer and every block close is also a
  buffer fill.
- CRC32C via `@import("blog").crc32c.hardwareCrc32C` (`src/crc32c.zig:5` in blog 0.0.17; `blog/src/root.zig:68`
  re-exports the module — the doc's `@import("blog").hardwareCrc32C` is off by one namespace).

**U6 (folded).** The combinator is the first form:

```zig
pub fn combinedCrc32C(prev: u32, data: []const u8) u32
```

and _not_ the three-argument `crc1/crc2/len` combine, and _not_ a `std.hash.Crc32.init()` builder. Why form 1: blog's
convention is `~fold(~0, data)` (init `0xFFFFFFFF`, final XOR), and CRC composition under that convention is just a
**seeded fold**: `crc(A || B) = ~fold(~crc(A), B)`. Every use site holds the bytes — the writer folds each appended
piece into the open block's running CRC (`crc_running = combinedCrc32C(crc_running, piece)`, no re-read ever), the
plain-mode reopen reseeds by folding the flushed extent, and the reader verifies a closed block with one whole-block
`hardwareCrc32C`. Form 2 (the GF(2)-matrix `crc32_combine`) buys nothing any of those sites needs and costs ~30 lines of
matrix math. No builder object anywhere.

What blog is missing for this is small and listed in §8.1; the property test proving the algebra
(`combinedCrc32C(hardwareCrc32C(A), B) == hardwareCrc32C(A ++ B)` over random splits and lengths) runs in Debug too,
where blog's x86_64 path uses its std `CRC-32/ISCSI` fallback — same convention, so the test proves the same algebra on
both paths.

## 5. The read path

**U10 (folded).** `WalReadFile` owns the fd (read-only, from `walOpenRead`) and mints one `FileReadProcess` per read
operation: the `Seek | Read` state, a block-sized buffer, the task description the doc asks for — `read_all` (the
no-alternative readout from the start) or `seek_then_read(target_state)` — the sink, and the walk cursor. Delivery
contract: a caller sink `fn (ctx, state_idx: u128, op: []const u8) !void`; startup replay applies through the existing
`applyIndexOp` (`src/lifetime.zig:467`, whose contract — caller sets `st.state` before applying — is exactly why the
sink passes `state_idx` separately from `data`); the remote-serve path streams the same records, wired by the consensus
design. One state machine, two drivers; the startup driver pumps `popCQE`/`park` synchronously during Phase A on the
index thread that owns the ring.

**The merged stream.** The logical stream is the file bytes `[0, N × |LBA|` (tail shorter than a buffer ignored)
followed by the PMEM chain (PMEM mode only): from ordinal `N`, slot `o mod buffers_count`, take buffers while the header
checks out. The walk predicate, pinned:

| header at ordinal `o`                         | verdict                                          |
| --------------------------------------------- | ------------------------------------------------ |
| `buffer_seq != o`                             | stale (previous lap or previous file) → **stop** |
| `buffer_seq == o` ∧ `data_len == 0` ∧ ¬filled | zero-terminator → **stop**                       |
| `buffer_seq == o` ∧ `data_len ==              | LBA                                              | ` ∧ filled                   | committed full buffer → take all, **continue** |
| `buffer_seq == o` ∧ `0 < data_len <           | LBA                                              | ` ∧ ¬filled                  | the live tail → take `data_len`, **stop**      |
| anything else (`data_len ==                   | LBA                                              | `∧ ¬filled,`filled` ∧ short) | torn metadata → **stop**, never deliver        |

The writer's resume point is wherever the walk stops: the next ordinal to write into, with `crc_running`/`last_state`
taken from that buffer's header (§2's uniform rule makes them correct in every case). Mid-chain stale false-positives
are unreachable by construction: commit-last persists a successor's terminator _before_ the predecessor's commit, so
"predecessor committed ∧ successor header stale" cannot occur, and the fresh-open ordering of §3.4 closes the only
remaining window.

**The tail block rule.** The last block of the merged stream is open — it has a CRC only if the writer padded and closed
it. A closed block's CRC match ends parsing at the padding (a padding run parses as `state_idx == 0` with `len == 0`,
and state 0 is the empty state — a freshly loaded snapshot also starts at `state = 0`, `sdks/state-snapshot.md` §5 — so
no real record ever carries it). A mismatch, or the open tail block, is read by framing alone: records parse while they
fit the merged extent; a record running past the extent is torn, dropped — replay stops there, never repairs. The fuzz
gate must hold: random truncations and byte flips never panic, the stream stops at the first inconsistency.

Delivered records also obey the `+1` discipline across deliveries: from the second delivered record on,
`state_idx == prev + 1`; a gap is an inconsistency and stops the stream (the writer guarantees it; the reader enforces
it as a second net).

**The seek.** `seek_then_read(T)` binary-searches the block index: read a block, take its first record's `state_idx` — a
mebibyte boundary is always a record start, so this is one parse — and if it exceeds `T` the target lies before the
block. Converge on the last block whose first record is `≤ T`, then scan forward, delivering every record with
`state_idx ≥ T`. Edges: `T` below the file's first record → deliver from the first record; `T` past the last → an empty
delivery (the sink is never called). States are u128s and totally ordered (the epoch slice sits above the op-ordinal
slice), so the compare is plain integer math.

**Driving.** A read task is armed as the doc shows: `state = .Seek` (or `.Read` for `read_all`), a slot from the
thread's `RingSlots`, the `TaskCtx` variant stored, `StreamSQ.pushReadOffset(fd, task_idx, offset, dst, flags)` at
LBA-aligned boundaries, `StreamSQ.commit()`, and each CQE dispatched by `FileReadProcess.state` — continue seeking,
start the readout, assemble the merged block, verify, deliver. PMEM tail bytes are plain `memcpy` — no ring traffic;
only file slabs go through the ring.

**Concurrency.** Everything of a pair is touched only by its index thread (the `state.zig` G1 discipline), so a
`WalReadFile` open alongside a live writer — the remote-serve case — interleaves safely with no atomics and no locks;
the reader sees the chain as of its own position in the thread's loop. A second _writer_ on a live triple is **U14**.

## 6. Ring integration

- `TaskCtx` (`src/slots.zig:41`) gains `file_read: struct { file_process: *FileReadProcess, offset: u64, buf: []u8 }`
  and `wal_flush: struct { writer: *WalWriteFile }` — plain data, one pointer plus scalars, destructor-free by the
  existing comptime rules; slot ids stay below `slots.max_capacity` by construction.
- **The submission path is `RingStuff.sqstream` (`StreamSQ`), not the direct `Ring.push*`.** Every ring arms a stream
  window at init (`src/lifetime.zig:370`), file logging already submits through it (`src/logging.zig:162`), and mixing
  direct pushes with a live `StreamSQ` on one ring is the Z2 hazard catalogued in `ZIGRING-FIXES.md` — the direct/stream
  cursor bookkeepings diverge. The WAL adds no new mixing: its flushes and reads go through
  `sqstream.pushWriteOffset`/`pushReadOffset` + `sqstream.commit()` (both variants already exist,
  `iouring.zig:1951`/`:1975`). The only direct push left on an index ring is `reportDrained`'s `pushMsgRing` at shutdown
  (`src/index.zig:182`), which Z2's resolution will make safe. Window-full surfaces as `push*` returning `null` (not an
  error) — that is `error.RingFull`'s stream-side face.
- The index thread's CQ drain (`src/index.zig:89`) gains the two lookups: a `wal_flush` completion advances the writer's
  queue (§3.3), a `file_read` completion steps its process. Reserved control indices (`src/messages.zig`) stay
  untouched. CQ batch commit stays as is (`BatchCQ.commit` releases consumed completions only — it does not publish
  SQEs; the WAL always publishes through `StreamSQ.commit()` itself).

## 8. What the upstream modules are missing

### 8.1 zigring (the U3 deliverable)

**Z7 (new; slots into `ZIGRING-FIXES.md`'s list): write pushes cannot carry `rw_flags`.**

- **Where:** `StreamSQ.pushWrite` (`iouring.zig:1928`) and `StreamSQ.pushWriteOffset` (`:1951`) — the WAL's actual path;
  symmetric gaps in `Ring.pushWrite` (`:491`), `Ring.pushWriteOffset` (`:522`), `Ring.pushWritev` (`:556`). All of them
  zero the SQE (`reserve` `:1905` / `getOpSlot` `:415` memset) and never touch `sqe.rw_flags`; the only functions that
  set `rw_flags` today are the socket sends (`pushSendZC` `:637`, MSG_* flags) and `pushCancel` (`:1478`, zeroing it
  explicitly).
- **Why it matters:** PMEM-mode WAL flushes need `sqe.rw_flags = std.os.linux.RWF.DSYNC` (`std/os/linux.zig:4974`, value
  `0x2`) so each `O_DIRECT` write also drains the SSD controller's volatile cache (`docs/todo.md`). Reads need nothing —
  `RWF_HIPRI` and friends are irrelevant here.
- **Proposal:** add an `rw_flags: u32` parameter to the write family. zigring has no external users, and mpy6a's only
  stream write call site is `src/logging.zig:162`, which passes `0` — so extending the existing signatures is free and
  preferable to parallel `*Rw` variants. Minimum set: the two `pushWriteOffset`s (stream first). A zigring-side
  re-export of `std.os.linux.RWF` would save the import, but a plain `u32` is fine too.
- **Not needed for the WAL:** Z1's `parkFor` (close's drain can use plain `park` today; the bounded variant would
  improve shutdown latency, not correctness), Z2 (avoided by going stream-only, §6), Z3–Z6 (unrelated).

### 8.2 blog (the U6 deliverable)

`crc32c.zig` needs the seeded fold behind `combinedCrc32C(prev: u32, data: []const u8) u32`. Three paths in that file,
each a few lines:

- x86_64/ReleaseFast (`:13`): the `crc32q`/`crc32b` loops with the running register started at `~prev` (zero-extended
  into the u64), final `^ 0xFFFFFFFF` — the existing `hardwareCrc32C` body with a different seed.
- aarch64 (`:33`): same change with `crc32cx`/`crc32cb`.
- fallback (`:53`): `std.hash.crc.@"CRC-32/ISCSI"` has no seeded `init` (`hash/crc.zig:951` — `init()`, `update`,
  `final`, `hash` only), so this path needs its own small fold — a 256-entry reflected table (`0x82F63B78`) or a bitwise
  fold, started at `~prev`, final `^ 0xFFFFFFFF`. Slow is fine; it is the non-server path.

The snapshot design: the registry (pairing snapshots with WALs), the sequencing (load snapshot → set `st.state` from the

## Open questions

- **U11 (blocking).** What constrains the _first_ accepted write after open? Iteration 1's confirmed `last_state`
  description ("the writer's monotonicity floor after restart") and U1's "`prev_state_idx` is null after start/restart"
  must be reconciled. Proposed: the open state **is** the effective predecessor — the first accepted write must satisfy
  `state_idx == floor + 1`, where `floor` is the tag on a fresh open and the walk-recovered `last_state` on a reopen;
  `prev_state_idx: ?u128` then simply holds the last accepted state (null before any). This makes the fresh file
  `wal.h.i.S` hold exactly `S+1, S+2, …` — matching the snapshot flow, where the tag is `st.state` at the procedure
  start and replayed records each move the state by one. Alternatives: no first-write check at all (the caller owns it;
  `last_state` then serves only the future consensus design), or a loose `> floor` instead of `== floor + 1`. Confirm or
  override.
- **U12 (blocking).** Failure semantics of `write`, two layers. (a) Write-side: errors 2/3 (`NoFreeSlots`, `RingFull`)
  are **admission refusals** — the check of §3.1.3 runs before any byte or header moves, so a refused write leaves
  nothing written and `prev_state_idx` untouched, and the post-commit submission cannot fail; `write` returns `!void`.
  (b) Completion-side: when the flush-chain submission at a CQE fails (window momentarily full), the writer parks a
  `flush_pending` flag and the index thread's drain retries each loop pass — no error surfaces anywhere, the data is
  committed and only the flush is delayed. Confirm or override.
- **U13.** Remaining `wal`-block defaults: `dir` — proposed default `"wal"` (relative to cwd, the directory created at
  startup; or should it be required?), `buffers = 32`, `lba = 4096`, `hosts = 1` (given); and confirm the reading of
  "not optional" as _always on with a valid default document_ (the siggy `Manager()` comptime check forces every field
  to default; "required key" is not expressible without changing it). Confirm or override.
- **U14.** Double-open guard: `walOpenWrite` on a triple with a live writer returns a typed error (proposed
  `error.WalOpen`); `walOpenRead` stays unrestricted, including concurrent with the writer. Confirm or override — the
  alternative is leaving the guard to the consensus/rotation designs' caller discipline.
