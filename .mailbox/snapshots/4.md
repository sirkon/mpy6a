## 1. The pad's answers, restated as fact

- **U19 — the composite's completion rule is AND, and the reply is the index thread's.** Confirmed as proposed, with the
  pad's actor correction folded in: **the front never replies; it dispatches; replies are made by indexes.** The rule,
  normatively: an event written through the composite is **complete** — durable, replyable — only when **both** sides'
  flushes have completed, and the client's reply, when one exists, is sent by the index thread only then. Outside a
  window the single writer's flush completing is the event's completion — the landed durability contract, unchanged.
  The tree already owns every piece of the shape: the flush CQEs die inside the index's own drain (`.wal_flush`,
  `src/index.zig:127-137` — reclaim the buffer, advance the writer's queue, nothing else), and the session fd belongs to
  the index thread from `routeAccepted` on, so no second channel exists to acknowledge by accident. The consequence set
  of iteration 3's §4 stands on the confirmed rule: durable ⊆ both files, always — either single-side rule loses durable
  events in one of the two outcomes (old-side-only loses at the swap, new-side-only at an abort, plain mode both times),
  which is exactly what the crash table and the repair scope assume. A plain-mode aborted migration therefore loses
  nothing durable, and the bring-tail is PMEM-only — it preserves the published tail (`CLWB`+`SFENCE`,
  `src/wal.zig:925-931`), not durability itself. The tracking — pairing an event with both sides' flush completions
  during a window — is staged-plan material; the design pins the rule, and the front/consensus material must honor it
  when its delivery channel lands.
- **U20 — the record cap is a producer contract, enforced at the index thread's intake.** The pad picks the alternative:
  the WAL's structural cap stands untouched — `framed > BLOCK_CONTENT` → `RecordTooLarge` (`src/wal.zig:961`), the 1 MiB
  block (`src/wal.zig:26-33`); records stay structurally legal spanning `lba`-sized buffers, and `wal-impl`'s own
  spanning tests keep passing unchanged — and the binding moves to the producers, with the enforcement **on the index
  side**: the index thread decides whether dispatched data is too large and may reply the client with proper
  diagnostics. Normatively: a record handed to an index thread's write path must not exceed the pair's `lba` (`lba` is
  the buffer size and the flush granularity, a power of two in `[512, 1 MiB]`, `src/config.zig:86-87`, `:554`); the
  check sits at the index thread's intake, where every dispatched event passes, window or not — today the front's
  dispatch, tomorrow whatever channel the consensus material lands — so it covers every event that can become the
  bring-tail's surplus; and the refusal is a protocol answer with a client-facing diagnostic — not a fault, not a
  freeze trigger (it stands on `wal-impl` §3.5's non-trigger side), with the wire shape the consensus design's. The
  room argument closes: the inter-write cut record is a window event, hence index-checked, hence `≤ lba`; it once fit
  ring `k`'s ordinary path — which keeps a buffer free (`src/wal.zig:974-975`) — so it fits the same-sized old ring
  emptied by the bring's flush, a fortiori. The bundled floor stands: `buffers ≥ 4` replaces today's floor of 2 at the
  validation site (`src/config.zig:557`), the doc line (`:389`) moving with it, and config validates the snapshot pool's
  `N ≤ 65535` beside `new_wal_buffer_idx: u16`. The pending `wal-impl` §3 amendment leaves the supersession list:
  nothing in `wal-impl` §3 changes.
- **U21 — the message, slot and pending discipline stands as compiled.** Confirmed. Iteration 3's §5 is normative
  exactly as written: the snapshot slot payload is `{ status, job }` on a `CrossTaskSlots` generalized over its payload
  — `in-flight` at the tick, `rollback` when an unwind dispatches cleanup, cleared by the elephant's `release(k)`; every
  release is an elephant's — the final-close elephant on success, the cleanup elephant on every failure rung — and the
  index thread never calls `release`; the terminal `SnapshotDone` reply clears the index's in-flight flag, riding the
  elephant's spin-retry idiom (`src/elephant.zig:67-75`) with the requesting ring's identity in the job; the pending op
  holds the acquired slot id and the target ring and retries only the `MSG_RING` once per batch pass (one pass = one
  drained batch, `src/index_inbox.zig:324-336`), never spinning the index thread; the fd reply carries the fd alone
  (`{ job, fd }` measures 24 bytes against the 16-byte cap, `src/cross_task.zig:67`), every other reply the job or a
  status alone; the tick's reserved `taskIdx` is `-7` (the only free index near the top: `-2` and `-3` belong to the
  inbox protocol, `src/index_inbox.zig:40`, `:44`); and the `CrossTaskMessageIdx` arm is implemented in the index
  drain (today such a CQE falls into `else` and its slot leaks, `src/index.zig:118-122`) — the elephant→index
  direction's first real senders being the fd reply, the abandon message, the completion and the terminal reply.
  Requests
  (`SnapshotCreate`, `SnapshotDump`, `SnapshotCleanup`, `SnapshotClose`) carry `{ job }`; exact variant naming is the
  staged plan's.
