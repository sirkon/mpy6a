## 1. The source design, restated in English

### 1.1 Overview

The snapshot mechanism is decoupled from consensus and runs opportunistically per `(host_idx, index_idx)`. The task is
set within a specific index: once every T seconds that index looks at the lengths of its WAL files — the WAL files of
the data sets carrying its index number, its own and the mirror data sets from other hosts — and decides "for the data
of this host under my index number, a snapshot must be taken and a new WAL file started."

### 1.2 The periodic size check

A ticker over the index-flow's ring delivers a special message once every T seconds. On receipt, the index thread (the
one holding `index_idx_0`):

1. Looks at all pairs `(host_idx, index_idx_0)` and the size of each pair's WAL file. Every pair whose size exceeds a
   certain `S` becomes a snapshot candidate.
2. Among the candidates, the pair `P` with the largest size is chosen.
3. A task is set: create a state snapshot for `P = (host_idx_0, index_idx_0)`.

### 1.3 Setting the snapshot-creation task

Snapshot creation runs on elephant threads. The task description travels through `CrossTaskSlots` and the message ring.
The index thread:

1. Selects an elephant from the existing ones by some criterion (round-robin, balanced round-robin, etc.).
2. Occupies a slot in `CrossTaskSlots` with the task description — the slot stays occupied until the operation
   completes, regardless of outcome.
3. Throws the slot identifier into the elephant's ring through its own ring.

### 1.4 Executing the task: the prelude

1. The elephant creates a new WAL file and sends the index thread a message (through the same mechanism): here is the
   new WAL file for this task (easiest done within the same slot). "What happens next?"
2. The index thread receives this message and:
   1. Takes a clone of its state.
   2. Replaces its WAL file interface with a composite one: on writing an event, write first to the NEW file, then to
      the old one. A write failure on the old file means the end of client service — new client requests stop being
      processed, and the thread listens ONLY to lifetime-control commands.
   3. Selects an elephant again, this time for the actual snapshot creation.

### 1.5 Creating the snapshot

The clone is already at hand — it was added to the slot's data. The elephant may be a different one from the elephant
that created the new WAL file.

1. The elephant dumps the state of the specific pair `(host_idx_0, index_idx_0)` and writes it to a file. The logic is
   synchronous — the elephant exists precisely for this.
2. After a successful creation it writes to a FIXED file (each index thread uses its own file) data of the form

   ```json
   {"host_idx":host_idx_0,"snapshot_path":"/path/to/snapshot/file","wal_path":"/path/to/wal/file"}
   ```

   with a mandatory `\n` after the line. It may then compact this file: keep only the last `N` records per `host_idx`.
   Naturally this is done transactionally — a new file is created, filled with the content, and renamed to the fixed
   name.

3. Then a message is thrown to the index thread: "compaction complete." On delivery failure, retry (after a small
   spin-wait).

### 1.6 Completion on the index thread

After receiving the message, the index thread replaces the composite WAL interface with a single one, in which it must
write ONLY to the new file. If it was frozen because of a write failure on the old WAL file, it makes a revival attempt.

### 1.7 Invariants and constraints

- Only ONE snapshot-creation operation may be in flight within an index. New ticker events for snapshots are ignored.
- The snapshot for a given `host_idx_0` is described by the last line (in that fixed file) carrying that
  `"host_id":host_idx_0`.
- An invalid line in the fixed file is a fatal error of startup and of functioning (if the elephant compacting such a
  file runs into it, it makes a process-stop request).
- WAL and snapshot file names contain the `state_idx` the mirror had at the moment the elephant was selected to begin
  the snapshot creation (fixed in the slot's data).

## 2. What the tree already has

The codec and the seams exist and are tested; the choreography does not:

- **The clone/dump/load codec.** `Controller.cloneIndexState(st, arena)` (`src/lifetime.zig:969`) deep-copies any
  `IndexState` into the caller's arena — sessions, compensator bytes, buffer backings, replay blobs; the result shares
  no allocation with the live state. `dumpIndexState` (`:842`) grows an `ArrayList(u8)` with the clone's queue allocator
  (the arena), so one `arena.reset(.free_all)` releases clone and dump bytes together. `loadIndexState` (`:890`) rejects
  `UnsupportedVersion`/`CorruptInput` and returns `state = 0` — the caller sets `st.state` from the snapshot file's name
  tag before any op is applied. `SNAPSHOT_VERSION = 1` (`src/state.zig:19`).
- **The WAL module** (`src/wal.zig`, landed per `designs/wal-steps.md`).
  `WalWriteFile.write(new_state_idx, floor_state_idx, data)` (`:950`) admits by `floor == head`; `head`/`tag` start at
  the base state (`:639`); the floor is never stored — it is computed validation input. Names:
  `wal.<host_idx>.<index_idx>.<state>` with `<state>` as 32 lowercase hex digits (`walPath`, `:196`). `close` (`:1262`)
  drains and awaits the in-flight flush on the caller's ring; `fault` (`:1213`) is a permanent per-writer stop;
  `flushResult` (`:1196`) faults on a negative CQE `res`. `fileSize` is a cold statx (`:336`). The battery: per-pair
  areas (`areaIndex`, `:220`) that "files rotate over … epoch after epoch" (`src/lifetime.zig:96`).
- **The adoption entry.** `Controller.walAdoptWrite(host_idx, index_idx, tag, fd)` (`src/lifetime.zig:434`) exists with
  the `wal-impl` shape: it **closes the old writer first**, then opens the writer over the elephant's fd and publishes
  the ordinal-0 terminator **before** "the caller appends the snapshot registry line" (`:429-433`) — the pinned rule _a
  registry-visible file implies its ordinal-0 terminator was persisted_. As written it is the swap's last step; the
  composite window this design needs does not fit that shape — see **U3**.
- **The writers' ownership rule.** `wal_writers: []?*WalWriteFile` — one live writer per pair; `walOpenWrite` (`:394`)
  refuses a live pair with `error.WalOpen` and never creates (creation is elephant-side, `:369-371`);
  `acquireWalBattery` (`:348`) maps the battery once per index thread.
- **The elephant threads** (`src/elephant.zig`). The loop (`:23-47`) parks on CQEs and dispatches `CrossTaskMessageIdx`
  by copying the slot payload out and **releasing the slot at once** (`:29-32`) — the existing
  acquire→deliver→receiver-releases discipline. `handleTask` (`:50-65`) has no real task kinds yet. Elephants have no
  inbox and no session state; the config knob is `elephants: u16 = 1` (`src/config.zig:51`).
- **`CrossTaskSlots`** (`src/cross_task_slots.zig`). `acquire()` → free-list pop (`:83`); `at(i)` — an unsynchronized
  pointer the sender writes and the receiver reads (`:99`); `release(i)` (`:109`) pushes back FIFO. Stored values are
  not synchronized (`:7-15`); the slot id travels as `res` of an `MSG_RING` with
  `taskIdx = messages.CrossTaskMessageIdx` (`src/cross_task.zig:3-13`). `CrossTask` payloads are plain data **capped at
  16 bytes** (`src/cross_task.zig:56-68`); an fd already travels in one (`ServerSocket`, `:45-47`). Capacity
  `cross_task_slots = 4096` (`src/config.zig:63`).
- **The index thread** (`src/index.zig`). It hosts `data_sets = cfg.wal.hosts()` states (`:61`),
  `own_state = &data_sets[cfg.host_index]` (`:91`). The loop drains the CQ before the inbox (`:106-157`); the
  `CrossTaskMessageIdx` arm is **marked but not implemented** — reserved indices fall into `else` and are dropped
  (`:113-117`, `:118-126`). The startup seam is documented at `:84-90`: per pair, the snapshot loader sets `st.state`
  from the file-name tag, then `walOpenWrite` + `attachStream`, then replay via `walOpenRead`. The `faulted` flag
  (`:97, :127-137, :140-152`) is thread-level: any writer's fault denies the whole front intake while the control plane
  keeps flowing and shutdown still completes. The front is the `IndexInbox(FrontMessage)` (`:19-32`), batched
  (`index_inbox.zig:324`), hung after 32 idle iterations (`:279`).
- **The periodic-tick precedent.** Not the timing wheel (`src/timing_wheel.zig` is the session-retry wheel, wired to
  nothing yet): repeating ring ticks today are io_uring timeout ops — `ring.pushTicker(taskIdx, spec, count, flags)`, as
  the front arms its repeating 500 ms `ShutdownTickIdx` ticker (`src/front.zig:22, 221`) and main arms the init deadline
  (`src/main.zig:212, 277-278`). The timespec must outlive arming (`RingStuff.tick_spec`, `src/lifetime.zig:1226`).
- **The stop choreography.** Process stop is main's: `runShard` blocks signals, parks on signalfd (`src/main.zig:176`),
  and on a signal runs `shutdown()` — `ShutdownDemandIdx` to every front and elephant ring (indexes are stopped by their
  fronts, `:266-273`), a repeating tick, then a wait for `ShutdownDoneIdx` (`:282-306`). A thread-level fatal is the
  `std.process.exit(1)` idiom (`src/lifetime.zig:286`, `src/index.zig:158-161`). **No channel exists today for a worker
  thread to request a process stop** — see **U11**.
- **What does not exist anywhere yet**: snapshot/rollover/interval/size config fields (`src/config.zig` has none), the
  fixed file and its append/compaction (only the ordering contract is pinned in `walAdoptWrite`'s comments and tests,
  `src/lifetime.zig:2038-2098`), the composite writer, the ticker on index rings, and any snapshot task kind on the
  elephant.

## 3. Decisions carried in from the sibling threads

Restated as fact, because this design builds directly on them:

- **New WAL files are created only by elephant threads**, reached only through `CrossTaskSlots`; `walOpenWrite` opens an
  existing file and never creates (`wal-impl` §1.1, landed). The fd is the only thing that crosses to the index thread;
  the elephant never touches the battery or the live state (`wal-impl` §1.1, `state-snapshot` §1).
- **The fd travels as a ring message plus a slot context** — the `wal-impl` pad's own words: a message into the index
  thread's ring and a context in `CrossTaskSlots`, telling "a new snapshot was taken and you must switch to the new fd;
  it writes in both old and new WALs while the snapshot creation is in process. The switch logic WAL → overlay of two,
  old and new WALs → switch to new WAL exclusively is part of the controller." The pad deferred the whole mechanism —
  and even `walAdoptWrite` itself — to this design.
- **The registry ordering invariant survives**: the ordinal-0 terminator publish (an index-thread act, a battery write)
  must precede the registry append that makes the file visible to recovery (`wal-impl` §1.1/§3.4). In this procedure the
  adoption happens at fd receipt and the append happens later, elephant-side — the ordering holds by construction.
- **The clone discipline** (`sdks/state-snapshot.md`, `.mailbox/index-state/3.md`): the clone happens on the index
  thread between service-loop passes, on a quiescent, thread-local data set — no locks, no atomics; the elephant sees
  only the clone, never the live state; the arena owns the clone and the dump bytes; one `reset(.free_all)` right after
  the snapshot write and its `fdatasync`, then the job shell is destroyed; the dump is written with a plain buffered
  writer, not io_uring (`state-snapshot` §4.4); the snapshot file is created under its final name
  `snapshot.<host_idx>.<index_idx>.<state>` — 32 lowercase hex, no temporary names, no renames — with one `fdatasync` as
  the only snapshot-side barrier (`state-snapshot` §3.4); the `state` tag rides the name, never the dump, and the loader
  sets `st.state` from it before the first op (`state-snapshot` §5).
- **The write-failure stop** (`wal-impl` §3.5, landed): a negative `res` on a `wal_flush` (or WAL `file_read`) CQE
  faults the writer and denies the thread's front outright; the control plane — the reserved `taskIdx` traffic and
  cross-task slots — keeps flowing so shutdown choreography completes. Non-triggers: park-and-retry backpressure,
  `WalFull`/`RecordTooLarge` protocol refusals, `WalGap`, `WalOpen`. "Nothing is retried and nothing is repaired until
  the process restarts" (`src/wal.zig:1206-1212`). This design's freeze (**U4**) reuses exactly this machinery and adds
  the one revival case the source doc demands.

Where `sdks/state-snapshot.md` and this design disagree — the registry's actor, format, and file; the torn-line rule;
the one-procedure scope — the source doc is newer and this letter treats it as the authority, with the supersession
flagged explicitly in **U6** and **U7** rather than silently.

## 4. The choreography, read end to end

This is the prelude's proposed synthesis of `docs/SNAPSHOTS.md` over the landed seams. Every `**U**` marks a point where
the plan cannot proceed on assumption alone.

### 4.0 The tick

Each index thread arms a repeating ticker on its own ring — the `front.zig` timeout-op pattern, not a new thread and not
the timing wheel (**U9**) — with a period `T` from config (**U8**). The CQE arrives as a reserved `taskIdx` the index
loop must learn to dispatch (today reserved indices fall into `else` and are dropped, `src/index.zig:118-126`). On the
tick, the thread reads the sizes of all its hosted pairs' WAL writers — its own data set and every mirror data set it
hosts; these writers are thread-local, so the size is the writer's tracked extent, no syscalls, no network (**U8**).
Pairs above the threshold `S` become candidates; the largest wins. If a procedure is already in flight for this index,
the tick is ignored — the one-operation invariant (**U7**).

### 4.1 Dispatch: the WAL file

The thread picks an elephant — proposed plain round-robin over `cfg.elephants` (**U10**) — and opens the procedure's one
slot: `acquire()`, then write the task description. The 16-byte `CrossTask` cap forces the SDK's job-handle pattern
(`state-snapshot` §3.2): the slot payload carries a variant `{ job: usize }`, and the heap job is the "task description"
the doc speaks of — `host_idx`, `index_idx`, the tag, the phase, later the fd, the clone, the paths (**U7**). The job
fixes the tag at this moment: the pair's current `state_idx`, per the doc's naming invariant (**U2**). The slot id then
travels as `MSG_RING` into the elephant's ring.

The elephant's task is the cold-open idiom (`createLogFile`, `src/lifetime.zig:316`): create
`wal.<host_idx>.<index_idx>.<tag>` under its final name. It writes the fd back **into the same slot** — the doc's
"easiest done within the same slot", a payload like `{ job, fd }` well under the cap — and `MSG_RING`s the slot id back
to the index thread. The slot is **not** released by either side: the doc holds it "until the operation completes,
regardless of outcome", which is a new discipline for `CrossTaskSlots` (the existing receiver pattern releases at once,
`src/elephant.zig:29-32`); only the owning index thread releases, at the end (**U7**).

The doc's own "Че дальше?" — what happens next — is the handler:

### 4.2 The handler: clone, adopt, overlay, re-dispatch

One synchronous pass on the index thread; no other message is processed inside it, so nothing slips between its steps:

1. **Clone.** The pair `P`'s data set is cloned into the job's arena (`cloneIndexState`). If `P` is a mirror, this is a
   mirror clone — the doc's candidates explicitly include mirrors, superseding the index-state thread's "own data set
   only" discipline (**U1**, blocking).
2. **Adopt.** The new writer is taken over the fd: publish the ordinal-0 terminator (`last_state = tag`), open the
   writer, `head = tag`, attach to the thread's stream window. The old writer is **not** closed — this reshapes
   `walAdoptWrite`, whose landed contract closes the old writer first (**U3**, blocking). The terminator-before-append
   invariant is preserved: the append is still in the future, elephant-side.
3. **Overlay.** The pair's write interface becomes the composite: every event is written **to the new writer first, then
   to the old one** — the order is load-bearing, because the new WAL is the committed future and the old one is the
   pre-commit fallback; if the old side refuses, the event is already in the new file. Each writer chains independently
   (`floor == head` per writer), so the old file stays a complete history and the new file accumulates the post-clone
   tail from the tag. Two live writers on one pair need battery capacity for both during the window — the per-pair area
   must gain a second slot, alternating across rotations (**U3**). A refusal on the old side — including `WalFull`,
   which for the composite means the oversized file has finally run out — freezes the thread's front exactly as the
   landed `faulted` machinery does, while the control plane keeps flowing (**U4**).
4. **Re-dispatch.** The thread selects an elephant again — possibly a different one, the doc says so explicitly — and
   `MSG_RING`s the same slot id into its ring; the slot's job now carries the clone.

### 4.3 The dump elephant

Synchronous, elephant-shaped work: `dumpIndexState(&job.clone, &out)`, write `snapshot.<host_idx>.<index_idx>.<tag>`
under the final name, one `fdatasync`, then the single `arena.reset(.free_all)` and job-shell destroy — the SDK's
§3.3-3.5 discipline, verbatim. On success the elephant appends the line to the fixed file —

```json
{"host_idx":host_idx_0,"snapshot_path":"...","wal_path":"..."}
```

— with its `\n`, where `wal_path` names the **new** WAL (the pair the registry commits is snapshot + new WAL; the old
WAL becomes an unregistered orphan, retention's business). It may then compact: keep the last `N` lines per `host_idx`,
transactionally via write-new/fill/rename (**U6**). A line that does not parse is fatal: at startup, and at runtime the
compacting elephant makes a process-stop request (**U6**, **U11**). The elephant then throws "compaction complete" to
the index thread, retrying the delivery after a small spin-wait if the push refuses.

### 4.4 Completion: the swap

On the completion message the index thread drains and closes the old writer (`close` reclaims its buffers and ring
slots), collapses the composite to the single new writer, and releases the slot — the procedure is done, regardless of
how it went. If the thread was frozen on an old-side failure, it now attempts revival: the old writer is gone, the
surviving writer is healthy, the frozen window's events were written new-first, and recovery via the registry line is
complete — so the front reopens (**U4**). If the procedure failed instead, the unwind runs: no registry line (a failed
dump never gains one, `state-snapshot` §8), composite reverted to the old single writer, the new WAL orphaned, the slot
released — and if the thread was frozen when the failure arrived, the stop stands, because no swap is coming (**U5**).

### 4.5 The recovery contract

At startup an index thread reads its fixed file; for each hosted pair, the **last** line with that `host_idx` wins; it
names the snapshot and the WAL. The existing seam then applies (`src/index.zig:84-90`): load the snapshot, set
`st.state` from the file-name tag, `walOpenWrite` over the named WAL, replay through `walOpenRead`. An invalid line at
startup is fatal (**U6**). The full startup choreography stays with the startup material; this design pins the fixed
file's contract and the sequencing hand-off (**U12**).

## 5. Invariants

- One snapshot procedure per index thread at a time; ticker events during a procedure are ignored (**U7**).
- The slot is occupied for the whole procedure, regardless of outcome; only the owning index thread releases it
  (**U7**).
- The tag is fixed in the job (the slot's data) at dispatch; the WAL and the snapshot names derive from it (**U2**).
- A registry-visible WAL implies its ordinal-0 terminator was persisted (adoption precedes the append; carried from
  `wal-impl`).
- The elephant sees only the clone; the fd is the only thing that crosses threads; the battery is never touched by the
  elephant (carried from `wal-impl`/`state-snapshot`).
- The snapshot file is final-named, `fdatasync`'d once, and released with one arena reset before the reply (carried from
  `state-snapshot`).
- The composite writes new-first-then-old; the old side's refusal freezes the front, never the control plane (source
  doc, plus the landed §3.5 mapping).
- The registry's last line per `host_idx` is the pair's committed snapshot; an invalid line is fatal at startup and at
  runtime (source doc).
- The durability contract is unchanged: a record is durable when its flush completes; the overlay adds no barrier and
  removes none.

## 6. What is out of scope

- The consensus driver: what is written and when, and how mirror data sets receive their events (the freeze assumes

- Retention and orphan cleanup (when `delete` is called), and the post-restart epoch bump's sequencing — handed to this
  design by `wal-impl` §10 but absent from `docs/SNAPSHOTS.md`; proposed deferred (**U12**).
- The network transport, `pmem-migrate`, log rotation (`designs/LOG_ROTATION.md` is its own material).

## Open questions

- **U1 (blocking).** Mirrors as snapshot subjects. The doc's candidates are all pairs `(host_idx, index_idx_0)` — the
  own data set and every mirror this thread hosts — and the dump is "the state of the specific pair". But
  `.mailbox/index-state/3.md` and `sdks/state-snapshot.md` §1 say the clone path is the **own** data set only and
  "mirrors belong to their hosts' procedures". Mechanically nothing blocks a mirror clone: `cloneIndexState(st, arena)`
  copies any hosted `IndexState`, and the data sets are thread-local either way, so the clone is exactly as consistent
  for a mirror as for the own pair. Proposed: the snapshot procedure clones any pair the thread hosts, own or mirror;
  the "own data set only" discipline is superseded, and `designs/INDEX-STATE.md` §12 gains a one-line amendment when
  this thread promotes. Confirm or override.
- **U2 (blocking).** The tag's minting moment and the dispatch-to-clone window. The invariant pins both file names to
  "the `state_idx` at the moment the elephant was selected, fixed in the slot's data". Two elephant selections exist
  (the WAL file's, then the dump's), and the clone happens between them — at fd receipt, inside the handler. If the tag
  is minted at the first selection, the pair can advance between dispatch and fd receipt, and the clone then sits at a
  state `Y ≥ tag` while both names say `tag`: the loader would set `st.state = tag` below the content's real state, and
  the mint would re-issue `tag+1..Y` on top of sessions that already carry them. If the tag is minted at the second
  selection, it postdates the WAL file's creation — which needed it for its name. Proposed: mint the tag at the first
  dispatch (matching the invariant's letter) and **pin the pair** for the window: from dispatch until the handler
  installs the composite, the pair accepts no new events (other pairs and the whole front keep flowing; the window is
  one elephant round-trip — the empty-file task — not the dump). Then tag = clone state = the new WAL's base, with no
  chain jump and no mint collision. Alternative: no pin, two tags — the WAL named by the dispatch state (an opaque base
  tag; the reader's floor net anchors to it), the snapshot named by the clone's state — which violates the invariant's
  letter for one of the two names. Confirm the pin, or pick the two-tag reading.
- **U3 (blocking).** The composite supersedes close-first adoption. `wal-impl` §3.4 pinned adoption as "close the old
  writer first, then adopt", noting the per-pair battery "structurally excludes ever dual-writing one op into both
  files"; the landed `walAdoptWrite` closes the old writer (`src/lifetime.zig:444-448`). The source doc mandates the
  opposite for the window: both writers live, each event goes new-first-then-old. This design therefore reshapes the
  seam: `walAdoptWrite` becomes adopt-without-close (terminator publish, writer over the fd, `head = tag`,
  attach-stream), the old writer's `close` moves to the completion step, and the pair holds two live writers during the
  window. Two consequences to pin: (a) the `WalOpen` one-writer-per-pair guard holds **outside** a procedure and yields
  to the procedure's own second writer during the window (different tags, so no double-open of one file); (b) the
  per-pair battery area must host both writers' buffers for the window's duration — proposed: each pair's battery
  capacity doubles, the area splits into two slots of `buffers` buffers, a rotation and its successor use opposite
  slots, and the alternation continues across epochs (plain mode re-zeroes at adoption; PMEM headers keep their
  never-zeroed rule, the walk already classifies stale areas). Confirm the reshape, the guard exception, and the
  two-slot battery.
- **U4.** Freeze and revival. The landed stop is thread-level and terminal: any writer's flush fault denies the whole
  front, nothing is repaired until restart (`src/wal.zig:1206-1212`; `wal-impl` §3.5's non-trigger list includes
  `WalFull`). This design reuses the stop as the freeze and adds the one revival the doc demands. Proposed: during the
  window, the **old side's** refusal set freezes the front — its flush faults, and also `WalFull` (for the composite,
  the oversized old file hitting capacity is exactly the "cannot serve into the fallback" case; the freeze is brief
  because the swap is what retires the old file). Pure submission backpressure stays park-and-retry, a non-trigger. A
  fault on the **new** side is the ordinary terminal stop — no revival, per §3.5 unchanged. Revival, at the swap: the

## WAL adoption.

I mean a process when we replace a composite WAL interface we an entry to a new WAL file only.
