## 1. The pad's answers, restated as fact

- **U5 — the unwind is elephant-owned, and the registry rewrites itself.** Two subsections, two rules. First: a failure
  at any pre-swap step moves the pair back to the single old-file interface, sets a rollback status in the snapshot
  slot, and pushes a cleanup task to an elephant, which removes every file the failed procedure created and releases the
  slot. Second: the fixed file is no longer appended — every change is a full transactional rewrite (§2) — so the
  torn-line rungs of iteration 2's ladder are gone, and with them **U17**. A push that meets `RingFull` is never spun on
  by the index thread: it lands in a per-thread pending op and is retried by the loop (§5) — the pad's
  `snapshot_pending: ?CrossTask` sketch, reshaped slightly in §5, because what fails is the ring message, not the
  payload.
- **U13 — the chain anchors at the clone state; the names are markers.** Confirmed as proposed: the adopt publishes the
  ordinal-0 terminator with `last_state = Y` and head `Y` in both modes; the loader takes `st.state` from the walked
  head, never from a name; the registry line gains `"state":Y`, and plain mode takes both `st.state` and the reopened
  writer's head from it, ignoring the redundant key in PMEM mode. One refinement the empty-file walk forces: `walkPlain`
  of a zero-length file returns `head == tag` and publishes the terminator itself (`src/wal.zig:779-782`), so plain
  mode's rule is `head = max(walked head, the line's "state" key)` — an empty new file under a tag `X < Y` walks to `X`
  and is corrected to `Y`; a non-empty file walks past `Y` and the key is inert. The landed close-first tests asserting
  `last_state == tag` (`src/lifetime.zig:2081`, `:2097`) reshape with the seam.
- **U14 — the adoption is three header fields on a dedicated line, and it is computable.** The pad's fields supersede
  iteration 2's `adoption: i16` sketch: `BufferHeader` gains `snapshot_in_progress: u8`, `new_wal_buffer_idx: u16`,
  `target_state: u128`, published at the handler pass's first step — after the create reply, before the composite serves
  — and read at restart by two branches (§3). Iteration 2's placement analysis survives underneath: the fields are
  meaningless on the ring's own lines, because `writeHeader` rewrites whole lines (`src/wal.zig:889-907`) and the
  still-live old writer would erase a per-slot mark on its next lap — so they live on the per-area control line, which
  no writer touches.
- **U15 — an elephant says the last word on the slot, always.** The pad is right and iteration 2's "the index thread
  releases on failure" is superseded: every path — all rungs of §6 — ends with an elephant task performing the release;
  the index thread only acquires and sets statuses. The discipline, and the one new reply it needs, are §5.
- **U16 — the index directory holds everything.** Confirmed as proposed: `<wal root>/<indexDirName(index_idx)>/` hosts
  the pair's WAL files, the snapshots and the fixed file alike; `walPath`'s `dir` argument becomes the index directory
  at the three Controller call sites (`src/lifetime.zig:399`, `:480`, `:509`) plus the snapshot-path helper; leaf names
  keep their globally unique `wal.<host>.<index>.<state>` spelling. Nothing is deployed, so nothing migrates.
- **U17 — dissolved, not answered.** With the rewrite-always registry (§2) there is no append that can tear; the doc's
  invalid-line fatality survives untouched for what remains — corruption that is not a torn append. Iteration 2's
  proposed torn-tail exception is dropped, and so is the ladder's truncate-back rung.
- **U18 — no automatics.** The registry-lost arm leaves the startup choreography: a maintenance tool — a planned `mpy6a`
  toolchain QoL command — scans an index directory, groups `snapshot.*` and `wal.*` by equal tag, and per hosted pair
  adopts the max-tag complete pair. The design's remaining obligation is the property the tool consumes: equal tags pair
  a snapshot with its WAL, uniquely among live files.

## 2. The registry: rewrite on every change

The elephant remains the registry's actor and the commit point (U6's unobjected bundle, unchanged). On every change —
once per successful procedure; there is no other writer of this file:

1. Read the current fixed file. An unparseable line met here is the runtime fatality of the doc's letter: the
   stop-request (U11).
2. Keep the last `N` lines per hosted `(host_idx, index_idx)` — the compaction knob, now applied on every write rather
   than at a size threshold.
3. Add the new line: `{"host_idx":H,"snapshot_path":"...","wal_path":"...","state":Y}` (the `state` key is U13's).
4. Write the whole result to a **fixed** pending name — a constant, e.g. `<indexDir>/registry.pending`,
   `O_CREAT | O_TRUNC` — never a random temporary.
5. One `fdatasync` of the pending file: the commit point, before the completion message.
6. `rename(2)` over the fixed name.

Consequences, normative:

- **No bare appends exist.** The ~128 KiB threshold and iteration 2's ladder rung 7 (compaction failure) are retired:
  every write is the compaction, transactionally. Iteration 2's §3.3 compaction sentence is superseded by this section.
- **The pending name is never read by recovery.** A leftover pending from a crashed procedure is junk for retention; the
  next rewrite truncates it.
- **No directory fsync is demanded.** The `fdatasync` precedes the rename, and after any crash either the old content or
  the new content stands whole under the fixed name — a lost rename is an aborted migration, and an aborted migration is
  recovery-correct (the window's events live in the old pair too, §4). Losing the rename loses the _procedure_, never
  the _data_.
- A failed rewrite at any step is not a truncation emergency but an ordinary failure rung (§6, rung 6): the old file
  stands whole, the line never lands, the procedure aborts.

## 3. The adoption mark: three fields, one dedicated line

**Where the fields fit.** `BufferHeader` today is exactly 64 bytes with 28 bytes of pad: `data_len: u32` @0,
`flags: u32` @4, `buffer_seq: u64` @8, `crc_running: u32` @16, `_pad_align: u32` @20, `last_state: u128 align(8)` @24,
`_pad_tail: [24]u8` @40 (`src/wal.zig:57-79`, size asserted `:76`). The pad's fields fit without growing the line:
`snapshot_in_progress: u8` @20 and `new_wal_buffer_idx: u16` @22 into the `_pad_align` word,
`target_state: u128 align(8)` @40, using 16 of the 24 tail bytes. The layout is pinned by `wal-impl` §2 (`:55`); the
amendment is recorded for promotion.

**On the ring's own lines the fields are zeros, forever.** `writeHeader`'s whole-line assignment rewrites every field
including both pads (`src/wal.zig:897-905`) and keeps zeroing the adoption fields — "a stale lap cannot leak a field
into the new one" (`:887-888`) now covers adoption state too. This is a feature, not a gap: no ring line ever carries
migration state, so no lap can forge it.

**The mark lives on a dedicated per-area control line.** The battery today is purely rings — `pairs × stride`
(`src/wal.zig:261-263`), each area a data array then a header array (`:241-249`), sliced per pair at `i × stride`
(`src/lifetime.zig:341-342`), wired by `Area.init` (`src/wal.zig:351-359`) — and the per-area granule-rounding tail
cannot host the line: it is zero bytes whenever `buffers × 64` fills the granule exactly. The stride therefore grows by
one 64-byte line, after the header array: data array, header array, **control line**, alignment. `openBattery`'s
`WalBatteryTooSmall` (`:302`) grows with it, as does the temp area's total (iteration 2's §2.1). The temp rings keep the
same geometry — control line reserved, zeroed at the mint, unused — so the areas stay uniform; the swap's copy never
crosses a control line, because it copies the data and header arrays only.

**The dance, in the pad's order.**

1. At the handler pass's first step — after the create reply, before clone, adopt and composite — barrier-rewrite the
   pair area's control line with `snapshot_in_progress = 1`, `new_wal_buffer_idx = k`, `target_state = X` (CLWB+SFENCE,
   the `persistHeader` idiom, `src/wal.zig:925-931`; a plain store in plain mode). The earliest mark widens the guarded
   window: every crash from here to the swap lands in one of the two restart branches below, including clone and adopt
   failures — which is why the unwinds clear the mark (§6).
2. At the swap, after the bounded drain: the barriered `@memcpy` of ring `k`'s data and header arrays into the pair
   area.
3. The barrier-rewrite of the control line with `snapshot_in_progress = 0`.

**The restart rule — two branches, run per hosted pair, before any open of the pair.** Read the control line.
`snapshot_in_progress == 0`: the pair is ordinary. Otherwise the winning registry line decides, exactly as the pad wrote
it:

- The current pair **bears `target_state`** — the winning line names the migrating pair — the adoption is needed:
  re-copy ring `k` into the pair area (idempotent; the source is intact until the slot is reused), clear the line.
- The current pair **references another state** — the previous pair won — the migration aborted: clear the line, reclaim
  ring `k`, then check the abandoned pair for a surplus record and bring it home (§4).

Iteration 2's temp-ring identity tuple is dropped: the mark itself carries `k` and `X` on the pair's own area, startup
finds it by scanning the hosted pairs' control lines, and `new_wal_buffer_idx` is the only pointer anyone needs.

**The crash table, updated** (supersedes iteration 2's §2.2 table; only the mark column moved):

| crash at            | pair area | fixed file | mark    | restart                                              |
| ------------------- | --------- | ---------- | ------- | ---------------------------------------------------- |
| create reply → mark | old chain | old line   | 0       | the old pair, exactly as today                       |
| mark → line commit  | old chain | old line   | 1, k, X | abort: clear, reclaim, check the abandoned pair (§4) |
| line commit → copy  | old chain | new line   | 1, k, X | adoption: re-copy ring `k`, clear                    |
| mid-copy            | torn mix  | new line   | 1, k, X | adoption: re-copy (idempotent), clear                |
| copy → mark clear   | new chain | new line   | 1, k, X | adoption: re-copy (no-op data), clear                |
| post-swap           | new chain | new line   | 0       | the new pair                                         |

Copy-start still implies line-committed by construction — the elephant's `fdatasync` precedes the completion message,
which precedes the swap — so a torn pair area always exists after the new line and is always finished forward. Plain
mode's battery is DRAM (`src/config.zig:89-90`): the mark, the torn mix and the un-flushed tails die with the process,
the branches never fire, and the registry line alone decides — which §4 shows loses nothing durable.

## 4. The bring-tail: the abort branch's second act

- **Scope: PMEM only.** In plain mode the mark dies with the battery, so the branch cannot fire — and under **U19**'s
  proposed rule there is nothing durable to repair there anyway.
- **The check** reads the abandoned pair the way recovery reads any pair — the new file's flushed bytes merged with a
  ring chain by ordinal (the `beginRead` extent shape, `src/wal.zig:1670-1679`) — except the ring is the temp ring `k`
  the mark names, walked directly. Deliver every record at or past the old pair's walked head (`seek_then_read`,
  `:1303`, the read path's own floor filter). Normally the delivery is empty. The only possible gap is the inter-write
  cut: the composite writes new-first-then-old as two synchronous battery writes, so a power cut between them leaves
  exactly **one** record new-side but not old-side; everything earlier reached both rings, and everything the old ring
  holds is recovered by its own walk. The pad's singular "last record" is exact.
- **The bring:** flush the old writer's un-flushed tail first (the pad's "the start should flush unflushed first" — the
  startup-opened writer drives its filled buffers into the file, emptying the chain), then append the delivered record
  through the ordinary write path, then flush. Room is guaranteed twice over. Structurally: the record once fit ring
  `k`'s ordinary path — which keeps a buffer free (`src/wal.zig:974-975`) and may carry an un-flushed tail — so it fits
  the same-sized old ring emptied by the flush, a fortiori. And by the pad's two constraints, which make the room local
  and obvious:
  - **One record must not exceed `lba`** (`lba` is the buffer size and flush granularity, a u32 in `[512, 1 MiB]`,
    `src/config.zig:86-87`, `:554`). Note this is a real tightening: the WAL's structural cap today is the 1 MiB _block_
    (`framed > BLOCK_CONTENT` → `RecordTooLarge`, `src/wal.zig:961`; records legally span `lba`-sized buffers, `:27-33`)
    — where the constraint is enforced is **U20**.
  - **At least 4 buffers per file.** Today's validation floor is 2 (`src/config.zig:557`, "the ring needs a current and
    a free buffer"); the floor moves to 4, same site, same doc line (`:389`).
- `new_wal_buffer_idx: u16` bounds the slot pool: config validates `N ≤ 65535` alongside.

## 5. The slot, the pending op, and the elephant's last word

- **The slot payload becomes `{ status, job }`.** `CrossTaskSlots` is generalized over its payload (U15's confirmed
  shape); the snapshot pool's payload is a two-word struct honoring the pad's "sets a proper status in a slot (rollback
  or such)": `in-flight` at the tick, `rollback` when an unwind dispatches cleanup, cleared by the elephant's
  `release(k)`. The per-phase messages keep the ordinary `cross_slots` pool with `{ job }` payloads.
- **Every release is an elephant's.** Success: the final-close elephant (cursor pick 3) closes the old fd best effort
  and releases. Every failure rung: the cleanup elephant unlinks the procedure's files (best effort — `ENOENT` is fine;
  the create-failure rung has no file), closes any transferred fd, releases. The index thread never calls `release`.
  Verified against all of §6's rungs — the pad's rule holds with no exception left.
- **The last word needs a hearing.** The final-close and cleanup elephants reply one terminal `SnapshotDone` message,
  and the index thread's in-flight flag clears on it — the doc's one-operation invariant is enforced to the true end of
  the procedure, not to its last dispatch. The reply rides the elephant's spin-retry idiom (`src/elephant.zig:67-75`);
  the job carries the requesting ring's identity so the reply lands on the right thread's ring.
- **The pending op.** A failed index→elephant push never drops (the codebase rule for ring pushes) and never spins — the
  index thread serves pairs; a spin stalls the whole thread, which is why the dedicated threads can spin
  (`src/elephant.zig:71-73`, `src/index_inbox.zig:248-262`) and the index cannot. The push's slot is acquired and its
  payload written once; what refuses is the `MSG_RING`. So the pending op holds the acquired slot id and the target
  ring, and the loop retries the `MSG_RING` once per batch pass (a pass = one drained batch, ≤64 CQEs + ≤64 inbox tasks,
  `src/index_inbox.zig:324-336`) until it lands. One pending op per thread suffices — one procedure per index, and a
  procedure's pushes are sequential. It lives in the index loop's frame beside `faulted` (`src/index.zig:97`); no
  per-thread state struct exists today, and the author's split puts loop wiring in `index.zig`.
- **The tick skips** while the in-flight flag is set or the pending op is non-null — on top of iteration 2's §3.0
  conditions.
- **Message variants and the 16-byte cap.** The cap is a hard comptime assert (`src/cross_task.zig:67`), and the shapes
  must fit it. Verified by probe: `{ job: usize }` measures 16 and fits; `{ job: usize, fd: i32 }` measures **24 and
  breaks the assert**. So the fd reply carries the fd alone — and every other reply carries the job or a status alone;
  the one-procedure-per-index invariant makes the context unambiguous (the reply arrives on the requesting thread's own
  ring, and that thread has at most one live procedure). Requests (`SnapshotCreate`, `SnapshotDump`, `SnapshotCleanup`,
  `SnapshotClose`) carry `{ job }`. Exact variant naming is the staged plan's.
- **Reserved indices, corrected.** Iteration 2's U9 said `maxInt(u64)-2` and `-3` are free — they are not: `-2` is
  `CrossTaskMessageIdx` and `-3` is `IndexWakeupTaskIdx` (`src/index_inbox.zig:40`, `:44`). The only free index near the
  top is **`-7`**; the tick takes it. And the `CrossTaskMessageIdx` arm does not exist in the index drain today — such a
  CQE falls into `else` and is dropped with its slot never released (`src/index.zig:118-122`), a leak; implementing the
  arm (dispatching by payload variant) is part of this design, as U15 already said. It is also this design's first real
  sender in the elephant→index direction: the fd reply, the abandon message, the completion and the terminal reply all
  ride it.

## 6. The choreography and the failure ladder, reshaped

**The handler pass** (supersedes iteration 2's §3.2):

1. **Mark.** Publish the control line `(k, X)` — the create reply is in hand. No front message is processed inside the
   pass, so nothing slips between these steps.
2. **Clone.** The chosen pair into the job's arena; an allocation failure → unwind A.
3. **Adopt.** Mint ring `k`, open the writer over the transferred fd, publish the ordinal-0 terminator with
   `last_state = Y`, set head `Y` (U13).
4. **Composite.** Every event new-first-then-old; each writer chains independently (`floor == head` per side,
   `src/wal.zig:955`); completion per **U19**. A new-side fault is the ordinary terminal stop; an old-side refusal
   freezes the front (U4).
5. **Re-dispatch.** Cursor pick 2, `{ job }`; a refused push lands in the pending op and the pass ends — no spinning
   inside the pass, the window keeps serving.

**The swap and the final close** stand as iteration 2's §3.4, with two additions: the control line's clear is the
dance's step 3, and the final-close elephant releases the slot and replies `SnapshotDone`.

**The failure ladder** (supersedes iteration 2's §6; crash cases are uniformly §3's table):

0. **`snapshot_slots.acquire()` fails.** Not a failure: the tick ends. The limit is the design working.
1. **The create dispatch push is refused.** The pending op holds it; the thread keeps serving.
2. **The create fails.** The elephant replies failure. **Unwind A, markless** (the handler pass never ran): status
   `rollback`, dispatch the cleanup task — via the pending op if refused.
3. **The clone cannot be allocated.** **Unwind A**: clear the mark, status `rollback`, dispatch cleanup. Ring `k` holds
   at most a minted header array, referenced by nothing.
4. **The adopt cannot be allocated.** Memory-only, the clone's twin: **unwind A** (destroy the half-built writer object
   first).
5. **The dump fails.** The elephant replies failure after the arena reset. **Unwind B**.
6. **The registry rewrite fails at any step** (read, filter, write, `fdatasync`, rename). The elephant sends the pad's
   abandon message; **unwind B**. The old file stands whole; no truncate-back rung exists anymore (**U17**). If the read
   itself met an unparseable line, that is the runtime fatality — the stop-request (U11) — before any abandon.
7. **A reply push is refused.** The elephant spin-retries (`src/elephant.zig:67-75`).
8. **The swap.** Memory only — the drain, the copy, the mark clear — and cannot fail; its crash cases are §3's table.
9. **The final close fails.** `close(2)` on the old fd: warn, keep working (U3); release and reply `SnapshotDone`
   regardless. The procedure is done.
10. **The thread stops outside or during a window.** Ticks skip a stopped thread; U4's rules are unchanged — the
    procedure still completes on the control plane (the cleanup and final-close tasks are control-plane messages, and
    the pending op drains through the ordinary loop), old-side freeze revives at the swap, new-side fault and
    failed-while-frozen leave the stop standing.

**Unwind A** (index thread, pre-composite): destroy the writer object if the adopt got that far (memory only), clear the
control line if the mark was published, set the slot's status to `rollback`, dispatch the cleanup task. End state:
serving on the old pair; a truncated orphan under a tag no line references — retention's.

**Unwind B** (index thread, composite installed): revert to the old single writer; run the bounded drain of iteration
2's §2.2 (both writers quiet, stepped through the thread's ordinary dispatch — `close`'s `awaitFlush` drops foreign
completions, `src/wal.zig:1238-1253`, and stays unusable mid-service); close the new writer; clear the control line;
status `rollback`; dispatch the cleanup task. If the thread was frozen, the stop stands (U4). End state: serving on the
old pair, or frozen until restart. The snapshot and new WAL files, if they got that far, are unreferenced junk — exactly
the `state-snapshot` §3.5 rule.

**The cleanup elephant:** unlink the new WAL and the snapshot best effort, close any transferred fd,
`snapshot_slots.release(k)`, reply `SnapshotDone`.

## 7. Errata carried from this round's re-verification

- **`O_DIRECT` was a misread.** Iteration 2's U3 said writes are `O_DIRECT` with `RWF.DSYNC` in PMEM mode. Wrong:
  `wal-impl` rejects `O_DIRECT` outright (`designs/wal-impl.md:73`); both modes are deliberately buffered, and
  `src/wal.zig:538` is the PMEM-only `RWF.DSYNC` flag on each flush's explicit one-buffer `pwrite` (`:531-538`). U3's
  conclusion stands — a flush is an explicit completed `pwrite`, so `close(2)` manages only the OS file object's
  lifetime — but on the corrected rationale.
- **The terminal stop is `WalFaulted`, not `WalFull`.** `WalFull` is a protocol answer, a non-trigger
  (`src/wal.zig:1210-1212`); the fault is the negative-CQE path `flushResult → fault` (`:1196-1223`). U4's addition —
  old-side `WalFull` freezes the front during a window — remains this design's own rule on top of the landed set.
- **The "elephant never touches the battery" sentence** is pinned at `designs/wal-impl.md:56`;
  `src/lifetime.zig:369-371` pins the adjacent rule (creation belongs to elephants), `:252-253` the battery's thread
  ownership.
- **Line drift**, corrected throughout: `writeHeader` `src/wal.zig:889-907`; `closeBuffer` `:1096-1114`; `deliver`
  `:1487-1493`; `fault` `:1213-1223`; `close` `:1262-1276`. Two facts the letter records for the plan: the walk of an
  empty file publishes the ordinal-0 terminator itself (`:779-782`), and plain-mode close does not flush the live tail
  (`src/index.zig:273-276`) — the un-flushed tail is lost there by contract, which §4 relies on.

## 8. Invariants

- At most one procedure per index thread, enforced to the terminal `SnapshotDone`; at most `N` process-wide (the slot
  pool); a tick that hits either bound is skipped, not queued.
- The slot `k` is occupied for the whole procedure, regardless of outcome; an elephant releases it on every path — the
  final-close elephant on success, the cleanup elephant on failure. The index thread never releases.
- The tag is minted at the first dispatch, fixed in the job, carried by both names; the snapshot content may run ahead
  of it; the chain anchor is the clone state `Y`, persisted in the new WAL's ordinal-0 terminator and in the registry
  line's `"state"` key for plain mode.
- `snapshot_in_progress == 0` on every control line outside a procedure; the mark's publish precedes the composite,
  hence every registry line; copy-start implies line-committed.
- The registry is rewritten whole on every change: read, keep the last `N` per hosted pair, add, pending file,
  `fdatasync`, rename. The last line per `host_idx` is the pair's committed snapshot; an invalid line is fatal at
  startup and at runtime — and no append exists that could tear one.
- The pairing property: `snapshot.h.i.X` pairs with `wal.h.i.X`; equal tags, unique among live files (a same-tag retry
  truncates its own orphan). The maintenance tool consumes it; startup does not.
- The composite writes new-first-then-old and completes an event only when both sides' flushes have completed (**U19**,
  proposed).
- Records must not exceed `lba`; a file's ring holds at least 4 buffers (**U20**, proposed).
- A registry-visible file implies its ordinal-0 terminator was persisted (the publish moves to the adopt, still before
  the append).
- The elephant sees only the clone; the fd is the only thing that crosses threads; the battery is never touched by the
  elephant — the mint, the terminator and the control line are index-thread acts.
- The durability contract is unchanged: a record is durable when its flush completes; the overlay adds no barrier and
  removes none.

## Open questions

- **U19 (blocking).** The composite's completion rule. Every recovery argument since iteration 1 leans on an unpinned
  rule: which flush completes a front event during the window. The landed machinery pins only the negative side — a
  negative CQE faults a writer, a faulted writer denies the thread's whole front intake (`src/wal.zig:1196-1223`,
  `src/index.zig:127-136`) — and no client path exists yet to answer by itself: today flush CQEs die inside the index
  drain (`src/index.zig:127-137`), and the front acknowledges nothing. Proposed: an event is complete — durable,
  front-acknowledgeable — when **both** sides' flushes have completed. Either single-side rule loses durable events in
  one of the two outcomes: old-side-only would let a durable event be missing from the new file at the swap (plain
  mode's battery dies with the process, so the un-flushed new-side bytes are gone), new-side-only would let one be
  missing from the old file at an abort (plain mode again). AND-completion makes durable ⊆ both files always, which is
  exactly what §3's table and §4's repair scope assume. Consequence, folded into §4: in plain mode an aborted migration
  loses nothing durable, and the bring-tail is PMEM-only — it preserves the published-tail property (CLWB+SFENCE,
  `src/wal.zig:925-931`), not durability itself. The front/consensus material must honor the rule when its delivery
  channel lands. Confirm the rule.
