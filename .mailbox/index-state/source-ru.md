# Состояния индексов.

Индекс в данной [системе](../src/shard-arch-hld.md) это поток исполнения (т.е. код + метаданные) И
данные. У самих данных есть деление, на примере с фактором репликации 2 на хосте с индексом 1 в
рамках индекса под номером, скажем, 4:

| Данные индекса 4 хоста 0 | Данные собственного индекса 4 (хост 1) | Данные индекса 4 хоста 2 |
| ------------------------ | -------------------------------------- | ------------------------ |

Здесь, понятно, "поток исполнения" для `(host_idx = 0, index_idx = 4)` различаются на хосте 0 и на
хосте 1: операции на хосте 0 проводятся как реакции на действия клиентов и внутренние вычисляемые
состояния ("отправить сессию X на повтор через T секунд", "начать повтор/компенсацию первой сессии
из очереди повторов"). А на хосте 1 они проводятся как "хост 0 привез через свое соединение
предложение выполнить такую-то операцию". Т.е. на хосте 0 корпус "поток выполнения" это реакторы на
пользовательские запросы и на внутреннее состояние, а на хосте 1 - это обработка прилетающих
операций, их фильтрация на основе логики консенсуса и применение.

## Данные состояния.

Каждый индекс содержит в себе активные сессии (над которыми в данный момент ведется работа) И сессии
ожидающие своего повтора - которые упорядочены лексикографически по
`(время повтора: u64, session_id: u128)` - это 20 байт, 8 байт времени повтора и 16 байт
идентификатора сессии:

```zig
const IndexState = struct {
    /// Здесь мы отдельно держим число сессий, ибо HashMap из verztable этого не дает.
    sessions_count: u64,
    sessions: verztable.HashMap(u128, *SessionData),

    /// Здесь длина каждого не меньше 20 байт, в первых 20 байтах содержится (время повтора, session_id).
    /// В остальных байтах содержится сериализованное представление SessionData.
    replay_queue: std.PriorityQueue([]u8, void, lessThan),

    // ...
}
```

Где `std.PriorityQueue` взято как для первого этапа. Оно потом будет заменено на объект сильно
идентичным интерфейсом, но логика внутри будет уже композитной, где PriorityQueue (или ее расширение
под наши нужды) будет всего лишь одним поставщиков, плюс добавятся упорядоченные файлы.

Нужно отразить факт работы с файлами сразу: реализовав враппер над этим `std.PriorityQueue`, где
метод `peekOrNull` выглядит как

```zig
pub const PriorityQueue = struct {
    pub fn peek(self: *Self) !?[]u8
    // ...
}
```

Где `!` выражает проблемы при работе с накопителем.

### `SessionData`.

Оно представляет собой следующую структуру:

```zig
const SessionData = struct {
    const Self = @This();

    /// Сессия может быть восстановленной для повтора-компенсации.
    /// Работа с ней происходит в НОВОЙ сессии — т.к. это может происходить в после перевоза
    /// данных сессии в совершенно другой шард со своими настройками, в котором такого индекса
    /// тупо нет и фронт сойдет с ума определяя в какой индекс ему присунуть очередную порцию
    /// данных от клиента. В случае свежесозданной сессии это, конечно, дублирующее значение.
    original_id: u128,

    /// compensator, идентификатор сервиса который должен выполнять компенсации для этой сессии.
    /// Задается пользователем при создании сессии. Валидируется сервисом - он должен проверить,
    /// что такой компенсатор у него настроен. "Настройка" означает, что задан сетевой адрес
    /// компенсатора. Который реализует протокол компенсации-проигрывания.
    /// Выбрана строка вместо числа, ибо операция редкая, а по перфу на логировании именно получение
    /// названия по идентификатору было бы болью. Естественное требование - в однажды созданной мапе
    /// компенсаторов НЕЛЬЗЯ изменять названия ключей
    ///
    ///     compensators = fixed {
    ///         marker = bind { bind = "10.0.0.1", port = 20301 }
    ///         viper  = bind { bind = "10.0.0.2" port = 20301 }
    ///         hermes = bind { bind = "10.100.10.10" port = 20301 }
    ///     }
    ///
    /// Естественно, здесь надо иметь ввиду расширения до т.н. "cloud native", где мы помимо `bind`
    /// будем иметь что-то вроде `dns`, `grpc` (имея ввиду xDS или etcd для последнего и т.п.). Ну
    /// и даже больше, когда сам compensators будет рантайм-резолвером координат сервисов-компенсаторов.
    compensator: []const u8,

    /// Счетчик количества попыток компенсации. 0 для новых сессий. Неудача компенсации увеличивает
    /// его на 1.
    retry_count: u32,

    /// Сами данные сессии. Содержимое этого поля изменяется под действием операций
    ///
    /// - `Create`. Семантически было бы правильнее сделать Create безнагрузочным, но тогда мы
    ///    бы получили лишний хоп.
    /// - `Append`. Добавление нового куска данных.
    /// - `Overwrite`. Все содержимое data заменяется на новый кусок данных.
    ///
    /// Остальные операции влияют только на метаданные.
    data: []u8,
}
```

#### Кодировка `data`.

**`Create(payload: []u8)`**

Инициализирует новый `data` с содержимым

| `uvarint(paload.len)` | `payload...` |
| --------------------- | ------------ |

**`Append(payload: []u8)`**

Добавляет в хвост `data` новый кусок с точно таким же форматом кодировки

| `uvarint(paload.len)` | `payload...` |
| --------------------- | ------------ |

**`Overwrite(payload: []u8)`**

Заменяет все текущее содержимого буфера на присланный `payload` в уже хорошо известном формате

| `uvarint(paload.len)` | `payload...` |
| --------------------- | ------------ |

#### Кодировка `SessionData`.

| `original_id: LE(u128)` | `uvarint(compensator.len)` | `compensator...` | `retry_count: LE(u32)` | `uvarint(data.len)` | `data...` |
| ----------------------- | -------------------------- | ---------------- | ---------------------- | ------------------- | --------- |

Именно эти данные хранятся в данных

### Кодировка `PriorityQueue`.

Вообще, сам `PriorityQueue` предоставляет сброс. Но проблема в том, что он не упорядочен. А я
упоминал про "композитный minheap", который будет такой же очередью приоритета над набором
источников. Один из которых - тот же самый `PriorityQueue`, а другие - файлы. Которые файлы
получаются из этого `PriorityQueue`, если он стал слишком большим. Если мы будем сбрасывать его без
упорядочивания, нам придется грузить все это в память. А мы его сбросили за то что он слишком
большой )

Поэтому, сброс очереди приоритетов берется не встроенный, а как выхлоп итератора над клонированным
`PriorityQueue`, который дает упорядоченность. Так как я уже предложил представлять данные сессиии
компенсации как блоб данных

| `retry_time: LE(u64)` | `session_id: LE(u128)` | `uvarint(session_data.len)` | `session_data...` |

То мы итерируемся по этим данным и прямо в таком виде и скидываем:

| `uvarint(minheap.count())` | `minhit iteration...` |
