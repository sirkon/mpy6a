## 1. The source design, restated in English

### 1.1 Basics

One index, including a mirror index, owns exactly one WAL file (per `docs/consensus.md`). The
working surface is two interfaces:

```zig
pub const WALController = struct {
    /// Hand out a WAL-file writer positioned for writing from the given state.
    /// Returns a wrapper over the existing file or, if there is none, creates
    /// the file and returns the same wrapper over it.
    pub fn open(self: *Self, index_idx: u16, state: u128) !*WALFile {}

    /// Delete the file.
    pub fn delete(self: *Self, index_idx: u16, state: u128) !void {}

    /// Maybe more; decided as we go.
};

pub const WALFile = struct {
    /// Append to the tail of this data log.
    pub fn write(self: *Self, buf: []u8) !isize {}

    /// Reposition the read cursor onto the record matching the given system state.
    pub fn read_seek(self: *Self, state: u128) !void {}

    /// Reposition to read from the beginning.
    pub fn read_begin(self: *Self) !void {}

    /// Close the file(s) (a scheme with two descriptors underneath is allowed).
    pub fn close() !void {}
};
```

Persistence stance: feeding SSD vendors is a bad idea for too many reasons, so per-record `O_DIRECT`
flushes are rejected outright. Local persistence is not denied by that; the two schemes below
deliver it while staying buffered.

### 1.2 Simple buffered writer

Each `WALFile` owns a battery of buffers allocated sequentially; buffer length should be a multiple
of the storage device's LBA (a wish, not a law: it reduces write amplification).

Write path:

1. Check that free buffers (plus the remainder of the current one) can hold the record; if not, fail
   immediately.
2. If the current buffer has room, copy into it and return.
3. Otherwise: fill the current buffer to its end and push it onto the flush queue; take a free
   buffer and copy there; if that one fills too, queue it and repeat.

On the way out: if nothing is being written (a per-file flag) and the flush queue is non-empty, arm
an SQE for the queue head and set the flag.

The CQ handler catches write completions, reaches into the `WALFile` (it travels in the `RingSlots`
task context) and:

1. Returns the just-written buffer to the head of the free list (the head, for cache warmth).
2. If this file's flush queue is empty, clears the writing flag and continues its own work.
3. Otherwise keeps the flag, arms the next SQE from the queue, and likewise continues its own work.

Buffer flushes are **strictly sequential per file**: writing N+1 while N later fails would leave
unknown bytes past a hole at a known file length; the design stays strictly tied to file lengths.
Nothing prevents different files from flushing in parallel.

Close: if the last buffer is non-empty, pad it with zeros to its end and write it whole; a failed
partial write of that final unit is thereby ignored by replay.

### 1.3 NVDIMM writer

NVDIMM memory is kept out of the RAM pool and mapped via DAX. It is cut into blocks no shorter than
an LBA and a multiple of 64 bytes (the L1 cache line). One buffer is `header: u512` plus a data
area; the source table says the data area is one LBA.

Write path, order critically important:

1. Space check as above, plus one extra rule: ending up with the last available buffer filled
   exactly (and no free successor) is an error. The source calls this point fundamental.
2. Copy data into buffers; every write operation is accompanied by CLWB → SFENCE, pushing the lines
   out of the CPU cache into the NVDIMM for real.
3. When a buffer is filled exactly, grab the successor, write its header length as 0, clear its
   filled flag, again with CLWB → SFENCE.
4. Update the metadata of the current buffer; on buffers that stopped being current, set the
   completeness flag. CLWB → SFENCE.
5. Queue filled buffers like the simple scheme does.
6. The source then starts "7. Critically important: if our current buffer was filled to the end."
   and the sentence is cut off mid-thought. The intended invariant is reconstructed in 3.2 below and
   pinned as **U4**.

The flush itself must be O_DIRECT, bypassing the page cache. The battery is treated as a ring: each
file length (always a multiple of the buffer size, otherwise the tail is cropped) corresponds to a
definite ring slot. On readback, the file size identifies the slot holding the remaining data; the
filled flag says the next slot continues the file; and because "last available buffer filled
exactly" is an error, the walk can never step past the live tail into stale slots.

### 1.4 Data format

Data is written in 1 MiB blocks; the last 4 bytes of a block hold a CRC32C (Castagnoli) over the
block content. A record that does not fit the block remainder zero-pads it (zeros counted in the
hash) and starts in the next block. Length estimation must account for this padding.

## 2. What the combined algorithm must satisfy

- One `WALFile` implementation serves both hardware situations.
- The mode is a deployment property: `.pmem` (battery = DAX-mapped NVDIMM) or `.non_pmem` (battery =
  ordinary RAM).
- The non-PMEM mode runs the identical write/flush algorithm minus the barrier calls. The only other
  place the modes necessarily diverge is recovery, and that divergence is not a mode branch in the
  algorithm but the absence of a persistent medium: in non-PMEM mode there is no ring tail to
  consult, because the battery died with the process.

## 3. Combined algorithm (draft)

### 3.1 Common structure

- **Battery.** Each `WALFile` owns N fixed-size buffers. Allocation is sequential and the battery
  behaves as a ring: the slot covering logical position p is `(p / stride) mod N`, where `stride` is
  the whole buffer size. A slot may be reused only after its buffer's flush completion. Geometry is
  **U3**; N and the header fields are **U7**.
- **Buffer layout.** `header: u512` (exactly one 64-byte cache line) followed by the data area;
  everything 64-byte aligned, and the whole stride sized to satisfy O_DIRECT alignment (**U3**).
- **Mode.** Fixed per `WALController` at init. In PMEM mode the battery is carved from a
  process-wide NVDIMM pool, partitioned deterministically per open file so that a restart maps the
  same ring. In non-PMEM mode it is LBA-aligned heap allocations, so that an O_DIRECT flush
  requirement holds by construction (**U2**). Proposed: the mode is a comptime parameter of a
  generic `WALFile(Mode)`, so non-PMEM pays nothing for the barrier calls (folded into **U7**).
- **The barrier primitive**, the single point of divergence in the write path:

```zig
fn persist(self: *Self, range: []const u8) void {
    if (comptime !Self.mode_has_barriers) return;
    for (cacheLines(range)) |line| clwb(line);
    sfence();
}
```

### 3.2 Write path

`write(buf)`, in order:

1. **Capacity gate.** Space in free buffers plus the current remainder must fit `buf`. Additionally,
   a write that would exactly fill the last available buffer with no free successor is an error, in
   both modes. The source calls this rule fundamental for the ring walk; keeping it in non-PMEM is
   proposed in **U5**. On failure: immediate error return, nothing queued.
2. **Copy into the tail buffer.** In PMEM mode, persist the freshly written range before any header
   exposing it: data lines first, exposing header second. This is the crash-ordering requirement
   behind the source's "the order is critically important".
3. **Exact-fill transition**, repeated while data remains:
   1. Grab the successor, initialize its header: `data_len = 0`, filled flag cleared; persist it.
      This header is the recovery walk's terminator: it must be durable before the filled buffer's
      header is, otherwise a crash leaves a filled tail whose successor slot still shows stale
      headers from a previous ring lap and recovery replays garbage. This is the proposed completion
      of the truncated source step 7 (**U4**).
   2. Mark the filled buffer's header: full data length, filled flag set; persist.
   3. Push the filled buffer onto the per-file flush queue.
   4. Continue copying into the successor (back to step 2).
4. **Tail metadata.** Update the current buffer's `data_len`; set the completeness flag on buffers
   that stopped being current during this call; persist.
5. **Exit kick.** If the writing flag is clear and the flush queue is non-empty: register a
   `wal_flush` context in `RingSlots`, arm one SQE for the queue head, set the writing flag. Return.

### 3.3 Flush path (io_uring)

- One flush SQE in flight per file: strictly sequential, whole-buffer writes, opened O_DIRECT per
  **U2**, with the geometry of **U3**. The `WALFile` reference travels in the `TaskCtx` of the slot,
  alongside the existing variants in `src/slots.zig`.
- CQ handler on a `wal_flush` completion:
  1. Return the just-flushed buffer to the battery (front of the free order, for cache warmth).
  2. If the file's flush queue is empty: clear the writing flag.
  3. Otherwise: arm the next SQE from the queue head; the flag stays.
  4. Either way, continue the handler's own work; the WAL never blocks the ring loop.
- Rationale carried over unchanged: a hole between buffers N and N+1 would put unknown bytes into
  the file at a known length; strict per-file order keeps the file length a meaningful recovery
  cursor.

### 3.4 Close

Pad the tail buffer with zeros to its end (zeros counted in the running block CRC), update and
persist its header, enqueue it as the final unit, drain in-flight completions, close the
descriptor(s). What this does to the still-open 1 MiB block is **U6**; under the source's simple
rule, a torn flush of the final unit is ignored by replay.

### 3.5 Recovery

- **Common.** The file length L must be a multiple of the stride; if it is not, the tail is cropped
  (a torn final flush). The logical stream is the file bytes [0, L) plus, in PMEM mode, the ring
  tail.
- **PMEM.** Map the pool; the slot `(L / stride) mod N` holds the first unflushed unit. Walk
  forward: each filled header says the next slot continues the file; the first non-filled header
  ends the walk, its `data_len` bounding the tail. Termination is guaranteed by three invariants:
  the persisted terminator of 3.2 step 3 (**U4**), slot reuse only after flush completion, and the
  exact-fill error rule (**U5**).
- **Non-PMEM.** The battery was RAM and died with the process; the stream is the file alone.
  Everything past the last completed flush is lost; the acceptability of that is exactly **U1**.
- **Validation and replay.** Complete 1 MiB blocks are verified by their trailing CRC32C. The
  incomplete tail block has no stored checksum anywhere, so how it is validated is **U6**. Records
  are self-delimiting frames per `docs/consensus.md`; replay stops at the first torn record;
  `read_seek(state)` / `read_begin()` position the cursor.

### 3.6 Data format

Unchanged from the source: 1 MiB blocks over the logical stream, trailing 4-byte CRC32C (Castagnoli)
per block, zero-padding at block rollover counted in the hash. Padding at a rollover is bounded by
the size of the record that did not fit (it is exactly the remainder that record rejected), which is
the source's "account for it in length estimation" caveat. The running CRC of the open block is
maintained incrementally as buffers fill.

## 4. What actually differs between the modes

1. Battery backing: DAX-mapped NVDIMM ring vs LBA-aligned heap battery.
2. `persist()`: CLWB → SFENCE vs compiled-out no-op. Per the decision, this is the only algorithmic
   difference.
3. Recovery authority: the ring is a persistent tail in PMEM mode and scratch memory in non-PMEM
   mode, so recovery consults it only in PMEM mode. This follows from the hardware, not from a mode
   branch in the algorithm.

Everything else (API, battery discipline, write path, flush queue mechanics, sequentiality, close,
on-disk format) is one shared implementation.

## Open questions

- **U1 (blocking).** Durability contract of non-PMEM mode. In PMEM mode a record is durable once its
  bytes and the headers exposing them have passed CLWB → SFENCE, before any disk I/O. In non-PMEM
  mode the battery is ordinary RAM, so disk flush completion is the only candidate persistence
  point, and even a completed O_DIRECT flush lands in the device's volatile write cache unless a
  sync primitive is added. Proposed contract for non-PMEM deployments: durability covers process
  crash only; the un-flushed tail is lost on crash and is recovered from quorum mirrors via
  background sync; power-loss durability is exactly what PMEM mode exists for. Confirm, or name the
  stronger contract wanted (e.g. FORCE_UNIT_ACCESS per flush, or fsync/fdatasync at commit points)
  and the io_uring/zigring primitive to use for it.

- **U2.** Flush I/O mode. The source demands O_DIRECT for the NVDIMM scheme (bypass the page cache)
  but rejected O_DIRECT only for per-record flushes in the simple scheme (SSD wear). The combined
  scheme always flushes whole, aligned buffers, which the wear argument does not apply to. Proposed:
  O_DIRECT whole-buffer flushes in both modes, mode-independent open flags, battery buffers
  allocated LBA-aligned in memory so the requirement holds by construction. Confirm or override (the
  alternative, page-cache buffered writes in non-PMEM mode, also works under the proposed U1
  contract).

- **U3 (blocking).** Buffer geometry vs O_DIRECT alignment. The source table says the data area
  equals one LBA, and the buffer must be no shorter than an LBA and a multiple of 64 bytes. If LBA
  means a 4096-byte logical block, header (64 bytes) plus data (4096) gives a 4608-byte stride,
  which O_DIRECT rejects: file offsets and lengths must be multiples of the logical block. Candidate
  geometries: (a) 512-byte logical blocks, data 512, stride 1024, matches the source table
  literally, but 512-byte sectors cost write amplification on modern SSDs; (b) 4096-byte logical
  blocks, stride 8192, data 8128 (127 cache lines); (c) your intended numbers. Proposed: parametrize
  `stride = m × logical_block`, `data = stride − 64`, with m large enough that `data ≥ LBA`, and
  derive N from it. Pin the numbers.

- **U4 (blocking).** Source step 7 reads, in full: "7. Critically important: if our current buffer
  was filled to the end." and the sentence stops. Proposed completion, consistent with source steps
  3-5 and with the recovery walk: an exactly filled buffer must never be exposed (persisted header,
  flush queue) before its successor's header is initialized and persisted as a terminator
  (`data_len = 0`, filled flag cleared); otherwise a crash leaves a filled tail whose successor slot
  still carries stale headers from a previous ring lap, and recovery replays garbage. Equivalently,
  the write path ordering is: terminator first, filled flag second, queue third. Confirm, or supply
  the intended completion of the sentence.

- **U5.** The "exactly filled last available buffer is an error" rule. The source calls it
  fundamental: it guarantees the recovery walk always finds a terminator inside the ring. In
  non-PMEM mode recovery never walks the ring, so the rule is not needed for correctness there.
  Proposed: keep it in both modes anyway; one code path, one discipline, and the cost is a
  corner-case write error that clears once in-flight flushes drain. Confirm or override.

- **U6 (blocking).** The incomplete tail block. CRC32C is stored only in the last 4 bytes of a
  completed 1 MiB block, so the block that is open at crash time has no stored checksum anywhere.
  Taken literally, replay must discard the whole open block, losing up to 1 MiB of records even in
  PMEM mode, where the bytes themselves survive in the ring. The same incompleteness appears at
  clean close. Proposed: (a) each buffer header carries a running CRC32C of its block so far, so
  recovery validates the tail buffer-by-buffer and stops at the first torn record, while the
  megabyte CRC remains the bulk check for complete blocks; (b) close finalizes the open block by
  zero-padding to the block end and storing the CRC (at most one block of zeros). Confirm both,
  either, or override.

- **U7.** Header fields and battery parameters, proposed and to be pinned once U3 and U6 are
  settled: per-file battery of N buffers, N configurable; in PMEM mode the NVDIMM pool is
  partitioned into fixed-size rings assigned deterministically per open (index_idx, state) pair so a
  restart maps the same ring; header (one 64-byte cache line): `data_len: u32`, flags (filled,
  closed), `block_crc: u32` (if U6(a) is confirmed), `buffer_seq: u64` (logical position / stride,
  sanity check), remainder reserved; mode as a comptime parameter of a generic `WALFile(Mode)`
  (versus a runtime branch). Confirm, trim, or extend.
