## 1. U19 restated: the tmp side runs the ordinary O_DIRECT discipline

**Fact.** The temporary-side WALFile is a WAL file like any other while it lives: the ordinary
`wal_flush` machinery — whole-area `O_DIRECT` writes over the LBA-aligned RAM battery, sequential
per file — reused verbatim by the composite, with the stall inversion of iteration 7 §1 (a tmp-side
flush failure fails the procedure, never the log). The iteration-6 parenthetical "(no `O_DIRECT`
obligation either)" is dropped as loose talk: the tmp file becomes the log the moment the procedure
commits, and it is O_DIRECT-disciplined throughout, in both deployment modes. The end-durability
mechanics stand as proposed: at commit, the tmp WALFile's whole state is memcpy'd into the fixed
battery place and persisted there (CLWB → SFENCE sweep under PMEM; comptime no-op under non-PMEM,
the flush frontier carrying the ordinary contract); no fdatasync anywhere on the WAL path.

## 2. U20 restated, as amended by C1: no WAL without a pair

**Fact.** Every `(host, index)` pair is a **snapshot + WAL file pair, always**. A WAL file never
exists without its snapshot, and a snapshot always carries its WAL reference. At the very first
start of an index state, the process creates a **pair with no data** — an empty snapshot and an
empty WAL file — and refers to the just-created WAL file from the snapshot's side. The pairless
fragment of iteration 7 §6 therefore cannot arise as a _referenced_ artifact: an uncommitted pair is
junk, never a recovery source.

**Fact — selection by the registry, not by tag comparison.** With the registry (C1, §3 below) the
recovery rule of U17 is amended twice over: the source of truth for which files belong to a
`(host, index)` is the **last valid line for that pair in the registry log**, not the greatest-tag
comparison over directory contents. Chain replay with state-dedup (§6 of iteration 7) survives only
in the reduced form the rotation path needs — a referenced WAL may still have rotated-out
predecessors — but the _selection_ is a log lookup, never a name parse.

## 3. C1 worked through: the transactional registry log

**Restated.** The Critical replaces the in-progress directory and its fixed temp names with a
**fixed registry log file** holding one line per committed pair:

```
host_idx:index_idx:snapshot-path:wal-path\n
```

The **last line for a given `(host_idx, index_idx)`** names the snapshot and WAL for that index
state. New files are created **right under their final names** — no temporary names, no renames.
Once the snapshot is ready — and the WAL file exists because the same procedure created it — a new
line is appended to the registry; **that append finalizes the transaction**. A line that does not
match the format is a **HARD STOP**: the invalid line and every line after it are ignored — a torn
or corrupt tail simply means the transaction it would have committed is not committed.

**Restated — junk management.** Files that match the snapshot and WAL name formats (so their
`host_idx` and `index_idx` are computable) and **precede the oldest live reference of that pair in
the registry** are removed. The "remove anything not listed in the log" idea is rejected: candidate
(uncommitted) snapshot and WAL files are not listed and must be removed by this precedence rule, not
by listing.

**Restated — compaction.** At the end of the snapshot routine, the procedure checks whether the
registry log grew too large; if it did, compaction leaves **no more than N newest records per
host**. (Note: grouped by `host` here, not by `(host, index)` — see U23's neighbor below; both this
letter's restatements follow the Critical's text verbatim.)

### The revised choreography (iteration 7 §12, amended)

- **Index thread:** steps 1–4 as before (multishot review, bound check, CAS the flag, meta-state),
  except the armed io_uring operations create the **empty WAL file and the snapshot file under their
  final names directly** — `<wal_path>.<index_idx>.<host_idx>.<state>` and
  `snapshot.<host_idx>.<index_idx>.<state>` — with `<state>` the full-state tag minted at procedure
  start. No in-progress directory, no `wal.tmp`/`snapshot.tmp`, no rename steps.
- **Composite phase:** unchanged in substance — every `write()` fans out into the old WAL file and
  the new one; the new side is an ordinary O_DIRECT-disciplined WALFile over its final-name
  descriptor (§1).
- **Elephant thread:** (1) create the snapshot file (final name), dump the cloned state through the
  `Dumper` into the plain buffered writer, and **make the dump durable** — the durability mechanics
  are **U24**; (2) no WAL rename — the WAL file already lives under its final name; (3) no snapshot
  rename; (4) no symlink step (its fate is **U23**); (5) reply OK or failure carrying how far the
  procedure got.
- **Index thread, on OK:** wait out both sides' in-flight flush SQEs; drop the old side's flush
  queue (the old file is abandoned mid-stream — its flushed prefix a complete replayable unit, junk
  for retention); memcpy the new WALFile's whole state into the fixed battery place and persist it
  (§1); swap in the direct interface on the new descriptor; **append the registry line and commit
  it** (the commit durability is **U22**); clear the flag; arm io_uring to close the old descriptor,
  whose CQ completion ends the procedure.
- **Index thread, on failure:** swap back to the direct interface over the old file; the new pair
  (both final-named files, however far they got) is uncommitted junk under the registry rule —
  removal is the junk rule's business, not the failure path's; arm io_uring to close the new
  descriptor; its CQ completion ends the procedure.
- **Crash windows:** before the registry commit, the new pair is unreferenced — recovery takes the
  previous line, the pair is junk by precedence; after the commit, the pair is authoritative and the
  §1 tail contract covers a battery mid-memcpy. The registry append itself is atomic-or-torn under
  the hard-stop rule: a torn line is ignored, the transaction it names simply never happened.

## 4. U21 restated: superseded

**Fact.** The in-progress directory `<wal_path>.inprogress/` with `wal.tmp` / `snapshot.tmp` is
**dropped** — confirmed and then superseded by C1 in the same pad. No temp names exist anywhere in
the design; the one-procedure invariant now guards the final names themselves (a same-tag collision
is impossible while the flag is held).

## 5. What does not move

Iteration 7 §7 stands, with these amendments on top of its own:

- The §10/§11 non-PMEM-shape and migration bullets lose their `wal.tmp` wording: the temporary
  **surface** (a second WALFile over the not-yet-committed file) survives; the temporary **name**
  does not.
- The §9 tail-crop rule loses the "abandoned mid-stream" failure case: the old file's abandonment at
  commit still applies (unchanged), but the failure path now abandons a final-named uncommitted file
  instead of a renamed fragment.
- The `snapshot` symlink (U17: advisory only) is pending **U23**.
- The registry itself, its commit semantics, its hard-stop rule, and its compaction are new §12
  material; the wire note (iteration 7 §5, last paragraph) stands unchanged.

## Open questions

- **U22 (blocking).** The registry log file's path and its commit durability. Nothing pins where the
  registry lives or what makes the finalizing append durable. Proposed: the path is `<wal_path>.log`
  — a sibling of the WAL family under the same `wal_path` prefix, discoverable from config alone;
  the commit is `append the line, then fdatasync the registry file, then clear the flag` — the
  fdatasync is the transaction's commit point, so a power cut after the procedure reports success
  never loses the line (a cut before it loses only an uncommitted pair, which the hard-stop rule
  already treats as junk). The append itself needs no atomic-write machinery beyond the hard-stop
  rule: one line smaller than a page, written in a single `write(2)`, is append-atomic-or-torn in
  practice, and torn is safe. Confirm or override.

- **U23 (blocking).** The compaction grouping and the advisory symlink. The Critical says the
  compaction leaves "no more than N newest records **per host**", while iteration 7's retention
  (U16, confirmed) grouped by `(host, index)` — a host running several indexes would keep N records
  per host total, not N per index. Proposed: the registry compaction groups by `(host, index)` after
  all, matching the retention rule and the selection rule (the last line per pair is what recovery
  reads; older lines for the _same_ pair are dead weight, older lines for _other_ indexes under the
  same host are not). Separately, the `snapshot` advisory symlink of U17 is now redundant twice over
  — recovery reads the registry, and tooling can parse the registry instead. Proposed: drop the
  symlink entirely. Confirm or override (each independently).

- **U24 (non-blocking).** The snapshot file's own durability, restated for the registry world.
  Iteration 7 proposed the elephant fdatasync the snapshot after the dump, before its rename; the
  Critical removes the rename cushion but leaves the need: a power cut between the registry commit
  and the snapshot's writeback leaves a **torn authoritative snapshot**, and with the WAL pair
  starting at the snapshot's state there is no fallback pair to mask it — the pair _is_ the last
  line. Proposed: the elephant fdatasyncs the snapshot file once, after the dump, before replying OK
  — "we make it durable after it is done", applied to the one file written in a single synchronous
  go. The WAL side needs nothing: it is created empty and every subsequent write is O_DIRECT under
  §1. Confirm or override.
