## 1. U22 restated: the registry is `<wal_path>.log`, committed by fdatasync

**Fact.** The registry log file is `<wal_path>.log` — a sibling of the WAL family under the same `wal_path` prefix,
discoverable from config alone. Its commit is `append the line, then fdatasync the registry file, then clear the flag`:
the fdatasync is the transaction's commit point, so a power cut after the procedure reports success never loses the
line; a cut before it loses only an uncommitted pair, which the hard-stop rule already treats as junk. The append itself
needs no atomic-write machinery beyond the hard-stop rule: one line smaller than a page, written in a single `write(2)`,
is append-atomic-or-torn in practice, and torn is safe — the invalid line and everything after it are ignored.

## 2. U23 restated: compaction per (host, index); the symlink is dropped

**Fact.** The registry compaction leaves no more than N newest records **per `(host, index)`** — matching the retention
rule (U16, iteration 7 §2) and the selection rule — not per host total: older lines for the _same_ pair are dead weight,
older lines for _other_ indexes under the same host are not.

**Fact.** The `snapshot` advisory symlink of U17 is **dropped entirely**: with the registry, recovery never reads a
symlink, and tooling parses the registry. No symlink step exists anywhere in the choreography.

## 3. U24 restated: the elephant fdatasyncs the snapshot before the reply

**Fact.** The elephant fdatasyncs the snapshot file once, after the dump, **before replying OK** — and therefore before
the index thread's registry append. A power cut between the registry commit and the snapshot's writeback would otherwise
leave a torn authoritative snapshot with no fallback pair to mask it — the pair _is_ the last line. "We make it durable
after it is done," applied to the one file written in a single synchronous go. The WAL side needs nothing: it is created
empty and every subsequent write is O_DIRECT under §12.

# Critical

There should be a functionality to "forget" about the last record. It is typical for consensus protocol execution,
where, say, one participant may agree on a new change and others were a bit too late and consensus did not pass.

So, the next op should be written over an old failed event. Take a look at the original proposal and make changes:

```zig
pub const WALFile = struct {
    pub fn write(self: *Self, buf: []u8) !isize {}

    // The rest.
};
```

Approach with commits will work. And returning `isize` means nothing with commits.

```zig
pub const WALFile = struct {
    // Writes after commited data.
    pub fn write(self: *Self, buf: []u8) !void {}

    // Commit collected data.
    pub fn commit(self: *Self) !void {}

    // The rest.
};
```

Invariants:

- Uncommited changes must never be flushed.
