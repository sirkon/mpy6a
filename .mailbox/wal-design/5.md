## 1. U13 restated: the name carries the epoch id

**Decision.** The file of `(index_idx, host_idx)` under a given `state` is
`<wal_path>.<index_idx>.<host_idx>.<epoch>`, where `<epoch>` is the **epoch id slice** of `state`
(CONSENSUS-PLAN 2.5) — nothing else of `state` enters the name: the counter and index slices
position _within_ a file and would only explode the file count. `read_begin` / `read_seek(state)`
are scoped to the epoch of the opened file: a cursor never crosses a rotation boundary, because
`RequestLog` replay of a quorum sync asks for a state that lives in the current epoch, and any
cross-epoch need arrives with the compaction/snapshot subject.

The pad adds one clause beyond the confirmation, restated as fact: **the epoch bump is bound to a
state index threshold.** Rotation (the switch to a fresh `<epoch>` file) is triggered by the epoch's
`index` slice reaching a configured bound; the new file opens at a fresh index base, so the u64
counter never approaches its ceiling within one epoch — the theoretical wrap-around gap is closed by
construction, not by luck. Which bound, and whether it is the only rotation trigger, is the
compaction/snapshot subject; this design pins only the naming, the open/positioning choreography,
and the requirement that a rotated-out file is a complete, replayable unit (the §7 close runs at
rotation exactly as at shutdown).

## 2. U14 restated: LBA change goes through `lba-migrate`, not through a restart

**Decision.** The crop-and-document proposal of iteration 4 is **rejected**. A configured LBA change
across a restart is not a supported state at all — the open-time geometry check (iteration 4, §1)
rejects an existing file whose stream is not a multiple of the configured LBA, and the config knob
means something now, so the check is enforced, not waived. LBA is deployment-tied, and the supported
path from one LBA to another is the offline toolchain command:

```shell
mpy6a lba-migrate -f 4096 -t 16384
```

Ripple effects, worked through:

- **Scope.** The command exists for **PMEM mode** deployments — the pool partition
  (`area_stride = N × (LBA + 64)` rounded up to LBA and page) and the control-array offset
  (`N × LBA`) are LBA-shaped persistent layout, so an LBA change is a re-lay of that layout, not a
  recompile-and-restart. Non-PMEM deployments change LBA by draining (`§7` close), removing the
  files, and starting fresh: there, the battery is RAM and dies with the process, so nothing
  persistent is LBA-shaped except the file-length multiple, which a fresh start satisfies trivially.
- **Shape of the rebuild.** Offline: quiesce the deployment, then per file — open under the old LBA,
  scan the valid stream (§8), and re-emit it under the new LBA: pad the open tail to the new
  block/LBA geometry, re-flush every area so the file length is a multiple of the new LBA, re-lay
  the PMEM pool with the new `area_stride`, and rewrite every control line (data areas are
  `data_area(p) = battery_base + p × LBA`, so every `buffer_seq`, every `crc_running` carrying
  position, and the terminator positions move). The record and block formats are LBA-independent
  (blocks are 1 MiB over the logical stream; a record that does not fit the open block's remainder
  zero-pads it), so the re-emit is a re-chunk of the same byte stream, verified by the same CRC32Cs
  — a migration that fails its own verification aborts without consuming the old files.
- **What the tool is not.** It is not part of the WAL library and not reachable from the consensus
  tract; it is a toolchain command over closed files, specified here only because this design is
  what makes the LBA a persistent-layout parameter and therefore owns the migration contract.

# Critical.

## Snapshots rethought.

I want to move snapshotting out of consensus chain altogether (which `epoch` in the WAL file name
implicitly implies). For this, we should use full `state` value WAL file names and its only
semantics will be "just some unique tag".

### Prerequisites.

What is the **index**. The index is an execution entity, which:

- Holds its own "index state" it directly controls (index state of the current host).
- Provides timing wheel machinery for its OWN index state.
- Has states of mirror indexes, which it only applies commands it was given through cluster
  connections. They have no timing wheel machinery over them, unlike the own one.
- Anything else, which we don't mind in here.

The "index state" holds active sessions, sessions to replay/compensate ordered by the said
replay/compensation order, etc. We don't mind them for now. Let's just say we can dump all its
internal data via its public interface, something like:

```zig
const IndexState = struct {
    // ...

    pub fn clone(self: *Self, dst_allocator: *std.heap.Arena) !*Self {}

    // You better to use it on a cloned entity, really...
    pub fn dumper(self: *Self) !IndexState.Dumper {}

    const Dumper = struct {
        // Is meant to be used synchronously, as the async logic via io_uring will be TOO complicated
        // without a good reason. We can just use a larger placeholder buffer, something like 512Kib or
        // more to make io_uring meaningless for the task.
        pub fn dump(self: *Self, placeholder: []u8, dst: std.Io.Writer) !void {}
    };
};
```

We also have "elephants". These are execution entities running their own threads giving orders
through cross tasks slots and io_uring messages containing references to these slots and whose only
purpose is to execute heavy blocking logic. It is out case exactly. So, let's start.

Our `WALController` marks an area for the "battery". Let's say we also have a set of buffers for a
temporary WAL file:

```zig
pub const WALController = struct {
    pub fn open(...) ... // Whatever. It creates WALFile pointing into a fixed place for (host_idx, index_idx) WAL file.

    // It returns a wrapper for the given RW desciptor and a buffer for temporary WAL files.
    pub fn tmp(self: *Self, tmp_fd: std.posix.fd_t) *WALFile {}
};
```

### A high level idea.

Invariant: no more than a single snapshot at once. There must not be parallel snapshot creations.

A certain index decides some of its index states (own or mirrored) WAL grew too large and compaction
is needed.

1. Each index thread has a multishot timer for "snapshotting procedures" ticking, say, once per 1
   minute or 10 minutes or whatever. Index thread reviews its data once it hits.
2. It may decide some of its index states' WAL grew too large and deserves a snapshot.
3. It tries to set "snapshot in process" atomically accessible boolean value into false -> true (or
   use integer for the task if it is easer, it doesn't matter).
4. Once the flag was raised:
   1. Set some own meta-state accordingly, something like
      ```zig
      snapshot_in_progress: ?struct {
          host_idx: u8,
          state: *IndexState,
          current_wal_len: usize,
      },
      ```
   2. Set up io_uring task to create a temporary WAL file (empty) in the "in-progress" directory.
      The file name better be fixed - it is safe since we only have at most 1 snapshot process.
5. Once it got a CQ reply with the FD (and that `snapshot_in_progress` must not be null at the
   moment), it:
   1. Clones the given state.
   2. Creates a composite WAL file for this particular state: it writes into the old one, then into
      the new ("temporary") one. An error on writing into the temporary means snapshotting is
      failed. A situation when the temporary file writes are stalled also means snapshotting is
      failed.
   3. Sends "create snapshot" task to an elephant. Elephant is round robin choosen I guess.
   4. Keep working.

Meanwhile, the elephant gets its task and do that syncrhonous logic:

1. Create snapshot file in "in-progress" directory. Better to have some fixed name.
2. Rename temporary WAL file into the valid name.
3. Rename snapshot into `snapshot.host.index.state`.
4. Replace a link `snapshot -> snapshot.host.index.old-state` with the new name.
5. Sends OK back to the index.

When the index got the elephant's Ok notification, it replaces composite WAL file interface with the
direct WAL file reference AND mempcy temporary buffer into the fixed place for the given (host,
index). Close the old file via the io_uring - once it catches the CQ of the close the snapshotting
is finished.

If the index got failure notification, it switches back to the direct WAL file interface pointing
the old file and close a temporary WAL file via the io_uring. Just like the Ok case, that last CQE
will finish a snapshotting procedure.

### Junk management.

Don't touch "in-progress" directory content. It only has fixed files and this is constant junk
overhead.

We have "state" part in files. We can group WAL and Snapshot files (separately) by host, order them
by state and leave only N latest ones, removing anything else.
