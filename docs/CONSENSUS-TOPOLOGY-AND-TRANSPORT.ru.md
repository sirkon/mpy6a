# Топология и транспорт консенсуса.

В этом материале будет описана связь и передача данных в консенсусе.

## Топология.

Индекс с номером i на хосте `host_idx` стремится подключиться к другим индексам с таким же номером на всех прочих
хостах.

Правило:

- Хост с индексом `host_idx_0` подключается к хосту с индексом `host_idx_1` тогда и только тогда, когда
  `host_idx_0 < host_idx_1`.
- Хост с большим индексом использует reply-канал подключения от установленного от меньшего к большему.

Таким образом, у нас суммарно будет иметься `index_count * (replication_factor - 1)` сокетов обслуживающих догон и
консенсус в рамках полностью функционального кластера.

### Установление подключения.

После того, как другой хост подключился, он представляется, указывая индекс своего хоста, индекс своего потока и свою
версию (последняя для валидации). Если такое подключение уже зарегистрировано за другим сокетом, то текущее подключение
должно быть:

- Заменено на новое.
- Само существовавшее подключение должно быть закрыто (`pushClose` в кольце индекса).

Обработку таких подключений проводят фронт-потоки, которые затем пересылают сокет установленного подключения в нужный
индекс-поток.

Подключения от меньшего большему производятся самими индексами.

## Транспортный протокол.

Транспортный протокол обслуживает как проводку операций консенсуса, так и передачу данных для "догоняния" убежавшего
состояния, передачу снапшотов и т.д.

Общий вид пакета:

| `seq_id: u16` | `vector_clock_frame: (u8, u128)` | `op_code: u8` | `op_payload: bytes` | `commit_envelope: (u128, uvarint, bytes)` |
| ------------- | -------------------------------- | ------------- | ------------------- | ----------------------------------------- |

Здесь `seq_id` - циклически изменяющиеся числа 0, 1, 2, ..., 65535, 0, 1, ... для буфера переупорядочивания на
принимающей стороне. Это связано с тем, что мы не хотим связывать команды отправки и кидаем их чисто асинхронно. А в
рамках io_uring нет гарантии сохранения хронологического порядка: даже если операция A записи в данный сокет была
запихнута в данное SQ ДО B, которое пишет в тот же сокет, то сама ОС может отправить B раньше A.

`vector_clock_frame` это пара (`host_idx`, `state_of_host_idx`), где каждый хост циклически передает свое известное
состояние для всех `host_idx` по-одному, последовательно. Это сделано для поддержкания работоспособности кластера даже в
условиях отсутствующей прямой связи между какими-то хостами, когда другие хосты могут играть роль посредников.

`op_code` - код операции. Содержит в себе как операции для проводки консенсуса, так и запросы на транспорт отсутсвующих
данных. Что-то вроде "передай мне снапшот за такое состоние", "передай данные для host_idx_0 начиная с состояния
state_idx" и т.п. Полный список операций будет установлен позднее.

`op_payload` - нагрузка. Кодировка будет установлена позднее.

`commit_envelope` - статус подтверждения операций. Передается как
`(no_of_decisions: uvarint, start_state_idx: u128, decisions: bitmap)`. Где в `no_of_decisions` закодировано число
операций с известным статусом подтверждения, `start_state_idx` - первое состояние из списка, `decisions` - битмапа с 1
для "подтверждено" и 0 для "не подтверждено". У нас по самому алгоритму работы порядок подтверждений строго фиксирован
благодаря механике функционирования, так что это необходимый и достаточный формат одновременно. Число исходов специально
вынесено перед прочими вариантами, чтобы ограничиваться простым 0 в случает отсутствия новых данных по подтверждениям.

## Подробности реализации.

Data plane (ресурсы) остается в lifetime.Controller

Control plane (логика) реализовывается в новом файле ./src/consensus.zig. Что-то может поменяться в уже существующих
файлах (изменение типов данных для CrossTaskSlots, например и т.п.)
