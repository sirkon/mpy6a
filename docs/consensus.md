# Протокол консенсуса.

Необходимо ознакомление с [архитектурой](shard-arch-concept.md).

## Лидерство.

Лидерство привязано к сессии. Индекс хоста, начавший вести сессию, становится ее лидером, что выражается
в индексе сессии.

В случае, если потеряна связь с хостом лидирующего индекса лидерство неким образом перехватывается одним
из этих зеркальных индексов. Для попытки перехвата лидерства по индексу необходимо, чтобы сессия
считалась находящейся в актуальном состоянии и чтобы подключение к зеркальному индексу на хосте
с лидирующим индексом продолжительное время не проводило никаких операций в течении оговоренного времени (в секундах).

## Подтверждение операций.

Для подтверждения успешности операции клиенту лидер должен получить одобрение кворумного числа
зеркальных индексов с других хостов шарда.

В случае, если отвалился лидирующий индекс, все имеющиеся записи считаются подтвержденными - это требование
домена, так как работа с WAL имеет следующий вид:

1. Декларация намерения "выполнить `X(args)`".
2. Выполнение `X(args)`.

Само такое взаимодействие уже подтверждает факт, что все необходимое для выполнения `X` готово. Нам очень желательно
сохранить информацию об этом, чтобы уменьшить сложность выполнения компенсации.

**Ответ на запрос подтверждения**

```
data CommitResponse
   = Commited
   | Outdated SequenceID   -- Диагностирует попытку продавить решение по сессии, которая отстала от "мейнстрима"
```

## Фоновая синхронизация.

Каждый индекс регулярно обменивается с зеркальными векторными часами состояний всех имеющихся у него индексов.
В случае, если зеркальные индексы присылают данному состояние некоего третьего большее чем имеется локально, данный
индекс запрашивает недостающие данные третьего индекса у индекса с самым последним состоянием. Так же эта информация
должна служить критерием для принятия решения о захвате лидерства по сессии - если данный индекс отстает в образе
индекса-лидера, он не пытается выполнять захват.

## Формальное описание.

### Команды.

Основная часть протокола закрывающая функциональность WAL.

> Во всех операциях всегда присутствует индекс хоста лидирующего данный лог: идентификатор хоста + эпоха хоста + индекс
> в рамках эпохи.

```
type HostStateIdx = (idx: u8, epoch_idx: u56, index: u64)

// описание представления другого хоста. По такой структуре на хост.
struct MirrorState:
   expected_epoch_id: u56
   current_idx:       u128
   active_map:        EpochSessions
   isolated_fifo:     LinkedList[EpochSessions]
   deferred_hooks:    Array[LogStateHook]
```

| Команда с форматом                         | Описание                                                                                                                                                                                                                      |
|--------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `Create(replayClassID u64, data raw)`      | Создать сессию с проигрыванием в ручке с данным идентификатором и записать первые данные. Можно было бы создавать отдельно и потом Append, но это лишний хоп. Очень часто взаимодействие будет выглядеть как Create -> Close. |
| `Append(sessionID: u128, data raw)`        | Добавить данные в сессию.                                                                                                                                                                                                     |
| `Overwrite(sessionID: u128, data raw)`     | Заменить накопленные в сессии пакеты на данный пакет.                                                                                                                                                                         |
| `Close(sessionID: u128)`                   | Удалить все накопленные данные сессии                                                                                                                                                                                         |
| `RestartIn(sessionID: u128, seconds: u16)` | Отправить сессию на повтор через seconds секунд.                                                                                                                                                                              |
| `Restart(minHostStateIdx: u128)`           | Запустить первую в списке для данного хоста сессию на повтор при условии, что локальное состояние для этого хоста находится на уровне не ниже данного.                                                                        |

Часть протокола необходимая для корректного функционирования системы.

| Команда с форматом                                                  | Описание                                                                                                                                                                               |
|---------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `Isolate(hostStateIdx: u128)`                                       | Изолировать накопленное состояние хоста для данного его состояния. Поднять ожидаемую эпоху для этого хоста.                                                                            |
| `Capture(hostStateIdx: u128, offset: u64, head: u16, seconds: u16)` | Отправить head сессий из захваченного состояния хоста на повтор через seconds секунд. offset здесь дает контроль, что хост делающий захват понимает, сколько оттуда уже было откушено. |

### Алгоритм и инварианты функционирования.

- Каждый хост ведет собственные операции в своем логе и пишет операции от других хостов в логи закрепленные за этими
  хостами. Это разные файлы. Один хост - один лог.
- По достижению актуального состояния хост должен представиться как (host_idx, cur_host_epoch_idx) и получить одобрение
  на это у кластера. Если предоставленное значение больше ожидаемого на конкретном хосте, он должен воздержаться от
  решения. Совпадает с ожиданием - одобрено.
- Значение `cur_host_epoch_idx` ВЫЧИСЛЯЕТСЯ после вычитки своего лога при рестарте. Это значение должно быть равно
  строго "последний `cur_host_epoch_idx` из лога" и +1 к нему.
- Решения об операции принимаются строго последовательно: одна операция - один квант времени. Следующая - следующий
  квант.
- Монотонность барьера эпохи. Для любого запроса или команды от `host_idx`, содержащей `incoming_host_idx = hidx`, хост
  производит валидацию `cmp(hidx.epoch_idx, hostStates[hidx.idx].expected_epoch_id)`. Если значение меньше 0, шлется
  жесткий отлуп. Если равно 0 - смотрим что там в команде, можно ли применять. Если больше нуля - воздерживаемся.
- Изоляция. Команда `Isolate(hostStateIdx)` содержит в себе точную логическую границу лога отлетевшего хоста (X).
    - Хост-инициатор пишет Isolate в свой собственный лог и реплицирует ее зеркалам.
    - При получении и обработке этой команды из лога инициатора, текущий хост проверяет локальный указатель лога
      репликации самого изолируемого хоста.
    - Если лог этого хоста на данном хосте не достиг точки X, хост обязан отложить фактическую изоляцию сессий. В
      `deferred_hooks` помещается задача "изолировать по достижению X" и список deferred_hooks дергается при каждом
      добавлении новой записи в лог-реплику того хоста.
    - Выталкивание пучка сессий в isolated_fifo происходит строго в момент, когда `current_idx` реплики состояния
      достигает X.
- Инвариант FIFO-Очереди Изолированных Пучков по Зеркалам. Так как на каждом узле для каждого зеркального индекса
  выделен свой собственный isolated_fifo, а лог конкретного отлетевшего хоста продвигается строго последовательно, хуки
  отложенных задач для этого хоста гарантированно стреляют в правильном хронологическом порядке. Элементы внутри
  isolated_fifo для конкретного host_id автоматически выстраиваются в идеальный FIFO-порядок без необходимости сквозной
  сортировки:
- Инвариант Линеаризуемости Захвата (Capture из Головы зеркального списка):Операция Capture (hostStateIdx, offset, head,
  seconds) применяется исключительно к элементу, находящемуся в голове (head) очереди isolated_fifo для конкретного
  host_id.Значение offset в команде сверяется со счетчиком уже обработанных сессий текущего контекста головы. Если
  offset не совпадает, зеркало возвращает Outdated SequenceID. Если кворум запрашивает Capture для hostStateIdx, который
  на данном узле еще не перешел в isolated_fifo (все еще ждет докрутки лога под хуком отложенных задач), операция жестко
  отвергается с ошибкой EpochNotIsolatedYet. Инициатор обязан повторить попытку позже.
- Переподключившийся после рестарта host_idx с бампнутой эпохой вычисляет свои прошлые сессии как бесхозные (так как их
  эпоха меньше его текущей рабочей пары). Он имеет право записать в свой лог команду Isolate для самого себя из прошлой
  эпохи, дождаться выполнения локального хука и запустить Capture для своего собственного host_idx, перекладывая данные
  из локального isolated_fifo в текущую active_map без физической передачи сессий по сети.
