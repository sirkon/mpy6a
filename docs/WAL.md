# WAL-файлы, работа с ними, формат данных.

> Реализация: план и принятые решения — в [`designs/wal-impl.md`](../designs/wal-impl.md),
> код — в `src/wal.zig` (формат, батарея, писалка, читалка), `src/config.zig`
> (блок `wal`), `src/lifetime.zig` (ресурсы и привязка к ring) и `src/index.zig`
> (диспетчеризация завершений).

Нужно ознакомиься с sdks/state-snapshot.md и c docs/shard-arch-hld.md, чтобы понимать о чем идет речь.

## Основы.

Как уже было сказано, один индекс, в т.ч. зеркальный индекс, имеет свой собственный WAL-файл. Под индексом понимается
тройка `(host_idx, index_idx, self_index_state)`. Внимание, здесь нет места данным состояниям данных индексов с других
хостов. Это - ответственность индекса как потока исполнения. Данные же индекса рассматриваются только те, которыми он
управляет сам, а не посредством операций пропущенных через сито консенсуса.

```zig
// Это тот самый lifetime.Controller из ./src/lifetime.zig
pub const Controller = struct {
    /// Выдать писалку в WAL-файл рассчитанную на запись начиная с данного индекса.
    /// Она возвращает враппер файла поверх существующего файла, либо, если файла нет,
    /// создает такой файл и возвращает тот же самый враппер над ним.
    pub fn walOpenWrite(self: *Self, host_idx: u8, index_idx: u16, state: u128) !*WalWriteFile {}

    pub fn walOpenRead(self: *Self, host_idx: u8, index_idx: u16, state: u128) !*WalReadFile {}

    /// Удалить файл.
    pub fn delete(self: *Self, host_idx: u8, index_idx: u16, state: u128) !void {}

    /// Мож что-то еще, смотрим в процессе.
};

pub const WalWriteFile = struct {
    /// Запись в конец данного блока данных.
    pub fn write(self: *Self, buf: []u8) !isize {}

    /// Закрытие файла/файлов.
    pub fn close() !void {}
};
```

Здесь читалка уже сложнее. Синхронный интерфейс возможен, но не универсален - он более-менее терпим для старта, хотя и
не оптимален, ибо индекс поднимает данные для себя и для зеркал. И совершенно не подходит для задачи прилетевшей с
другого хоста "отдай записи начиная с состояния X". Разберем это вопрос ниже, а пока работаем с записью.

Запись должна сохранять согласованность данных. При это держим в уме, что кормить производителей твердотельников - идея
плохая по очень многим причинам. Поэтому мы сразу отказываемся от сброса записей по одной с `O_DIRECT`.

Предлагается два режима работы. Оба - с буферизацией. Но будет так же буферизация рассчитанная на спец-железо, которая и
работает со скоростью памяти (ессно медленнее, чем "обычная" работа с памятью, которая амортизируется кешами на ЦПУ).

## Буферизованная писалка с оциональным NVDIMM.

Мы здесь имеем массив буферов расположенных последовательно и массив метаданных буферов, где метаданные имеют размер в
64 байта.

Разложение памяти аналогично для обоих режимов:

```zig
   buffers: []u8, // длина index_count * buffers_count * buffer_size.
   headers: []BufferHeader, // длина среза - index_count * buffers_count.
```

причем в случае NVDIMM (PMEM-режим) мы используем НЕ аллокатор, а сразу метим место mmap-нутой NVDIMM-плашке. Для этого
какую-то область этой памяти отдаем под индекс-потоки и делим это пространство по количеству индексов
`(host_idx, index_idx)`. А уже в этой индекс-области размещаем буфера и хидеры. Количество буферов задается в конфиге,
так же как количество хостов (равно фактору репликации) и размер LBA (изменение любого из этих параметров в конфиге
потребует миграции - для этого в тулчейне будет заведена команда/команды).

При записи мы (последовательность критически важна!):

1. Проверяем, что места (объем в свободных буферах + остаток в текущем) хватит для записи новой порции данных. Если
   нет - сразу отлуп. Причем ситуация, когда мы получаем полностью заполненный последний буфер - а дальше места нет -
   так же считается ошибочной. Последний момент принципиален.
2. Пишем все данные в буфер.
3. Если текущего буфера не хватает, мы захватываем новый и пишем в него. В PMEM-режиме Каждая операция записи
   сопровождается CLWB -> SFENCE для сброса данных из кеша в эту самую NVDIMM-плашку по-настоящему.
4. Если в результате записи мы получили ровно заполненные буферы, мы захватываем следующий и пишем его длину: 0 и
   снимаем флаг заполненности. Так же с CLWB -> SFENCE.
5. Изменяем метаданные буфера бывшего текущим на начало операции. Если он перестал бы текущим (были захвачены новые)
   ставим на него флаг завершенности. Сопровождаем изменение, разумеется, CLWB -> SFENCE. Здесь, внимание, вначале
   изменяются метаданные ПОСЛЕДУЮЩИХ буферов (здесь последовательность может сохранятся, т.е. изменяем мету следующего
   буфера, затем следующего после него и т.д), и только под конец делаем "коммит", изменяя мету старого буфера.
6. Ставим заполненные буферы в очередь на запись начиная с определенной позиции. Причем НИКОГДА не кидаем сразу
   несколько буферов, чтобы не получить ситуации когда у нас записан N+1-ый буфер, но нет N-го из-за дерижирования
   потоками исполнения в ядре ОС. Это всегда: кидаем задачу на запись начиная с позиции Offset в SQ, дожидаемся ответа в
   CQ, ставим следующую задачу (если следующий буфер помечен заполненным). При этом, после записи, метим сброшенный
   буфер пустым.

Операция записи здесь обязательно должна делаться как O_DIRECT минуя кеш страниц ОС.

## Формат данных.

Запись выглядит как

| `state_idx` | `uvarint(len(op))` | `op...` |
| ----------- | ------------------ | ------- |

Мы пишем данные блоками по 1Миб. Где последние 4 байта содержат CRC32C (Castagnoli) хеш по содержимому блока. Если новая
добавляемая запись не лезет в остаток, мы добиваем текущее содержимое нулям (учитывая эти нули в хеше) и новую запись
пишем уже в следующем мегабайте. Это нужно учитывать при оценке длины.

Замечание: нужно использовать готовую функцию

```zig
pub fn hardwareCrc32C(data: []const u8) u32 { ... }
```

Доступную через `@import("blog").hardwareCrc32C` для вычисления CRC32C для блока и использовать стандартный комбинатор
для хешей конкатенации блоков.

## Вычитка

Верхнеуровневая логика. В обоих режимах мы игнорируем хвост файла, если остаток меньше длины буфера. В PMEM-режиме у нас
добавляются блоки в памяти. Файл относится к определенной паре `(host_idx, index_idx)`, поэтому мы понимаем, где искать
буфера.

Сами буферы рассматриваются как кольцо, где определенной длине файла соответствует строго определенный буфер, могущий
содержать следующие данные. Допустим, `buffers_count` у нас равен 32. Каждый буффер для пары имеет длину `|LBA|`. А
длина файла равна `|LBA| * N`. Тогда буфера с индексами `(N mod 32 + 1) mod 32`, `(N mod 32 + 2) mod 32` и т.д. по
формуле `buffer_idx(N + k) = (N mod 32 + k) mod 32` могут содержать дополнительные данные, которые еще не были сброшены
перед, скажем, отключением питания. Мы вначале читаем файл, а затем, ориентируясь по состоянию хидеров, дочитываем из
памяти.

Поиск делать двоичным: мы знаем, что блоки делятся на 1Mib области снабженные CRC32C в конце, так что мы гарантировано
попадем в самое начало следующей записи, если начнем читать с границы мебибайта. По содержимому мы понимаем, где
находимся и можем сразу отсеивать случай когда индекс первой записи там больше.

### Как это предлагается реализовывать.

Первое, мы должны определять "начало". Т.к. читаем мы либо с самого начала при старте, либо вначале ищем позицию
операции с определенным индексом и читаем начиная с нее тогда, когда хост запросил операции начиная с определенной.

Состояние процесса у нас описывает что-то вроде

```zig
pub const FileReadProcess = struct {
    state: enum { Seek, Read },
    buf: []u8,
    fd: std.posix.fd_t,
    ...
}
```

и когда мы ставим задачу поиска, мы ставим `state = .Seek`, занимаем слот и кидаем туда что-то вроде

```zig
pub const TaskCtx = union(enum) {
   ...
   FileRead: struct{
     file_process: *FileReadProcess, // отсюда берется fd
     offset: u64,
     buf: []u64, // буффер в нужное число байт
   },
}
```

которая, придя в CQ, будет обработана в зависимости от `state` и будут проведены дальнейшие действия (продолжение
поиска, начало вычитки и т.п.)

судя по всему, в `FileReadProcess` нужно так же держать какое-то описание текущей задачи, которую выполняет данный
процесс. Потому что выдача операций с начала - это одно, одна только безальтернативная вычитка. А вычитка начиная с
нужного состояния - другое.
