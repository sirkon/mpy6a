# Формальная архитектура шарда mpy6a.

Для понимания материала необходимо ознакомиться с [shard-arch-concept.md](shard-arch-concept.md)
и [consensus.md](./consensus.md).

## 1. Конфигурация и взаимодействие внутренних и системных акторов.

### Топология потоков (Thread-per-Core)

- **Индексы:** Обрабатывают логику консенсуса по сессиям. Висят на изолированных кольцах `io_uring`.
  Каждый поток жестко прибит к своему ядру CPU (`pthread_setaffinity_np`).
- **Фронты:** Принимают входящие TCP-соединения, парсят батчи smart-клиентов и выполняют первичное
  рукопожатие.
- **Слоны:** Фоновые воркеры для тяжелых синхронных/блокирующих задач (DNS-резолв, генерация снапшотов памяти). Общаются
  с Индексами через lock-free SPSC очереди.

### Ядерный бюджет и SQPOLL

Для исключения системных вызовов `sys_enter` на fast-path путях используется ядерный поллинг `IORING_SETUP_SQPOLL`.
Формула распределения ядер хоста:
`Общее число ядер = 2 * (Фронты + Индексы) + Слоны` (при схеме 1 кольцо = 1 поток SQPOLL).

## 2. Как поднимается система (Восстановление)

1. **Локальный старт:** Индекс вычисляет путь к данным, читает последний иммутабельный слепок (Snapshot) и докручивает
   поверх него операции из локального WAL-лога.
2. **Сетевой догон (Catch-Up):** Через абстрактный интерфейс реплик индекс находит адреса зеркал и запрашивает векторные
   часы. После чего в ускоренном режим подсасываем либо логи, либо снапшоты убежавшего состояния + логи.
3. После догона вычисляем текущую эпоху (см. [консенсус](./consensus.md)) и сверяем ее с ожидаемой у кластера. Если
   сессии предыдущей эпохи не изолированы, предлагаем консенсусу сделать это.

- При малом отставании: зеркало стримит недостающие операции из своего WAL.
- При критическом отставании: зеркало передает полный снимок состояния, после чего индекс накатывает дельту и объявляет
  себя готовым (`State: Active`).

## 3. Протокол сетевого взаимодействия

### Фаза Рукопожатия (Handshake)

Любое новое соединение на Фронте обязано прислать первым пакетом структуру `HandshakePacket`.

- **Если тип = INDEX_REPLICATION:** Фронт извлекает `SrcIndexID`, находит соответствующее локальное кольцо Индекса и
  передает владение сокетом (`fd`) ему. Фронт полностью исключается из дальнейшего обмена по этому сокету.
- **Если тип = CLIENT_TRANSPORT:** Сокет остается под управлением Фронта. Фронт начинает читать из него батчи задач.

### Роутинг запросов клиентов

- **Команда "Создание сессии":** Фронт выбирает наименее нагруженный Индекс (по схеме Round-Robin или наименьшей очереди
  задач), генерирует составной `SessionID` (включающий ID этого Индекса) и отправляет задачу на создание через
  `io_uring_msg_ring`.
- **Команды мутации/чтения:** Фронт извлекает номер Индекса из битовой маски `SessionID` и напрямую перенаправляет пакет
  в кольцо нужного Индекса.

### Индекс сессии.

Предварительно.

| `host_id: u8` | `epoch_id: u56` | `index: u64` |
|---------------|-----------------|--------------|

Оно же является индексом состояния индекса (тьфу). Идентификатор сессии становится равен текущему индексу состояния.

### Обмен пульсом между индексами.

Индексы с определенной периодичностью обмениваются друг с другом пульсом. В котором они в векторных часах
развозят слепок голов по всем индексам (своим и чужим).

Этот обмен может проводиться либо в рамках фронтов, либо в рамках конкретного индекса. В первом случае
довозятся слепки состояния снятые через атомики. Несоответствие некоторых значений друг другу (первый снятый компонент
часов неминуемо будет более поздним чем последний) нас не особо волнует, ибо разные индексы - разные сессии. А сессии
вообще никак не связаны друг с другом. Нас интересует только монотонность каждого из компонентов, а она имеется.

Таким образом, пульс будет состоять из n = (2f + 1)*idxcount записей, каждая по 16 байт.

Как вариант, возможно проводить такое взаимодействие в рамках каждого из индексов. Тогда каждый индекс
будет обмениваться такимии часами ТОЛЬКО по срезу своих зеркальных индексов и себя.

Надо предусмотреть оба варианта. Изначально основываемся на пульсе между индексами, т.е. 48 байт на репликации x3
и 80 байт при репликации x5.

### Работа индекса.

Каждый индекс ведет колесо времени, с помощью которого он отслеживает время жизни сессий у себя и время последнего
взаимодействия с зеркальными индексами. Если данный индекс напрямую общается с зеркальным индексом X, то он должен
отслеживать состояние X. Если от X слишком долго не было данных и другие субъект довозят состояние X не превосходящее
текущее, то данный индекс ставит задачу об отправке сессий на повтор. Причем, разные хосты выбирают разные сессии
(какой-то вычислимый критерий). При прохождении этого решения ожидаемый индекс лишенного лидерства над собственными
сессиями хоста увеличивает эпоху на 1. Так что если X заявится с новой пачкой данных, как-будто ничего не было, он
получит отлуп.

При получении задачи на репликацию от зеркального X текущий индекс подготавливает запись в лог **индекса X**. Это
отдельный файл специально для индекса X. Это принципиальный момент и отличие от RAFT-а. На самом деле данный
алгоритм относится к семейству epaxos, а РАФТ-подобное взаимодействие стало возможно благодаря жесткому
делению на индексы и относительной дешевизне записи в разные файлы при использовании io_uring.

#### Состояния индекса.

Индекс имеет два состояния:

- Поллинг CQ.
- Поллинг LLQ (lockless queue) от фронта.

Которые он переключает последовательно:

1. Вычитка до 16 элементов из CQ.
2. Вычитка до 16 элементов из LLQ.
3. По результатам вычитанного изменяем состояния.
4. Повторяем начиная с 1.

В целом, динамика индекса выглядит следующим образом:

1. Вычитали элементы из CQ.
2. Вычитали элементы из LLQ.
3. Пробегаемся по ним по всем (не забывая про буфер переупорядочивания при получении данных по сети),
4. Формируем для каждого события из CQ и LLQ реакцию, это либо сформировать команду в SQ, либо что-то еще.
5. Коммитим записи.
6. Повторяем с пункта 1.

#### Состояния сессий.

- ExpectProgress. Ожидание любой команды относящейся к данной сессии.
- ExpectConsensus: Сессия ожидает консенсуса по операции.
- ExpectOpLog: Сессия ожидает завершения записи в лог операций.
- ExpectReply: Сессия ожидает успешной отсылки ответа клиенту.

В самой сессии хранится код текущей операции. Пришедшее подтверждение для другого типа операции означает немедленную
ошибку.

## Субъекты и их взаимодействие.

Субъект - это либо клиент, либо внутренний субъект (фронт, индекс или слон):

- Каждый из внутренних субъектов имеет свое кольцо.
- Состав субъектов фиксируется при старте приложения.
- Каждый из субъектов создает свое кольцо и сохраняет его в массиве.
- Кроме этого, индексы отдельно создают LLQ-очереди (lockless очереди) и так же регистрируют их в "публичном" массиве.
- Количество фронтов равно степени двойки len (Fronts) = 2^F. Количество индексов равно степени двойки len (Indices) =
  2^I. I > F.
- Каждый фронт работает ТОЛЬКО со "своими" индексами, которых он однозначно определяет по своему и по их идентификаторам
  по предикату $P \left (sid\cdot 2^{I - F} \leqslant iid <  (sid+1) \cdot 2^{I-F} \right)$, где `sid` - идентификатор
  фронта, а `iid` - идентификаторы индексов. Которые индексы являются просто порядковыми номерами.

Здесь у внутренних субъектов:

- Фронты получают задачи от других субъектов через CQ, в который прокинут индекс слота с описанием задачи. Т.е. другие
  субъекты захватывают слот (хоть через мутех - это редкое явление), заполняют его и кидают через СВОЮ очередь сообщение
  адресованное дескриптору очереди фронта с указанием индекса.
- Слоны получают свои задачи так же как и фронты.
- Индексы получают задачи через LLQ (**L**ock **L**ess **Q**ueue) очереди или через тот же CQ, но для задач
  маршрутизации это исключительно LLQ.

Подключаются к сервису. Фронт, каждый из которых поставил задачу на MultishotAccept:

- По RoundRobin определяет идентификатор фронта, который будет работать с этим подключением.
- Передает задачу "работа с данным дескриптором" выбранному фронту.

### Передача задач через сообщения io_uring.

Для нее мы имеем кольцевой или list буфер достаточно размера. Со спинлоком для надежности. С поллингом
"крутимся пока не появится слот". Субъекты ОБЯЗАНЫ немедленно копировать задачу и освобождать слот при получении
извещения.

Для постановки задачи мы:

1. Запрашиваем идентификатор свободного слота.
2. Формируем задачу в нужном слоте.
3. Передаем через сообщения io_uring индекс слота адресуя получателя через дескриптор нужного субъекта.

Здесь мы передаваемые сообщения делим на две части: с msg result меньшим C = maxU32/2 и большим. Коды >= C
означают, что нагрузки нет и это передача каких-то определенных фиксированных задач без параметров.
Если меньше, то описание задачи содержится в контейнере для задач.

#### Реализация контейнера для задач (РКЗ).

Отдельная задача представляет собой одну из ветвей ADT (union в Zig). Технически, оно выполнено как:

- Массив `tasks: []Task` размером N с задачами фиксированного размера.
- Индекс `head` первого свободного слота (0 после инициализации) для получения по нему свободного слота.
- Индекс `tail` последнего свободного слота (N-1 после инициализации).
- Массив `nexts: []i32` того же размера, что и массив с задачами. Где содержимое указывает на индекс следующего
  свободного элемента для не последнего элемента и -1 для последнего. Содержание после инициализации:

  | Индекс   | 0   | 1   | 2   | ... | N-2 | N-1 |
                  | -------- | --- | --- | --- | --- | --- | --- |
  | Значение | 1   | 2   | 3   | ... | N-1 | -1  |

**Здесь занятие слота будет выглядеть как:**

1. Берем лок.
2. Берем `i = head`. Если `i < 0`, то выходим с ошибкой - места нет. Снимаем лок ессно.
3. Делаем `head = nexts[i]`.
4. Снимаем лок.
5. Пишем в `tasks[i]` описание задачи.

**Освобождение слота i**

1. Берем лок.
2. Сразу помечаем его последним: `nexts[i] = -1`
3. Альтернатива: `head < 0` (свободных нет):
    - Свободных нет. Тогда `head = i`, `tail = i`
    - Свободные есть. Тогда `nexts[tail] = i` и сразу `tail = i`.
4. Освобождаем лок.

### Передача задач через LLQ-очередь от фронта к его индексам.

Такой способ передачи задач применяется ТОЛЬКО при маршрутизации запросов от клиентов через фронт на нужный индекс.

Данные от клиентов имеют две формы:

- Задача создания новой сессии. По которой индекс выбирается произвольным образом: RoundRobin, случайный и т.п.
- Задача относящаяся к существующей сессии, что отражено в первых байтах нагрузки. По которой сразу понятно, какой
  индекс ее обслуживает (идентификатор сессии содержится в ответе на задачу создания новой сессии, все дальнейшие
  взаимодействия в рамках данной сессии проводятся с этим идентификатором).

Если места в LLQ индекса нет, фронт НЕМЕДЛЕННО ставит задачу по отправке клиенту сообщения об ошибке и сообщает
об этом в логах. Ничего кроме этого делать не нужно. Если это была внутренняя операция сессии, то эта сессия в конечном
итоге протухнет (т.к. клиент не будет более слать обновлений для нее) и будет отправлена на повтор. Как вариант,
можно держать дополнительный буфер для отсроченной отправки задачи. Но в конечно счете все сведется к описанному
механизму "ничего не делать", если забьется и буфер.

Передача задачи через LLQ должна сопровождаться посылкой сообщения через SQ в кольцо индекса, если тот индекс
пометил себя спящим (что может сопровождаться засыпанием на ожидания данных из CQ своего кольца).

Делается это следующим образом:

На фронте выбираем LLQ нужного потока.

1. Пишем данные в кольцо.
2. Проверяем состояние бинарного флага "sleep". ВНИМАНИЕ: мы НЕ ИЗМЕНЯЕМ этот флаг. ТОЛЬКО ЧИТАЕМ.
3. Если флаг говорит, что индекс "уснул", посылаем через сообщение.

В это время сам индекс проверяет входящие данные следующим образом:

1. Вычитывает до K задач из CQ и LLQ. Если задачи есть, то обрабатываем их и повторяем с 1.
2. Если N раз задач не было:
    1. Ставим флаг sleep.
    2. Еще раз делаем попытку вычитки - задачи могли появиться, пока мы ставили флаг. Если задачи появились, то
       сбрасываем процесс подготовки к засыпанию, в т.ч. сбрасываем флаг sleep и обрабатываем появившееся. Потом
       повторяем с 1.
3. Подвисаем на ожидании данных из CQ.

### Обвязка передачи задач через кольцо io_uring.

Как мы видим по предыдущим пунктам, кольцо может использоваться как для непосредственного довоза задач, так и для
извещений подвисших потоков о наличии у них задач.

В связи с этим, есть идея иметь обвязку, которая занимается доставкой обоих этих типов сообщений.

Я планирую реализовать следующий подход:

Есть общая для всех потоков РКЗ (см. на несколько пунктов выше про контейнер задач), которая висит
готовая в [cross_task_slots.zig](../src/cross_task_slots.zig).

Мы вводим специальные taskIdx для этих двух задач. Скажем,

```zig
const CrossTaskMessageIdx = std.math.maxInt(u64) - 2;
const FrontTaskNotificationIdx = std.math.maxInt(u64) - 3;
```

Соответственно, задачи с описанием будут перевозиться с первым кодом, а их API будет содержать индекс
с описанием задачи:

```zig
pub fn sendTask(self: *Self, receiverFd: posix.fd_t, slotIdx: u32) !void {}
```

А задача извещения будет выглядеть как, где под капотом для taskIdx будет использоваться второй код.

```zig
pub fn sendWakeup(self: *Self, receiverFd: posix.fd_t) !void {}
```
