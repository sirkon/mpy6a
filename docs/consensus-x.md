# Асинхронный консенсус.

Узел состоит из 3, 5, 7 и так далее машин. Количество машин обозначим через F и будем называть это число фактором
репликации.

Между любыми двумя машинами имеется двунаправленное подключение.

Каждая машина хранит полное состояние каждой другой ИЗОЛИРОВАННЫМ образом. Т.е. на каждой машине имеется состояние i-ой
машины, лог i-ой машины, она делает снапшоты i-ой машины, через консенсус или локально - неважно, `i = 0..(F-1)`

## Обслуживаемая логика.

Если клиент делает изменение существующей области данных X, он обязан дождаться подтверждения проведения предыдущей
операции над X. Следующая операция мутирующая X может идти ТОЛЬКО после подтверждения предыдущей операции.

Никакие два набора данных X и Y не пересекаются.

Т.е. операция мутации Y не обязана дожидаться подтверждения следующей ровно перед ней операцией мутации X.

Данные НЕ МИГРИРУЮТ (на лету). Если они были в рамках i-ой машины (т.е. i-го состояния, они там и остаются). i-ая машина
является лидером i-го состояния. Миграции возможны, но они никогда не пересекаются с клиентскими операциями.

## Предлагаемая логика консенсуса.

Отлупы при прилете операции над X, над которым в данный момент идет подтверждение мутации, мы возлагаем на валидацию на
основе имеющегося состояния, так что в консенсус пролетают только валидные операции.

Клиентские операции СТРОГО УПОРЯДОЧИВАЮТСЯ при обработке каким-то образом. Каким - неважно. Но обработчик имеет дело с
потоком, который он считает эталоном порядка и операции в рамках консенсуса строго соответствуют этому однажды
полученному порядку.

Допустим, клиент добавляет данные к существующему значению X – `X.Append(data)` – и перезаписывает значение Y как
`Y.Overwrite(data)`. Эти операции отображаются в логе как `Append(X, data)`, `Overwrite(Y, data)` и т.п.

Кроме этого, у операций имеется "кармашек", в котором закодированы последние решения по предыдущим операциям, были ли
они подтверждены большинством или нет:

```zig
const CommitEnvelope = struct {
    first_uncommited: StateType // u128, скорее всего
    size: u32,     // Скока операций
    bitmap: []u64, // просто битмапа для first_uncommited = M, M+1, M+2, .... 1 - подтверждено, 0 - не подтверждено.
}
```

Если количество еще не разрешенных операций слишком сильно выросло, превысив некий предел N, обслуживание клиентов
приостанавливается до тех пор, пока курсор подтверждений не сдвинулся.

Соответственно, при чтении лога мы не считаем операцию подтвержденной, пока в какой-то операции прописан явный коммит
для нее.
